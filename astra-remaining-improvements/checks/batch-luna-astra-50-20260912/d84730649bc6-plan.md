## Confirmed defect and bounded change

`getIncidentDetail` validates the requested incident with `canViewIncident(actor, incident)`, but its `parentIncident` lookup and `childIncidents` selection embed complete related Incident objects without checking visibility. A viewer allowed to see a public child can receive its confidential parent's title, description, services, assignee and escalation state. A public parent similarly exposes confidential children. The direct confidential-detail check and dashboard list filter do not protect these nested reads.

Apply the existing `canViewIncident` predicate to each parent/child candidate before embedding it. A hidden parent must become `null`; hidden children must be omitted; visible relationships and ordering remain intact. The rule is already defined: admin sees all; any user sees nonconfidential incidents; the assignee sees their confidential incident; a responder with matching service membership sees that confidential incident; an unrelated viewer/responder does not. Reuse this policy rather than inventing a second role rule. Preserve the selected incident's existing authorization and response contract.

This slice protects **embedded parent/child Incident records**. It does not claim to remove every relationship identifier from raw incident fields or timeline metadata, to authenticate the demo `?as=` actor, or to redesign all response data. Broader identifier minimization, escalation side effects on reads, concurrent JSON writes and atomic evidence/file persistence remain explicit follow-ups. Do not add real notification, script or webhook execution.
