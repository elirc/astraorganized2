# Next 25 projects: implementation report

Completed September 8, 2026. This batch adds projects 51–75 to the previous 50, focusing on compact CRUD learning projects and bounded improvements to the larger teaching scaffolds. The changes are applied in each original Desktop folder, including the selected project in `_Organized Desktop`.

## What was delivered

- **25 project improvements**, with 697 changed or new files.
- **225 learning documents**, nine per project, totaling 200,261 words.
- **235 passing test cases**, 25 client builds and 14 server builds.
- **37 passing TypeScript checks**, 14 migration commands, 14 seed commands and 25 Chromium interaction checks.

The courses teach a junior SWE how to read the actual code, trace a request, validate input, preserve data integrity, test failures, debug and implement a related improvement independently. Optional exercises are clearly separated from delivered changes.

## Suggested learning order

Start with 51 and 58–61 for validation, edit forms and CRUD request flow. Continue with 52–56 and 72 for persistence, ownership and transactions. Study 62–66 for membership, capacity, checkout and booking races. Move to 67–71 for archive/restore and bulk audit consistency, then 57 for WebSockets and 73–75 for backup validation and authenticated application tracking.

## Verification scope

Checks used isolated working copies, disposable PostgreSQL schemas, temporary SQLite storage or fresh browser storage. The browser harness forwarded requests to actual local servers and adjusted CORS for its temporary origin. The original databases and dependency installations were not replaced. The two browser-storage projects used their own declared dependency installations; other checks used recorded verification-workspace dependencies. A clean install in every original folder and deployed integrations are not claimed.

The implementation includes repaired JSON seed serialization, database CLI scripts, compiled server entry paths, stable auth selectors and React module deduplication where needed. One support-ticket seed referenced a nonexistent `subject` column; it now uses the actual `title` column.

A 390px screenshot and document-width measurement were captured for every project. See each verification page for its measured result; this is not a full responsive or accessibility audit.

## Boundaries and next work

- **JS1/legal-case-tracker:** A stable sort needs a secondary key. With several equal timestamps, ID determines the remaining order. Count matching records after filters, calculate the last page, clamp the request, then fetch that page. Synchronous array operations cannot interleave midway through an await because there is no await in that boundary. This explanation is specific to one process. Adding disk I/O or multiple API instances requires a new coordination design.
- **JS1/subscription-billing:** A stable sort needs a secondary key. With several equal timestamps, ID determines the remaining order. Count matching records after filters, calculate the last page, clamp the request, then fetch that page. A repeatable-read transaction keeps the count and rows from describing different database snapshots. The status transaction acquires a row lock before comparing status: a competing request waits, then sees the newly committed value. Both UPDATE and activity INSERT must use the same transaction client.

- **JS1/warehouse-ledger:** Number.isInteger checks the quantity rather than truncating it. A request for 1.7 units must not quietly become one unit. The bound matches the SQL integer column. The product lock is taken even for receipts so all writers participate in one ordering. Warehouse existence is checked before inserts; SQL foreign keys still protect stored references.
- **JS1/secure-notes:** The title has a 2–200 character rule; the body is text up to 20,000 characters. Validation happens before the note mutates. This is a small authentication teaching app, with in-memory sessions, open CORS and synchronous hashing. Persistent accounts, rate limits, session expiration and deployment configuration remain separate improvements.
- **JS1/live-chat:** Starting listeners at module import makes tests unexpectedly bind ports and retain database connections. Explicit lifecycle functions put those side effects under caller control. stopRuntime terminates sockets, closes the server and listener, and clears a scheduled retry. The current reconnection attempt is bounded teaching behavior, not a durable delivery guarantee: disconnected clients recover recent history, not an acknowledged message queue. Author names remain free-form demo labels, not authenticated users.

This is client request control, not server-side POST idempotency. Error feedback preserves a learner's draft so they can fix the problem and retry.

- **newcodexJS/12-chat-polling:** Polling retrieves messages after a cursor. Membership must be checked on every poll, not only when the UI first opens a room, because membership can change. - **newcodexJS/13-ecommerce-storefront:** The order, line items, stock decrement and cart removal share one transaction. It is not connected to a payment provider. Cart merge and administrative operations still need separate review before a production design.
- **newcodexJS/14-appointment-booking:** The booking notification is a database row, not an email sent by this task. Inserting it inside the booking transaction ensures the two records commit together. Availability windows, booking buffers, advance-booking policy and cancelled-record rescheduling remain separate business rules; the tested guarantee is overlap protection and atomic booking confirmation, not full scheduling policy enforcement.

- **recipeview:** A quantity is a number or a deliberate blank, not an arbitrary object coerced to zero. The browser parses kitchen fractions before sending JSON. The API validates nonnegative ingredient quantities and positive recipe yield. Canonical positive integer IDs reject strings such as 1e2 rather than interpreting them as another record. This remains a local personal recipe app without multi-user authorization.
- **calendar+jobtrack:** The parser is pure: it returns either a validated backup or an error. Purity makes malformed cases easy to test without touching storage. A future redesign could store one versioned document or use one IndexedDB transaction.

This app is a browser persistence study case; it does not contain a server CRUD API.

Other transitions still use ALLOWED_TRANSITIONS. This is a narrow retry guarantee; POST creation still needs a separate idempotency design. JWT ownership checks remain on every application path. JOB_TRACK_DATA_DIR lets tests use a fresh temporary database instead of touching the development data directory.
