## Does it transfer? (D4, stated plainly)
**The CRUD half transfers well; the stack transfers worse than any other project in the batch.** Astra made a smart call: rather than teaching an AI job-application bot (browser automation + LLM plumbing, entirely off-target), it grafted a genuine CRUD tracker onto the side and teaches *that*. The lessons — stable identity vs. mutable content, captured version as the concurrency token, data and audit written in one transaction, a draft that survives a 409, "a saved application and a refreshed library are separate outcomes" — are stack-independent and are among the clearest statements of those ideas in the whole set. But the implementation is Python's stdlib `http.server` with hand-rolled request routing in `applybot/dashboard.py`, which is not merely off-stack, it is *off-framework*: a learner will see nothing that resembles an Express router, a Next route handler or an ASP.NET controller, and nothing that resembles an ORM. The one genuinely on-stack artifact is `applybot/web/app.js` — plain `fetch`, a captured baseline (`const base = editor`), an `adopt()` that only advances the shown version on an accepted response, and a `run()` wrapper that disables conflicting actions. That file is worth reading on its own terms. The rest: read for ideas, do not copy the shape.

## What Astra did well
- The store is a textbook compare-and-swap and the course describes it line-accurately. `applybot/application_store.py:217-243`: validate first (`version_input`, `application_input`) *outside* the transaction, then inside `transaction()` load the row, compare versions (409), `UPDATE … WHERE id=? AND version=?`, `if changed.rowcount != 1: raise StoreError(…, 409)`, `self._audit(db, identity, "UPDATE", expected + 1)`, re-read. Delete (`:245-257`) does the same with `DELETE … WHERE id=? AND version=?`.
- The wire contract separates business input from concurrency metadata, and the adapter enforces it: `applybot/dashboard.py:203-212` requires the request body's keys to be exactly `{"version", "application"}` (or `{"version"}` for delete) and otherwise answers "Supply the captured version and the editable application for updates." 03-WORKED-CHANGE.md states this as the design rule: "The client cannot put server-generated identity or timestamps inside the editable value."
- The course keeps success and refresh as distinct outcomes, which is a subtle failure mode juniors routinely get wrong: "Contrast that with the browser test where the save succeeds but the following list refresh fails: the saved notice stays visible, the accepted editor version advances, and the library reports its separate problem." (03-WORKED-CHANGE.md) — and practice exercise 2 tests the same idea again ("a failed count refresh does not relabel a successful save as failed").
- It did not touch the user's personal data. The backup (`backups/da9c28730758/`) contains only 7 pre-existing files (`applybot/{browser,cli,llm,profile,tracker}.py`, `profile.example.yaml`, `README.md`); `profile.yaml` was never modified, matching the stated limit "Personal profile and browser session were not loaded or changed."
- Test count is exact: 13 + 12 + 10 + 8 = 43, matching `deliveries/da9c28730758.json` `modelTests: 43` and VERIFICATION.md's "runs 43 tests".

## Problems found (evidence required)
- **[D4]** Off-stack and off-framework. `applybot/dashboard.py` hand-parses paths (`if len(parts) in (3, 4) and parts[:2] == ["api", "applications"]`) on top of `http.server`, so nothing about request routing, middleware, dependency injection, ORM mapping or migrations carries to Express/Next/ASP.NET. No file in `astraupskill/` mentions any target-stack technology — the only hit for `typescript|express|\.net|C#|react|node` across all nine files is an incidental "Node 22.16.0 checks browser JavaScript syntax" in VERIFICATION.md:9.
- **[D3/D8]** The course is the thinnest in the batch at 4,029 words, and several chapters read close to a generic CRUD template with this project's nouns substituted. The README's journal framing ("Keep a learning journal with observation, hypothesis, experiment, and result") and the closing milestone paragraph are structurally the same advice that `grokbuildorderproject/astraupskill/README.md` and `grokbuildteamproject/astraupskill/README.md` give in their own words; here it carries less project-specific weight because 02-CONCEPTS.md is only 437 words. The *practice* chapter is the specific one — exercise 1's "Validate real calendar dates, including leap days" and "Do not recreate the database to avoid migration work" are pointed and local.
- **[D5]** Setup is one command (`python -m applybot dashboard --data-dir .\practice-data`) with no virtualenv or dependency step in `astraupskill/README.md`; the install instructions live only in VERIFICATION.md ("install the development requirements in a virtual environment, install Chromium") and the root `README.md`. A junior following the course README in order will hit an import error before reading VERIFICATION.md, which is chapter 9 of 9.
- **[D7]** The tracker shares a package with the original job-automation code (`applybot/browser.py`, `llm.py`, `ats.py`, `tracker.py`), and `tests/test_profile_and_cli.py` (12 of the 43 cases) covers profile validation and offline planning rather than CRUD. 01-CODEBASE-MAP.md does separate them, but a junior opening `applybot/` sees eleven modules of which four are irrelevant to the lesson.

## One-paragraph summary for the index
Astra took a job-application bot — a project with almost no CRUD value — and grafted a genuinely good local application tracker onto it, then taught that instead. The core is `ApplicationStore.update`: validate outside the write transaction, compare the captured version, `UPDATE … WHERE id=? AND version=?`, insist exactly one row changed, write the audit event in the same transaction, re-read the accepted row. The browser half is equally careful, capturing a baseline before the request, keeping the draft when the save is rejected, offering export and an explicit "load current", and — the detail worth stealing — keeping "the save succeeded" and "the list refresh failed" as two separate, independently reported outcomes. 43 Python tests and 8 Chromium scenarios exist exactly as claimed, and the delivery provably never opened the user's real `profile.yaml`. The limitation is the stack: Python's stdlib `http.server` with hand-rolled routing and hand-written SQL, so nothing about framework structure, ORMs or migrations transfers to Node or .NET. Do it as a short elective for concurrency and draft-recovery thinking, read `applybot/web/app.js` properly, and set up the virtualenv before chapter 1 because the course README forgets to tell you to.
