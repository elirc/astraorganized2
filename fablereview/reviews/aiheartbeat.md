## What Astra did well
- The lesson chosen is a genuinely good one and is explained from first principles: `03-WORKED-CHANGE.md` — "Values such as task ids are bound with `?`, but SQLite parameters cannot stand in for an identifier. The collection is therefore the one value that must be converted to a table fragment." That distinction (bound value vs. interpolated identifier) is exactly what juniors get wrong.
- **Verification honesty is the best in the batch.** `VERIFICATION.md` states outright that the change is defence in depth, not a fixed exploit: "The results therefore establish defense in depth for direct store callers, not a demonstrated exploit against a previously unvalidated HTTP route." It also volunteers that npm "emitted repeated invalid/damaged lockfile warnings while reifying dependencies" and that "passing checks do not mean those installation warnings were never emitted".
- It even talks itself *out* of an overclaim it could have made: `03-WORKED-CHANGE.md` — "The explicit route `.safe()` documents the policy, while Zod 4's integer validation already rejects unsafe integers; the course does not present it as a separate SQL-injection fix." That is correct, and rare.
- The new regression is a real negative test with a state comparison, not a `toThrow` smoke test: it seeds one row in each of the three tables, snapshots `readWorkspace(db)`, fires three hostile collection strings and six invalid ids at both `save` and `delete`, re-compares the entire decoded workspace, then proves a valid write still succeeds (`packages/dashboard/lib/workspace-store.test.ts:39-64`).
- The repro block in `VERIFICATION.md` is unusually careful: it pins Node 22.16 / npm 10.9.2, creates a GUID-named temp folder and points `PULSE_WORKSPACE_DB` at it so the learner's real `workspace.db` is untouched, checks `$LASTEXITCODE` after every step, and warns that "Calling the root `npm test` with additional flags introduces another npm script layer, so inspect forwarding before assuming a concurrency or timeout option reached the test runner."

## Problems found (evidence required)
- **[D2]** The delta is very small and the practical risk it closes is narrow. The HTTP route already validated the collection with `z.enum(["projects","tasks","applications"])` (unchanged, `packages/dashboard/app/api/workspace/route.ts:8`), so the guard only protects callers that bypass the route *and* violate the `Collection` TypeScript type — which the new test can only reach through a deliberate `as never` cast. The course says as much; the score reflects that this is a hardening nit rather than a CRUD improvement.
- **[D2]** The other production edit is a no-op by Astra's own admission: adding `.safe()` to `z.number().int().positive()` changes nothing under Zod 4 (`03-WORKED-CHANGE.md` concedes "Zod 4's integer validation already rejects unsafe integers"). So of two changed source files, one contains a documentation-only change.
- **[D2]** Nothing in the actual CRUD surface improved: no ownership checks, no pagination, no idempotency, no conflict handling, no payload-level validation beyond what already existed. The store already had `BEGIN IMMEDIATE`, Zod record schemas, `PRAGMA foreign_keys = ON` and `ON DELETE SET NULL` before Astra arrived — the course teaches those, it did not add them.
- **[D2, churn]** `README.md` shows as a 419-line replacement in the diff, but `diff <(tr -d '\r' old) <(tr -d '\r' new)` reduces to **four added lines** (a link to the course). Astra rewrote the whole file's line endings, which buries a four-line change in a whole-file diff — the opposite of what a reviewable commit should look like.
- **[D7]** `__proto__` and `constructor` are used as the hostile test inputs without ever explaining *why those two strings in particular* — prototype pollution and the `hasOwnProperty.call` idiom are assumed, not taught. `03-WORKED-CHANGE.md` mentions "three known own properties" and moves on.
- **[D3/D4]** Practice exercise 4 (import/export design) has no implementation and no runnable check; `VERIFICATION.md` correctly labels it "a proposed contract … a new importer was not implemented by this change", but that leaves a fifth of the practice list unverifiable.
- **[D4]** The host project is an agent orchestrator, not a CRUD app; only `packages/dashboard/lib/workspace-store.ts` (one file) is on-topic. A learner has to ignore most of the repo, and nothing in `01-CODEBASE-MAP.md` warns them how much of the monorepo is irrelevant to the lesson.

## One-paragraph summary for the index
A small, careful, scrupulously honest lesson wrapped around a very small change. The whole delta is two guard functions in one file: a collection name is interpolated into a SQLite table name (`workspace_${collection}`) because SQL parameters cannot stand in for identifiers, so a runtime string must be proven to be one of three known own properties before it reaches the query — a genuinely useful thing for a junior to internalise, demonstrated by a regression that fires `__proto__`, `constructor` and `tasks; DROP TABLE workspace_projects;--` at both save and delete and then diffs the entire workspace. The verification chapter is the best I read in this batch: the 505-test claim matches the shipped log line for line, the chapter states that the fix is defence in depth rather than a closed exploit, and it even points out that one of its own two edits (`.safe()`) is a no-op under Zod 4. Take it as a 90-minute elective on SQL identifiers, transactions and negative testing — not as a CRUD feature course, because no CRUD behaviour was actually added or fixed.
