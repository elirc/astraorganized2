## What Astra did well
- The code change is the real thing, not cosmetics. `extension/model.js:44-77` is a genuine command handler: unknown message types rejected, unknown keys rejected (`plain()`), `expectedRevision !== current.revision` throws a lost-update error, and create/update/delete each enforce identity rules ("Saved-message identity cannot change", "Saved message not found"). This is textbook optimistic concurrency in ~30 lines.
- The persist-then-reconcile ordering is implemented *and* taught. `extension/background.js:34-35` persists the accepted snapshot, then `try { return await reconcile(accepted) } catch { return {...await read(), warning:'Timer data was saved, but an alarm or break window could not be synchronized...'} }`. 04-TESTING-AND-DEBUGGING explicitly asks the learner to classify "did the write complete, or did the effect after the write fail?" — the single most transferable idea in this course.
- Verification honesty is exemplary. VERIFICATION.md's test breakdown ("six timer tests, three existing background tests, eighteen shared-model tests and twelve worker-reliability tests") matches the files line-for-line, and `astra-remaining-improvements/checks/interlude/first/browser.log` shows `"expected": 10, "skipped": 0, "unexpected": 0, "flaky": 0`. Limits are stated bluntly: "This remains a local app with no server database, authentication, multi-user access control or durable distributed outbox."
- 05-PRACTICE is labelled honestly as *proposed* work ("The following changes are exercises, not delivered features") and escalates properly: filter → duplicate → conflict recovery UI → HTTP+SQL service → ownership + outbox, with acceptance criteria per item ("an in-memory mock cannot demonstrate SQL concurrency").

## Problems found (evidence required)
- **[D4]** The project is a Chrome extension with `chrome.storage.local` / `localStorage`, not a CRUD web app. There is no HTTP API, no SQL, no React, no server-side authz anywhere in the delivered code — `server.js` is a 22-line static file server and 01-CODEBASE-MAP admits "it does not implement a database or CRUD API." The transferable concepts (validation at the boundary, revision checks, partial patches, commit-then-effect) are real, but the learner practises them against a browser storage key, and the only genuinely CRUD-web exercises (05-PRACTICE items 4 and 5) come with no scaffolding, no reference solution, and no fixtures.
- **[D7]** The codebase is written in an extremely dense single-line style that a junior will struggle to read. e.g. `src/app.js:202` is one statement spanning ~700 characters chaining three `button(...)` factories with inline async handlers. The course never warns about this or offers a reformatted reading copy.
- **[D7/D3]** 3,774 words across 9 files is thin for the density of ideas (~420 words/file). 02-CONCEPTS has to cover drafts, revisions, validation and committed side effects in a few paragraphs; there are no diagrams and no worked "predict the output" quiz items with hidden answers — the predictions are prose instructions ("Explain this behavior before reading the implementation") rather than checkable prompts.
- **[D5]** Setup requires `npx.cmd playwright install chromium` and the browser suite launches a real unpacked extension via `chromium.launchPersistentContext` (`tests/browser/interlude.spec.js:39`) with `channel:'chromium'`. On a fresh machine without that channel installed, scenario 10 fails for environmental reasons and the course does not say how to skip it or what a partial pass looks like.

## One-paragraph summary for the index
Interlude is the best-argued course in this batch, but it teaches CRUD by analogy rather than on the target stack. The code change is real engineering — a pure validation/command model with optimistic `expectedRevision` concurrency, full saved-reminder CRUD, and a service worker that persists accepted data before reconciling alarms and reports a warning when the after-effects fail — and the 39 Node plus 10 Chromium tests genuinely exercise those paths, with evidence logs that match VERIFICATION.md exactly. Do this one if you want to understand *why* lost updates happen, why a partial `PATCH` is safer than sending the whole settings object, and why "the write succeeded but the side effect did not" is a distinct outcome that needs its own user message. Do not do it expecting to write HTTP handlers, SQL or React: there is no server, no database and no auth in the delivered code, and the exercises that would add them (05-PRACTICE items 4–5) are proposals with no scaffolding. Treat it as a strong elective on concurrency and commit boundaries, taken after you already have one Node+SQL CRUD app under your belt.
