## What Astra did well
- The tests are the real thing, not mocks. `apps/api/test/workers.spec.ts:8-14` refuses to run unless `WORKFORCE_TEST_DATABASE === "owned-temporary-cluster"`, the host is `127.0.0.1` and the database is `astra_workforce_test`; `scripts/test-database.mjs` spins up a throwaway PostgreSQL cluster in `mkdtempSync`, migrates, runs Jest over supertest, then stops the cluster. This is the strongest verification setup in the batch by a wide margin.
- The atomicity claim is actually proven at the database. `workers.spec.ts:417-440` installs a real `BEFORE INSERT ON "AuditLog"` trigger that raises on `WORKER_UPDATED`, issues the update, then confirms the worker row is unchanged and drops the trigger. That is how you demonstrate rollback — not by asserting a mock was called.
- Optimistic concurrency is implemented correctly and for the right reason. `workers.ts:117-131` does `updateMany({ where: { id, tenantId, version, employmentStatus: { not: "TERMINATED" } }, data: { ..., version: { increment: 1 } } })` and throws a conflict when `result.count !== 1`. `02-CONCEPTS.md` even shows the equivalent SQL and explains why read-then-unconditional-update reintroduces the race, and why auto-retrying would silently discard the loser's work.
- Defense in depth is real, not asserted: application code rejects a foreign/inactive company (`workers.ts:63-74`), *and* the migration adds `Worker_companyId_tenantId_fkey FOREIGN KEY ("companyId","tenantId") REFERENCES "Company"("id","tenantId")` (migration.sql:442) plus `Worker_tenantId_email_key` (line 355). The course explains that these protect against different attackers.
- `VERIFICATION.md` is precise and self-incriminating where it should be: "The supplied Docker configuration was not run because a Docker daemon was unavailable", "The final browser phase was rerun after correcting workspace Vite resolution; the unchanged API suite's 29 passing results were retained as separate evidence", "Request-time account checks do not cancel an already executing transaction". The delivery `limits[]` repeats all of it.
- The screenshots are genuine renders of the running app, not mockups. `astraupskill/images/desktop.png` shows a populated directory with a row literally titled `<b>Literal</b> Learner` and revision numbers 1/2/6 — i.e. the XSS-literal-rendering and versioning claims are visible in the capture.

## Problems found (evidence required)
- **[D5/D6]** The evidence the course cites does not travel with the project. `astraupskill/` contains only the 9 markdown files and `images/`; there is no `evidence/` directory (compare master2/3/4, which ship `evidence/*.json` and `*.log`). `VERIFICATION.md` says "Logs and machine-readable results are recorded in the parent workspace's implementation checks and delivery manifest" — they are, at `AstraOrganized2/astra-remaining-improvements/checks/workforce/`. A learner who receives only this repo cannot check any of the 37 claimed results.
- **[D6, minor]** The API and browser numbers come from two different runs — `fourth/backend.json` (29 Jest) and `browser/browser.json` (8 Playwright). So "all 37 passed" was never observed in a single green run. It is disclosed, but the headline number is a composite.
- **[D3]** There is no failing-test-first loop anywhere. Because the app was written from scratch there is no before/after snapshot to diff, so `03-WORKED-CHANGE.md` walks an existing working flow rather than asking the learner to break and repair it. The one genuine hands-on moment is "repeat with two tabs" — good, but singular.
- **[D3/D7]** All five items in `05-PRACTICE.md` are open-ended design tasks ("Implement company maintenance", "Make retryable creation explicit"), and `06-SOLUTIONS-AND-REVIEW.md` deliberately gives review heuristics rather than solutions. For a *junior*, exercise 3 ("A concurrent worker create and company archive require a transaction/locking rule … Test both operations racing in real PostgreSQL") and exercise 5 (design an idempotency receipt with normalized payload fingerprints) are mid-to-senior tasks with no worked answer to check against.
- **[D7]** Every chapter is continuous prose with no subheadings except in `05`/`06`. 3,748 words describing a ~1,900-line application means the map is thin relative to the code; a junior opening `apps/web/src/App.tsx` (605 lines, single component file) gets very little guidance on the frontend half.

## One-paragraph summary for the index
The most complete project in this batch and the best model of what "good" looks like for a junior: an empty NestJS module becomes a real multi-tenant worker directory with scrypt password hashing, short-lived tokens re-checked against the account on every request, tenant predicates on every query, optimistic concurrency through a version-conditional `updateMany`, lifecycle guards, and audit rows committed in the same transaction as the change they describe. Uniquely in this batch the claims are proven against a real PostgreSQL cluster the test harness creates and destroys itself — including a rollback test that installs an actual failing trigger on `AuditLog` — and the reviewed screenshots show the running app. The weaknesses are pedagogical rather than factual: there is no break-it-then-fix-it loop, and all five practice exercises are open-ended mid-level design tasks with review heuristics instead of solutions. Budget several days, read `02-CONCEPTS.md` twice, and note that the evidence files the course cites live outside the project folder.
