## What Astra did well
- **The "audit only what actually happened" fix is a real observability bug worth teaching.** The backup `WorkManagementService.cs` ran `await AuditAsync(user, "automation.executed", …)` unconditionally at the end of the `foreach`, so an automation rule whose `MoveToStatus` value did not parse produced an `automation.executed` record with no execution behind it. The new code sets `var executed = false`, flips it inside each successful branch, and only then audits. An audit log that lies is worse than no audit log, and that framing is exactly right for a junior.
- **Validation is placed at two layers on purpose, and the course explains why.** `Enum.IsDefined` guards go into the domain (`WorkTask.ChangeStatus` throws `ArgumentOutOfRangeException`) *and* into the service (`UpdateStatus` returns `Result<WorkTaskDto>.Failure("Task status is invalid.")`) — throw at the domain boundary where a violation is a programming error, return a `Result` at the application boundary where it is user input to be mapped to a 400. That is the correct layering and the one juniors most often collapse.
- **`InvalidTaskPlan_PreservesAllExistingFields` tests the right thing.** It snapshots `(Priority, DueDate, EstimateHours, Status, Tags)` into a tuple, triggers a late-failing tag enumerable, and asserts every field is unchanged — then does the same for an out-of-range status. This is a state-preservation assertion, not an "it threw" assertion.
- **There is a genuine end-to-end HTTP test**, `HttpInvalidStatus_IsAClientFailure`, which starts the real API, `PATCH`es `{ status: 999 }` and asserts both `HttpStatusCode.BadRequest` and that the body contains "Task status is invalid" — closing the loop from domain guard to serialized HTTP response.
- **The limits are unusually self-critical.** They name a claim that was only *read*, not executed ("Legacy unsupported automation audit skipping was source-reviewed but not directly injected in the suite") and the precise weakness of the positive test ("asserts DTO state and audit presence, not exact audit cardinality or reloaded persistence").

## Problems found (evidence required)
- **[D2][D5] The HTTP test spawns a child `dotnet run` on a hardcoded port and requires a prior Release build.** `WorkManagementServiceTests.cs:162` launches `dotnet run --configuration Release --no-build --project src/BuildAsana.Api/BuildAsana.Api.csproj --no-restore --no-launch-profile --urls http://127.0.0.1:51937`, then polls `/health` up to 40 times at 250 ms. This fails on any machine where port 51937 is taken, fails if `--no-build` finds no Release output, adds up to 10 s to the suite, and resolves the working directory by walking `".." × 5` from `AppContext.BaseDirectory` — which breaks if the output path depth ever changes. `Microsoft.AspNetCore.Mvc.Testing`'s `WebApplicationFactory<Program>` does this in-process with no port, no prebuild and no child process, and is what the learner should be shown.
- **[D2] The course's own headline excerpt contains newly-introduced dead code.** The normalizer quoted in `03-WORKED-CHANGE.md` is `.Select(tag => string.IsNullOrWhiteSpace(tag) ? throw … : tag.Trim()).Where(tag => tag.Length > 0)…` — the `Where` clause can never filter anything, because any tag that would trim to length 0 has already thrown in the `Select`. The chapter reproduces this verbatim without noticing.
- **[D2][D4] Astra applied opposite judgements to the same anti-pattern in two projects in this batch.** Here the limits record "Frontend retains API-unavailable mock fallback and local-only board changes" — the client still substitutes mock data when the API is unavailable. In `.netvg` Astra *removed* exactly this pattern and made it the centrepiece lesson ("quote creation must not manufacture a success during an outage or business rejection"). Neither course mentions the other or explains when a fallback is honest (read-only dashboard) versus dishonest (a write that appears to succeed).
- **[D4] No persistence layer.** The repository is an in-memory dictionary; the limits confirm "In-memory shared references and dictionary locks do not supply durable transactions, aggregate rollback, or cross-request isolation". There is no EF Core, no SQL, no transaction — the "save/audit" sequence the course keeps referring to is two dictionary writes that can partially complete, which the limits say plainly but no chapter turns into a lesson about what a transaction would have bought.
- **[D8] The central lesson duplicates `.netzen`'s.** "Materialize the normalized collection before mutating, because deferred LINQ can half-apply" is the same insight as `.netzen`'s `ReplaceTags` fix, taught on a different noun (`Plan` vs `ReplaceTags`, `_tags` in both). The prose differs, so this is not copy-paste, but a learner doing both courses pays twice for one idea.

## One-paragraph summary for the index
A competent, well-evidenced validation course whose best idea is not the enum guards but the audit fix: the original code wrote an `automation.executed` record even when no automation branch ran, and seeing that spelled out ("an audit log that lies is worse than none") is worth the reading time. It also demonstrates the layering rule juniors most often collapse — throw from the domain where a bad enum is a programming error, return a `Result` failure from the application service where it is user input bound for a 400 — and backs it with 9 real xUnit tests that assert *state preservation* after a rejected call, including one end-to-end HTTP check that a `status: 999` PATCH returns 400 with a matching message. Counts reconcile exactly against the TRX and the limits are candid about what was only source-reviewed. Caveats: the HTTP test spawns a child `dotnet run` on a hardcoded port instead of using `WebApplicationFactory`, the repository is an in-memory dictionary so nothing here teaches transactions or EF Core, and the "materialize before you mutate" lesson duplicates the one in `.netzen`. Take it as an elective after `.nettrello`; budget 4-5 hours.
