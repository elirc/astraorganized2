## What Astra did well
- Business invariants are enforced on the whole aggregate rather than scattered through handlers. `src/lib/ledger-schema.ts:298-302` — after parsing, `for (const t of w.transactions) { requireRef(...); if (paid(w, t.id) > t.amountCents) throw new LedgerError("Payments cannot exceed a transaction amount."); }`. Note that `applyCommand`'s `payment` branch (`ledger-domain.ts:198-215`) deliberately does **not** check overpayment itself; it pushes the row and lets validation of the resulting workspace reject it. That is a genuinely instructive pattern and the course explains it.
- Money never touches floating point. `ledger-schema.ts:366-381` `decimal(value, scale)` regex-validates the literal string, builds `Number(whole) * 10 ** scale + Number(fraction.padEnd(scale,"0"))`, and rejects anything that is not a safe integer or exceeds `1_000_000_000`. Amounts are stored as `amountCents` / `deltaMilli`.
- The IndexedDB layer is correct in the ways that are easy to get wrong: the compare-and-set (`current.workspaceId !== reference.workspaceId || current.revision !== reference.revision` → `LedgerError(..., "conflict")`) happens **inside** the same `readwrite` transaction as the `put`, the mutation callback is synchronous, and there is an in-code comment explaining why — "The callback must be synchronous; unrelated awaited work can deactivate IDB transactions" (`ledger-storage.ts:163`). The promise resolves on `tx.oncomplete`, not on `request.onsuccess`, so the UI's "Saved" really means committed.
- Verification reports failures it found and fixed, which almost nothing else in this batch does. `VERIFICATION.md` §"Corrections discovered during verification": a second `BroadcastChannel` object was letting the sending tab hear its own message and show a false "another tab changed this" advisory; and two automation runs timed out on background tabs. It also states "Earlier failed logs remain available; they are not represented as passing evidence", and separates distinct checks from repeat runs ("Repeated runs and responsive screenshot rechecks are not added to the distinct-check count").
- It did not leave the old curriculum lying around to rot. 48 files under `docs/upskill/` received a header — "**Historical curriculum:** This file describes the earlier LocalOps implementation. Its source anchors and unimplemented-feature statements are preserved for comparison" — which is exactly right, because those files cite line numbers (`src/components/LocalOperationsApp.tsx:201-428`) that the refactor invalidated.
- Practice tickets are real ownership work with numeric acceptance criteria, e.g. Ticket 3: "Work through 10.50 owed, 3.01 paid, 1.00 reversed. The resulting outstanding should be 8.49, with the original payment and correction both visible."

## Problems found (evidence required)
- **[D5]** 15 of the 67 claimed checks come from `python scripts/verify_browser.py`, and **the course never names that command**: `grep -n "verify_browser\|python" astraupskill/*.md` returns nothing. `04-TESTING-AND-DEBUGGING.md:3-9` lists only `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`. A learner cannot reproduce the browser evidence, and there is no statement of the Python/Chromium prerequisites.
- **[D3]** Only three code blocks exist across the nine chapters (`grep -c '```'` gives 2 in each of 03, 04 and 07 and **0** in README, 01, 02, 05, 06 and VERIFICATION). A course whose whole subject is five new library files shows almost none of them.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` is "review guidance", not solutions — it gives policy reasoning for each ticket but no worked code and nothing to diff your attempt against. For tickets 2–5 (schema migration, payment reversal, moving a slice to a server, snapshot lifecycle) a junior will finish with no way to know whether they got it right.
- **[D7]** The material is mid-level. IndexedDB transaction deactivation, `durability: "strict"`, revision-based conflict detection, `BroadcastChannel` cross-tab advisories, schema versioning with strict objects, and whole-aggregate invariant validation are all introduced in 5,740 words with no glossary. `07-TRACE-LAB.md` even frames the goal as being able to "explain asynchronous IndexedDB behavior to another developer" — that is a senior-adjacent bar.
- **[D4]** The whole app is client-only. There is no HTTP layer, no Express/Next route handler, no SQL, no auth, no server-side validation anywhere in the course; `05-PRACTICE.md` Ticket 4 ("Move one CRUD slice to a server") is the only server content and it is left entirely as an unguided exercise. Half of the rubric's target stack (Node/Express, SQL, ASP.NET) gets no practice here.
- **[D2, risk not disclosed]** This is a rewrite, not a patch: `src/components/LocalOperationsApp.tsx` went 3,398 → 1,444 lines and `src/lib/local-business.ts` 804 → 884 with five new files. Feature parity is asserted by the 15 browser checks, but neither the course nor the delivery JSON contains an explicit before/after feature inventory, so a reader cannot confirm nothing was quietly dropped. A "what the old app did that the new one does not" table is missing.
- **[D1, minor]** `VERIFICATION.md` says "39 domain tests, 13 deterministic storage tests"; the file has 34 top-level `test(` calls in `tests/domain.test.ts`, with the balance coming from nested subtests. The total (52) matches the log exactly, so this is bookkeeping rather than inflation, but the per-file number cannot be reconciled by reading the source.

## One-paragraph summary for the index
An unusually complete piece of work: a 3,400-line "everything in one component" app taken apart into a validated schema layer, a command reducer gated on an expected revision, a reviewed legacy migration, and an IndexedDB repository whose writes are single transactions with a compare-and-set on `workspaceId` + `revision` and a promise that resolves on `oncomplete` rather than on the request callback. The domain lessons are the ones juniors most need — money as scaled integers, invariants enforced over the whole aggregate rather than per handler (overpayment is rejected by validating the resulting workspace, not by the payment branch), foreign-key guards before deletion, recurrence clamped to real calendar months — and they are backed by 52 node tests and 15 Chromium scenarios whose raw logs and nine screenshots are shipped, including a candid account of two bugs the verification run itself uncovered. Two caveats before you commit to it: everything is browser-local, so you will practise validation and concurrency but no HTTP, SQL or auth; and the chapters are almost entirely prose, with only three code blocks and no worked solutions, so plan to read `src/lib/ledger-storage.ts` and `ledger-schema.ts` alongside them.
