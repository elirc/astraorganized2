## What Astra did well
- It found and fixed a real, exploitable defect rather than a stylistic one. The backup's `backend/src/modules/auth/auth.schemas.ts:8-16` accepted `role: z.enum(["SYSTEM_ADMIN", ...])` on the **public** registration route, and `auth.service.ts` wrote `role: input.role` straight into `prisma.user.create`. Anyone could `POST /api/auth/register` with `role: "SYSTEM_ADMIN"`.
- The fix is applied at two layers and tested at both. The schema rejects the field, and the service ignores it — and there is a test that calls `authService.register(... role: "SYSTEM_ADMIN" ... as unknown as ...)` directly, bypassing the route, and asserts `prisma.user.create` was still called with `role: "READ_ONLY"`. That is exactly the right way to prove "defence in depth" rather than assert it.
- It caught a bug most reviewers miss: `app.use((error, _req, res) => ...)` is **not** error middleware in Express 4 — with three parameters it is ordinary middleware and never runs on a thrown error. `02-CONCEPTS.md:9` states the rule plainly — "Express 4 does not infer that a three-argument function is error middleware. The formal `(error, req, res, next)` shape is required even if the request argument is unused."
- The JWT hardening is textbook: `algorithms: ["HS256"]` on verify (closing algorithm-confusion), plus explicit claim parsing that rejects a refresh token presented as an access token, a non-`Role` `role` claim (`"ROOT"`), and missing/blank `sub`/`email`. All five of those cases are asserted in one test.
- Exercises and solutions are properly separated and both are runnable. `05-PRACTICE.md` gives nine tasks each with a named assertion target ("Assert 400 and assert `prismaMock.user.create` was not called"); `06-SOLUTIONS-AND-REVIEW.md` opens with "The following solutions are runnable inside `backend/src/app.test.ts` because they use the real imports and hoisted fixture already present there. They are complete assertion blocks rather than pseudocode" — and delivers exactly that.
- The reproduce block in `VERIFICATION.md` is the most careful in the batch: it saves and restores `$env:DATABASE_URL` in a `try/finally`, uses a synthetic URL that "neither operation opens a database or applies a migration", and throws on every non-zero exit code.
- Limits are stated without hedging: "A passing mock cannot prove PostgreSQL constraints, durability or multi-process races", "Refresh rotation and access-token revocation are not implemented", and "the schema's future CRM entities do not imply implemented CRUD routes".

## Problems found (evidence required)
- **[D4]** This project has **no CRUD entity routes at all** — only auth. `astraupskill/README.md` admits it ("The Prisma schema contains many future CRM models, but this project currently exposes the auth router and a small frontend login flow"). A learner finishes with excellent authentication/authorization and error-transport practice but writes no create/read/update/delete handler, no pagination, no ownership check on a resource, and never touches a live Postgres.
- **[D2]** `role: z.never().optional()` is functionally right but produces an opaque client error. Zod's message for a `never` field is not "role may not be set by the caller"; combined with `.strict()`, a caller sending `role` gets a generic 400 with no actionable explanation. A `.refine`/custom error message would teach better API hygiene and is what the course's own §"safe errors" chapter argues for elsewhere.
- **[D2]** There is now no code path anywhere that can create a privileged user. Registration hardcodes `READ_ONLY` and no admin-provisioning route or seed exists in the diff. `README.md` lists "provisioning of administrators" among things a passing build does not prove, but the course never says "you now need an out-of-band way to create the first admin" — which is a real operational consequence of the fix.
- **[D2, unchanged]** `authService.register` still does `findUnique` then `create` (read-then-write TOCTOU). The `P2002` catch makes the outcome correct, but the course presents the pattern without noting that the lookup is now purely for the friendly message and the unique index is the actual guard. Exercise 7 gets close ("a race must not bypass the fixed policy") without stating it.
- **[D7]** The test harness assumes comfort with `vi.hoisted` + `vi.mock("./db/prisma.js")` module mocking, Supertest, and TypeScript casts through `unknown`. `04-TESTING-AND-DEBUGGING.md` (374 words) explains the fixture but is the shortest chapter in the course and carries the heaviest machinery.
- **[D7]** No glossary. "Trust boundary", "output allowlist", "claim", "algorithm confusion", "TOCTOU"/"unique race", "hoisted mock" appear without definitions; `02-CONCEPTS.md` explains the concepts but never names them for lookup.
- **[D3, minor]** Only `03`, `04`, `06` and `07` contain code (`grep -c '```'` is 0 for README, 01, 02, 05). Chapter 02, which carries the conceptual load (trust boundaries, Zod, roles, JWTs, error mapping), shows no code at all.

## One-paragraph summary for the index
The most valuable *bug* in the batch and one of the two best courses. Public registration on this CRM backend accepted a caller-supplied `role`, so anyone could sign themselves up as `SYSTEM_ADMIN`; Astra closed it at both the Zod boundary and inside the service, then proved the second layer by calling the service directly with a cast. Along the way it found that the Express error handler had three parameters and therefore never ran, pinned JWT verification to HS256 with real claim validation (a refresh token presented as an access token, or a `role: "ROOT"` claim, are now rejected), bound refresh records to their token subject, scoped logout by user, and turned the register read-then-write race into a single 409 via Prisma's `P2002`. Nine Supertest tests against the real Express app with a hoisted Prisma mock back all of it, the logs are shipped, and the practice chapter's nine exercises each have a runnable solution in the next chapter. The one thing to know going in: this repository has no CRUD entity routes at all — you will learn authentication, authorization and error transport extremely well, and write no create/read/update/delete handler.
