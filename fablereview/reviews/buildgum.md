## What Astra did well
- The money and idempotency content is the best in the batch and the numbers in the course are literally the numbers in the code. 03-WORKED-CHANGE.md works `subtotalCents = 3900 * 2 = 7800`, `discount = floor((7800 * 20 + 50) / 100) = 1560`, `total = 6240`; `src/initial.ts:14` sets the Automation Field Manual at `priceCents: 3900`, `:83-84` defines `BUILD20` at `percent: 20`, and `src/model.ts:374-376` computes `Math.floor((subtotalCents * (discount?.percent ?? 0) + 50) / 100)`. The half-up-in-cents rounding is not hand-waved.
- Replay/idempotency is implemented where it belongs — inside the storage lock, before baseline comparison. `src/repository.ts:30` `if (replay(current.state, command)) return current;` and `src/model.ts:387-393` matches on `requestKey` **and** re-derives `fingerprint(command.buyer, command.quote)` before accepting the replay. The course draws the correct conclusion: "This can succeed even when the caller's baseline is old: the operation identifies an already accepted receipt rather than applying another change."
- Cart integrity is enforced by the domain, not the form: `src/model.ts:340-361` bounds the cart at 50 lines, validates each quantity `integer(item.quantity, 1, 99)`, requires `p?.active`, and **sorts lines by product id** so that equivalent cart orderings produce the same fingerprint — a detail the course calls out and that most tutorials would never notice.
- Astra removed claims the app did not implement rather than leaving them in place: "Checkout displayed a fixed order number and payment, tax, and delivery claims without performing those operations. This implementation replaces those claims with explicit local simulation" (`astraupskill/README.md`), and VERIFICATION.md is blunt: "Do not promote a local simulation into a production claim merely because the interface looks complete."
- Setup is the most reproducible in the batch: `package.json` pins **exact** versions (`typescript: "6.0.3"`, `vite: "8.0.14"`, `react: "19.2.6"` — no carets), `dev` uses `--host 127.0.0.1 --port 5180 --strictPort`, and the README explains *why* the origin matters ("Opening another port or using `localhost` instead of `127.0.0.1` creates a different storage location. Seeing a fresh catalog there does not prove your earlier records were deleted").
- Verification counts reconcile exactly (37 + 7 loop-generated = 44), and the six claimed screenshots all exist at `astraupskill/images/{storefront,editor}-{1440,800,390}.png`.

## Problems found (evidence required)
- **[D4]** Browser-only. VERIFICATION.md states the gap honestly — "There is no authenticated actor, authorization boundary, server database, payment acceptance, tax calculation, recurring billing, stock reservation… Orders are explicitly simulated receipts" — but it means the learner practises idempotency, versioning and validation with `localStorage` and `navigator.locks` standing in for a database and a transaction. Everything must be re-learned against real persistence, and no chapter says what the server-side equivalent of `replay()` or the raw-baseline check would be.
- **[D8]** Template smell across the batch. `astraupskill/README.md` says "Budget several focused sessions"; `e15/astraupskill/README.md` says "Allow several focused sessions"; `JSProjectLearn/astraupskill/README.md` says "Allow several focused sessions." All three then follow with a "a useful session/milestone produces a small diff + a reproducible check + an explanation of one tradeoff" paragraph. The technical chapters here are strongly project-specific; the framing prose is interchangeable.
- **[D7]** The chapter that teaches the hardest material — receipts, fingerprints, frozen attempts, lost acknowledgements — is 542 words. Step 2 introduces "It places this command in `attempt` before awaiting persistence" and Step 4 "An exception after the actual write represents a lost acknowledgement" with no diagram or timeline; for a junior, the distinction between "write failed" and "write succeeded, response lost" is exactly the thing that needs a picture. No time budget or prerequisites are given.
- **[D5, minor]** The browser suite is a Python script in a Node project: `astraupskill/04-TESTING-AND-DEBUGGING.md:25-27` requires `python -m pip install playwright==1.59.0` and `python -m playwright install chromium`. That is documented and workable, but it is an extra toolchain a JS-track junior will not otherwise need, and it is not mentioned in the course README's setup block.
- **[D2, minor]** `test/model.cjs` imports the compiled output (`require("../.verification/model.js")`), produced by `scripts/test.mjs` running `tsc -p tsconfig.test.json`. It works and is self-contained, but it means the test file cannot be run directly with `node --test test/model.cjs` on a clean checkout; the course never warns about this, and `.verification/` is absent from the delivered tree.

## One-paragraph summary for the index
Buildgum is the best money-and-idempotency lesson in the batch. Astra deleted a checkout that flipped a boolean and printed a fixed order number, and replaced it with integer-cent arithmetic you can check by hand (the course's `floor((7800 * 20 + 50) / 100) = 1560` is the literal expression in `src/model.ts`), receipts that snapshot the product title and price accepted at checkout so a later catalog edit cannot rewrite history, cart lines sorted by id so an equivalent cart yields the same fingerprint, and a request-key replay path inside the storage lock that makes a retried checkout after a lost acknowledgement return the existing receipt instead of creating a second one. 44 unit tests and 15 Chromium scenarios exist exactly as claimed, and setup is the most reproducible here — exact pinned versions, a fixed `127.0.0.1:5180` origin, and an explanation of why the origin matters for browser storage. The limitation is the same as JSProjectLearn's: no server, no database, no authorization, so idempotency and versioning are practised against `localStorage` and Web Locks. Take it as a focused elective on money, snapshots and retry semantics, then immediately redo the same ideas against Postgres in the grokbuild projects.
