# buildjira (BuildJira issue tracker) — Fable review

- **Path:** `_Organized Desktop/02 Build Projects/buildjira`  ·  **Wave:** 2  ·  **Stack:** ASP.NET Core (net8) singleton store + JSON file / static browser JS (an old TypeScript/Node/Prisma/React tree is archived in place) / bespoke .NET console regression harness  ·  **Batch:** B09
- **Astra's change (one line):** Fixes a genuine data-corruption bug in `BuildJiraStore.UpdateIssue` — `ApplyPatch` assigned fields to the **live singleton `Issue`** as it walked the JSON body, so `{"title":"Rejected replacement","storyPoints":101}` returned a validation error *after* the title had already been written, and the next unrelated valid save serialized that leaked title to disk. The repair applies the patch to `Clone(issue)`, validates everything, and only then calls `CopyMutableIssueFields(candidate, issue)`; it also adds `JsonValueKind` guards before every `GetString()`/`TryGetInt32()` so malformed field types return the existing `VALIDATION_ERROR` envelope instead of throwing.
- **Course size:** 4,445 words across 9 files  ·  **Tests claimed:** 1 harness ("scenarioGroups: 6, malformedInputCases: 9")  ·  **Tests found on disk:** `tests/BuildJira.Api.Regression/Program.cs` (114 lines, ~30 `Assert(...)` calls across the 6 named scenario groups), exit-code driven. **Zero xUnit tests.**

## What Astra did well
- **The bug is real, correctly diagnosed, and the *second-order* consequence is what makes it a great lesson.** The immediate symptom (a rejected PATCH mutates in-memory state) is bad; the course's point is worse and better taught: because the store is a singleton persisted lazily, "a subsequent valid description update on **another issue** called `Save`, serializing the leaked title" (`03-WORKED-CHANGE.md`). A junior learns that rejected-request state leakage becomes *durable* via an unrelated code path — the reason validate-then-commit matters even without a database.
- **The `System.Text.Json` lesson is correct and is the one juniors actually need.** `title.GetString()` on a JSON number does not return null — it throws `InvalidOperationException`, which surfaces as a 500. Likewise `storyPoints.TryGetInt32(...)` throws when `ValueKind` is not `Number`, despite the `Try` prefix. The fix guards `ValueKind` before every accessor, and `02-CONCEPTS.md` states the rule: "otherwise malformed JSON kinds can throw instead of returning the established validation envelope."
- **`05-PRACTICE.md:22` is the best exercise in the batch**: *"For each body, predict whether `GetString` or `TryGetInt32` would throw in an unguarded implementation: `{ "title": 7 }`, `{ "rank": "10" }`, `{ "dueDate": true }`, `{ "storyPoints": [] }`. Add a `ValueKind` guard and return the matching validation message. The observable requirement is a normal validation envelope, never an exception."* Prediction, then code, then an observable criterion — and the answer is in a separate file.
- **The regression harness asserts the things that actually prove the fix.** `tests/BuildJira.Api.Regression/Program.cs` checks, after a rejected patch, that the file bytes are byte-identical (`File.ReadAllBytes(dataFile).SequenceEqual(initialBytes)`), that `Project.UpdatedAt` did not move, that the audit list length is unchanged — and then, critically, that after an *unrelated* valid save and a store reopen, `Issue(reopenedBoard, initialIssue.Id).Title == initialIssue.Title`. That last assertion is exactly the second-order bug, and it would have caught the original defect.
- **Evidence is reported at the right granularity.** `expectedTests: 1` with a separate `scenarioGroups: 6` / `malformedInputCases: 9` breakdown, rather than inflating ~30 assertions into "30 tests". `exitCode: 0` is meaningful because `Assert` throws `InvalidOperationException`. The README also discloses the archived TypeScript/Prisma tree ("intentionally left in place as commented archival reference material… The active application lives in `apps/dotnet/BuildJira.Api`").

## Problems found (evidence required)
- **[D2] `CopyMutableIssueFields` is a hand-maintained list with no compile-time link to `ApplyPatch`.** It copies exactly 8 properties (`Title`, `Description`, `Status`, `Priority`, `AssigneeId`, `StoryPoints`, `Rank`, `DueDate`) and `ApplyPatch` today handles exactly those 8, so there is no bug *now*. But `Issue` also has `Type` and `SprintId` (`apps/dotnet/BuildJira.Api/Models/Domain.cs:90,94`), and the day someone adds `type` to `ApplyPatch` and forgets this method, valid patches will be **silently discarded with a 200 response** — the worst possible failure mode. The course calls the helper "safer to review than replacing the whole object" (`03-WORKED-CHANGE.md:26`) without mentioning this coupling risk at all.
- **[D2] Redundant duplicated branches were introduced.** In the `dueDate` handling of `ApplyPatch`, the new `else if (dueDate.ValueKind != JsonValueKind.String) { error = Validation("Due date must be an ISO-8601 date-time string or null."); return false; }` is followed by an `else { …identical body… }`. Two branches with the same message and the same `return false`; one `else` would do.
- **[D2][D7] No xUnit.** The regression is a top-level-statements console app with a private `static void Assert(bool, string) { if (!condition) throw new InvalidOperationException(message); }` — fail-fast, so the first failure hides the other ~29 assertions, with no test names, no TRX, and no `dotnet test`. `04-TESTING-AND-DEBUGGING.md` teaches this harness as the testing approach for the project.
- **[D2] `Clone<T>` is a full JSON serialize/deserialize round-trip on every PATCH** (`BuildJiraStore.cs:647` `JsonSerializer.Deserialize<T>(JsonSerializer.Serialize(value, JsonOptions), JsonOptions)!`). Fine for a teaching app, but the course presents cloning as free and never mentions the cost or the alternatives (a `record` with `with`, a hand-written copy constructor, or validating into a DTO before assignment).
- **[D5] The verification command requires a prior Release build and a roll-forward override.** `dotnet run --project tests/BuildJira.Api.Regression/BuildJira.Api.Regression.csproj -c Release --no-build` with `DOTNET_ROLL_FORWARD=Major` against an installed .NET 10 runtime for a net8 target. Disclosed in the environment note, but `--no-build` will fail confusingly for a learner who has not built first, and the course does not put the build step immediately above it.

## Improvements needed (ordered, concrete, actionable)
1. **Remove the `ApplyPatch` ↔ `CopyMutableIssueFields` coupling.** Safest minimal change: instead of copying fields back, replace the object in the collection (`state.Issues[state.Issues.FindIndex(i => i.Id == issueId)] = candidate;` after restoring identity fields `Id`/`Key`/`ProjectId`/`ReporterId`/`CreatedAt` onto the candidate). Then add a paragraph to `03-WORKED-CHANGE.md` on why "copy the named fields back" is the fragile option and what a `record` + `with` would give you. Add a regression assertion that every `ApplyPatch`-settable field survives a valid patch. (effort: M)
2. **Port the harness to xUnit** (`tests/BuildJira.Api.Tests/`): one `[Fact]` per scenario group, and a `[Theory]` with the nine malformed bodies as `[InlineData]` — that loop is already parameterised in `Program.cs` and converts almost mechanically. This ends the fail-fast masking and gives the delivery a real test count instead of `expectedTests: 1`. (effort: M)
3. **Collapse the duplicated `dueDate` branches** in `ApplyPatch` into a single `else { error = Validation("Due date must be an ISO-8601 date-time string or null."); return false; }`, and re-check the quoted solution in `06-SOLUTIONS-AND-REVIEW.md:33` still matches. (effort: S)
4. **Put the build step next to the run step** in `VERIFICATION.md` (`dotnet build tests/BuildJira.Api.Regression/BuildJira.Api.Regression.csproj -c Release` immediately before the `--no-build` run), and state up front that `DOTNET_ROLL_FORWARD=Major` is only needed when no .NET 8 runtime is installed. (effort: S)
5. **Add a short `02-CONCEPTS.md` note on the cost of `Clone<T>`** (JSON round-trip per request) and contrast it with a copy constructor and with validating into a DTO before touching the entity — the third option is what an EF Core codebase would actually do, and naming it gives the lesson somewhere to go. (effort: S)

## One-paragraph summary for the index
The sharpest bug story in the batch. BuildJira's `UpdateIssue` handed the **live** singleton `Issue` to its patch walker, so a request that set a valid title and then failed on `storyPoints: 101` returned a validation error with the title already changed in memory — and the next unrelated valid save wrote that leaked title to disk. Astra fixes it with clone → validate → copy-back, and pairs it with the `System.Text.Json` trap every junior hits: `GetString()` on a number and `TryGetInt32()` on a non-number both *throw* (a 500), so you must check `ValueKind` before the accessor if you want a 400. The regression harness asserts the right things — unchanged file bytes, unchanged project timestamp, unchanged audit count, and that an unrelated later save does not make the rejected title durable — and the evidence is reported at honest granularity (one harness, six scenario groups, nine malformed cases) rather than inflated. Weaknesses: there is no xUnit anywhere, the copy-back helper hand-lists eight fields with no compile-time tie to the patch walker (a future ninth field would be silently dropped on a 200), and the store is a JSON file, so nothing here teaches EF Core. Read it early; budget 3-5 hours.
