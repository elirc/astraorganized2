## Does this transfer to the CRUD-web goal? (off-target-stack note)

**Yes, more than any other mobile project would.** The platform is React Native, but nothing in the *lesson* is React Native. What is actually taught is: a repository layer that owns SQL and returns domain records; parameterised binding vs. concatenation; `changes`/affected-row counts as the signal that distinguishes "updated" from "id not found"; `undefined` vs `null` PATCH semantics; where validation belongs (repository, not screen); cache/notification invalidation only after a successful write; and a service that must not run domain side effects when its persistence call reports failure. Rename `updateSet` to `PATCH /sets/:id` and every sentence still holds — 06-SOLUTIONS even writes the 409-shaped reasoning explicitly. What it does **not** teach: HTTP status codes, ownership/authz, pagination, or anything server-side; there is no user, no request, no session. Take it as the "repository and service boundary" chapter of a web curriculum, not as a substitute for building an Express/Next route.

## What Astra did well
- The change fixes four genuine defects, not cosmetics. Diffing `backups/676bcb38df2b/src/db/repos.ts` against the live file shows the old `updateSet` pushed `${col} = ?` for a key that was present-but-`undefined` (`cols.push` ran before any undefined check), bound `undefined` into the parameter array, and called `bump()` unconditionally even when zero rows changed. `startRun` also called `Date.now()` twice — once for the INSERT at line 196 and once for the returned `startedAt` at line 204 — so the persisted row and the record handed to the caller could disagree. All four are fixed.
- The service guard is the most valuable bit and is properly tested. `workoutFlow.ts:90-92` is now `if (!finishWorkout(workout.id, note)) { return { progressionEvents: [], milestones: [] }; }`, and `src/services/__tests__/workoutFlow.test.ts` proves the consequence with `finishWorkout.mockReturnValueOnce(true).mockReturnValueOnce(false)` then asserting `countCompletedWorkouts` was called exactly once across two `completeWorkout` calls. That is a behavioral assertion, not a "the call happened" assertion.
- Tests are negative-space tests, which is rare. `repos-mutations.test.ts` asserts `expect(runSync).not.toHaveBeenCalled()` and `expect(listener).not.toHaveBeenCalled()` for invalid input, and asserts the exact bound parameter array (`expect(runSync.mock.calls[0][1]).toEqual([8, 's1'])`) to prove the `undefined` key was skipped rather than bound as null.
- VERIFICATION.md is unusually candid about what a mock cannot prove: "A mocked `runSync` response establishes the JavaScript contract; it cannot prove SQLite foreign-key cascades, filesystem durability or native module behavior. No Android/iOS release build, emulator run, UI interaction or browser run is claimed." It also explains *why* the run used `--maxWorkers=1 --testTimeout=30000` (the pre-existing plate-math property test takes 6.66s) and states that no assertions were skipped.
- Original sources are preserved as `astraupskill/snapshots/repos-before.ts.txt` and `workoutFlow-before.ts.txt`, and the course repeatedly tells the learner to diff them — the before/after is available to the learner without a git checkout.

## Problems found (evidence required)
- **[D2]** The new boolean return values are ignored by every UI caller. `src/screens/ActiveWorkoutScreen.tsx:383` is `deleteSet(set.id); onClose();` — a stale delete now returns `false` and the screen still closes as if it succeeded; likewise `:102`/`:260` `deleteWorkout(workout.id);` and `WorkoutDetailScreen.tsx:90`. Only `workoutFlow.ts` consumes a result. The course names this ("a production product would still need visible error handling") but the shipped code leaves the improvement half-wired, and no exercise requires the learner to wire it.
- **[D2]** The validation pass in `updateSet` (`src/db/repos.ts:456-462`) is a second loop over `Object.entries(fields)` with a hardcoded allow-list of non-numeric keys: `if (value === null || key === 'note' || key === 'kind' || key === 'isFailure' || key === 'completedAt') continue; if (typeof value !== 'number') throw new Error(...)`. Any future non-numeric column added to `mapping` (say `tag`) will make `updateSet` throw `"tag must be a number"` at runtime, because the skip list and the mapping are maintained separately. Folding validation into the single existing `for (const [k, col] of Object.entries(mapping))` loop would remove the trap. Exercise 1 in 05-PRACTICE even asks the learner to add a hypothetical `durationSeconds` field and "state where its validation belongs" — walking them straight into the seam Astra left open, without warning.
- **[D2]** `updateSet` now *throws* on invalid input, and it is called directly from render-path handlers with no try/catch: `ActiveWorkoutScreen.tsx:341,347,352,361,368,377`. A thrown error from `onChange` in React Native surfaces as a redbox/crash, not a message. The change swapped silent corruption for an unhandled exception; the course discusses the tradeoff in 07-TRACE-LAB ("A screen-level error boundary or handler would need to present recovery") but no boundary was added.
- **[D7]** Paragraph order is scrambled in at least four files — each one opens with a summary/drill paragraph that only makes sense *after* the introduction. README.md opens with "Use a notebook with five columns: user action, domain object, persistence call..." before it has said what Small Plates is; the "Small Plates is an Expo SDK 57 React Native app" sentence is the *second* paragraph. `01-CODEBASE-MAP.md` opens with "The read path matters as much as the write path" and only reaches "The application starts in `App.tsx`" three paragraphs later. `07-TRACE-LAB.md` opens with "Repeat the trace for program completion" before the trace it is repeating. A junior reading top-to-bottom will be lost for the first screen of every file.
- **[D7/D8]** The course leaks its own build machinery at the learner. 04-TESTING-AND-DEBUGGING: "Root observed the complete 92-test suite passing after the locked 544-package install" and "Root's successful locked install is the prerequisite for authoritative results." "Root" is an Astra orchestration role, meaningless to the reader.
- **[D5]** VERIFICATION.md's reproduce block gives `npm test -- --maxWorkers=1 --testTimeout=30000` but `package.json` defines `"test": "vitest run"` — the flags reach Vitest, not Jest, and the surrounding prose still uses Jest-flavoured wording. It also correctly discloses that the recorded run invoked `node node_modules/vitest/vitest.mjs` directly, so the documented command is not literally the verified one.

## One-paragraph summary for the index
Small Plates is an Expo/React Native lifting log, but the course is really about the repository and service boundary, and that part transfers cleanly to Node+SQL CRUD web work. Astra fixed four real defects — `undefined` patch keys being bound into SQL, unconditional cache invalidation on zero-row updates, two different `Date.now()` values between the inserted row and the returned record, and a service that replayed program progression when a workout was finished twice — and backed each with a negative-space test that asserts what did *not* happen (no SQL call, no listener notification, one progression save across two completions). The 92 claimed tests are all on disk and the evidence JSON records a clean `exitCode: 0`, with VERIFICATION.md openly admitting the database is mocked and no device or emulator was ever run. Two things to know before starting: the new boolean return values are still ignored by every screen (the improvement stops at the repository), and every file's first paragraph is out of order, so start at paragraph two. Do this one if you want to understand affected-row counts, `undefined`-vs-`null` patch semantics and idempotent completion; skip it if you need HTTP, auth or pagination, because there is no server here at all.
