## Is this really a "SQL course"? (off-target-stack note)

**No — and that is good news.** Despite the folder name, `buildsql` today is not a SQL curriculum. It is a React 19 + TypeScript single-page app ("IPSKILL") that *presents* a preserved archive of 310 lessons and 2,155 missions across six tracks (SQL, TypeScript, Node, React, C#, .NET) and tracks the learner's own applied CRUD projects. Astra's change and the entire `astraupskill/` course are about the **app**, not the archive. So what a junior actually practises here is React controlled forms, runtime validation at a shared contract layer, optimistic concurrency, search + status filter + pagination, draft-versus-accepted state, and transactional persistence — squarely on the CRUD-web target. The SQL/backend content is deliberately deferred to Practice tickets 3 and 4 (a Node or .NET contact API with paginated routes, expected versions, then authenticated ownership), which are honestly labelled as exercises, not delivered features. What is missing from the delivered code: there is no server, no HTTP layer, no SQL and no auth anywhere. The archive's SQL lessons are *reference material this app displays*, and VERIFICATION says so plainly: "Structural validation can check identities, counts, fields and reward consistency. It does not establish that every historical explanation or reference solution is correct."

**Verdict:** KEEP    **Path role:** core

## What Astra did well
- The central change is a textbook compare-and-swap and it is implemented correctly. `src/storage.ts` `commit()` opens one `readwrite` transaction, `get("current")` first, then `if (expected ? !current || current.id !== expected.id || current.revision !== expected.revision : current !== null) throw new ConflictError()` — identity **and** revision, inside the same transaction as the `put`. The course explains exactly why the identity is needed on top of the number (02-CONCEPTS: "an older tab could coincidentally hold a matching numeric revision from an unrelated imported document"). That reasoning is the difference between someone who has read about optimistic locking and someone who has shipped it.
- Validation is placed at the boundary both the UI and import must pass. 03-WORKED-CHANGE argues "A check located only in a React button handler would let import bypass the rule" and points at `validateProject` in `contracts.ts` — and the code agrees: `contracts.ts:204` `if (p.status === "review") text(p.evidence, "Review evidence", 10000, 40);` is reached by both `putProject` and `importWorkspace` via `validateWorkspace`.
- Domain functions are pure and clock-injectable. `progression.ts:157-185` `putProject(workspace, input, expectedVersion?, now = new Date())` builds a new array and returns `validateWorkspace({...current, projects})` without mutating the caller's object — which is what makes the "assert the input snapshot is unchanged" advice in 04-TESTING actually possible.
- Verification is the most thoroughly evidenced in this batch, and the counts are honest to the scenario. `checks/buildsql/browser-01/results.json` lists 19 named scenarios with per-scenario timings and `"passed": true`; `authoring-01/results.json` lists 7. VERIFICATION explicitly declines to double-count reruns: "Repeating a suite after a fix is necessary evidence but does not create additional unique scenarios", and discloses the two failures found during verification (a `window`-assuming test setup, and a 5-second timeout raised to 30s for the full SQL pack parse) with the reason, rather than hiding them.
- Practice tickets escalate properly and refuse to overclaim. Ticket 4: "Derive identity from the server's authenticated context rather than accepting an arbitrary owner ID from a form... The interface hiding a button is helpful presentation; server-side authorization is the control that protects the operation." Ticket 3 adds "The current IPSKILL application has no account system, so this exercise must not silently invent an authorization model."

## Problems found (evidence required)
- **[D2]** The scope is a rewrite presented as a change. The backup holds 18 files; the delivery touched 55. `src/App.tsx` grew from 308 to 1,098 lines and seven source modules (`storage.ts`, `contracts.ts`, `progression.ts`, `useWorkspace.ts`, `content-loader.ts`, `PracticeView.tsx`, `LibraryView.tsx`, `WorkspaceSettings.tsx`) did not exist before. A junior cannot meaningfully diff `docs/original/src__App.tsx.txt` against 1,098 lines and learn a change; the before/after framing the course leans on ("Compare it with the current implementation to see concrete changes") works for the three named behaviors and not for the rest.
- **[D2/D7]** `src/App.tsx` is still a 1,098-line file whose `App()` component alone spans lines 92-474 and owns the loading, view-routing and curriculum state. The course opens 01-CODEBASE-MAP with coping advice for exactly this ("When reading a large component, identify the functions it delegates to before attempting to memorize its markup") rather than fixing it. A course about clean boundaries should not ship its largest file as the counterexample.
- **[D7]** The code style is compressed in a way that will slow a junior down: multi-declarator commas throughout, e.g. `storage.ts` `const tx = db.transaction("workspace","readonly"), request = tx.objectStore("workspace").get("current"); let result: Workspace | null = null, error: unknown;` and `progression.ts:163` `const current = validateWorkspace(workspace), existing = current.projects.find(...)`. The course never mentions the convention.
- **[D7]** 6,392 words is thin relative to a ~3,400-line TypeScript app with IndexedDB, CRDT-free concurrency, a 2,155-mission content pipeline and an authoring CLI. `02-CONCEPTS.md` has to establish draft/accepted, identity/revision and whole-document vs row-level concurrency in three paragraphs, with no diagram of the two draft layers (form draft → workspace draft → accepted) that the whole course depends on.
- **[D4]** Nothing in the delivered code touches SQL, HTTP or authorization, despite the project name and the six-track archive. A learner who picks this expecting SQL practice gets a React app; the SQL work is only in Practice ticket 3, unscaffolded. The README does say so, but not until the last paragraph of a nine-paragraph page.

## One-paragraph summary for the index
Ignore the folder name: `buildsql` is a React 19 + TypeScript app, and this is one of the strongest CRUD courses in the set. Astra replaced an unacknowledged `localStorage` autosave with a real IndexedDB commit that does a read-compare-write inside a single transaction, rejecting a save whose expected `{id, revision}` no longer matches — and then built the lesson around the two things juniors get wrong about that: why a rejected write must retain the user's typed draft, and why matching the revision number alone is not enough once an import can replace the whole document with a new identity. Validation lives in a shared `contracts.ts` so the import path cannot bypass what the form enforces, the domain functions are pure with an injectable clock, and the practice list has genuine search, status filter and pagination to study. Verification is the best-evidenced in the batch: 69 checks, every sub-count reconcilable against files on disk, with the two mid-verification failures disclosed rather than buried. The costs: the "change" is really a rewrite (`App.tsx` 308 → 1,098 lines, seven new modules), there is no server, SQL or auth in the delivered code, and the backend/ownership work you actually need is Practice tickets 3 and 4 — good tickets, but prose with no scaffolding.
