## What Astra did well
- Every one of the four fixes is a defect a junior will meet in real work, and each is a *different* category: ordering/authz, input validation, partial-update semantics, and concurrency. Backup `src/lib/socket/actions.ts` joined the room and wrote presence before `loadBoardSnapshot`; the current file loads first with the comment "an unauthorized join must not subscribe the socket or create presence" (`src/lib/socket/actions.ts:88`).
- The `?? undefined` lesson is genuinely valuable and correctly diagnosed. Backup `board-service.ts:473-480` had `description: params.patch.description ?? undefined`, which silently turns an explicit `null` clear into "leave the column alone". The replacement `src/lib/services/card-update-set.ts` uses `Object.prototype.hasOwnProperty.call(patch, ...)` and is unit-tested at the exact `.set` argument level (`tests/socket-actions.test.ts:125-132`).
- The concurrency fix is real, not cosmetic: backup read `db.select({version}) ... nextVersion = board.version + 1` *outside* the transaction and then updated; the current code does one atomic `tx.update(...).set({version: sql\`${boards.version} + 1\`}).returning(...)`. The course explains why ("so two transactions do not both select the same old board version", `02-CONCEPTS.md`).
- `registerBoardSocket(socket, dependencies)` is a clean testing seam and the test drives the *real* registration function, not a copy — the course says so explicitly and the test file confirms it (dynamic import after setting a dummy `DATABASE_URL`).
- VERIFICATION.md is the most honest in the batch. It states which paths are *not* atomic ("archive, restore, template and role paths still call it outside an enclosing transaction. They are not claimed to have full transactional atomicity"), that lint exit-0 can still hide warnings, and that the keyboard fix in `Card.tsx` was "source-reviewed and compiled, not browser-tested".

The course never says "delete or ignore `next.config.ts`".
- **[D2, minor]** `src/lib/services/board-service.ts:487` now throws `new DomainConflictError(..., params.expectedVersion!)` — a non-null assertion added to silence the compiler rather than narrowing the type. Small, but it is exactly the habit the course elsewhere warns against.
- **[D2, minor]** Inconsistent presence checks in the same handler: `card:update` uses `rawPatch.description !== undefined` for description but `hasOwnProperty` for `dueAt` (`src/lib/socket/actions.ts:258-259`). Equivalent over JSON transport, but it undercuts the chapter's own "omitted vs null" thesis.
- **[D3]** Four of the nine practice exercises (4 service half, 7, 8, 9) are reasoning or "proposed" work with no runnable harness, so the predict→run→verify loop breaks for nearly half the practice set. There is also no failure lab: the course never asks the learner to revert one guard and watch a named assertion fail.
- **[D5, minor]** The change bumped `drizzle-orm` from `^0.40.2` to `^0.45.2` and added `package-lock.json`; VERIFICATION says `npm ci` but never flags that the ORM minor bump is part of the delivery, so a learner diffing against an older clone will be surprised.

## One-paragraph summary for the index
The strongest course in this batch and the best CRUD content: four genuinely different production bugs in one realtime Kanban app — authorize-before-join, strict payload validation, omitted-vs-null patch semantics, and non-atomic version allocation — each fixed in the real code and each pinned by a passing Node test that drives the actual socket registration function. The lessons on `?? undefined` swallowing an explicit `null` and on moving a version read inside the transaction are worth the whole course on their own. It is also the hardest: Socket.IO, Drizzle, dependency injection and LexoRank arrive with little scaffolding, and about half the practice exercises are reasoning-only because there is no database harness. Do it after an easier authz course, budget a full day, and expect to look things up.
