## What Astra did well
- The refund fix is a genuinely subtle, correctly diagnosed bug. The original (`backups/7f871ce5e237/src/lib/commerce/orders.ts:531`) compared `refundedAmount + amount > payment.amountCaptured` **while also** decrementing `amountCaptured` on every refund (line 567) — double counting, so a legitimate second partial refund was rejected. The new code compares `amount > payment.amountCaptured` once, and the test `"uses the remaining captured balance for sequential refunds"` pins 100 → 60 → 0.
- Idempotency-key binding is a real correctness upgrade in both files: `src/lib/commerce/webhooks.ts:75` and `orders.ts:556` now reject a key reused with a different payment, kind or amount (`IDEMPOTENCY_CONFLICT`, 409) instead of silently returning someone else's receipt.
- The duplicate-fulfillment-line fix prevents actual double stock consumption: the pre-existing loop recomputed `remaining` from `orderLine.quantityFulfilled` (not yet updated in the loop) and the consumption pass re-filtered the same reservations, so `[{line-1,1},{line-1,1}]` could consume the same reservation twice.
- Test count grew 6 → 11 and the new tests assert *state*, not calls: the duplicate test serializes the whole order + reservations + fulfillments before and after and asserts `expect(after).toEqual(before)`.
- `04-TESTING-AND-DEBUGGING.md` records the actual failure history honestly ("Earlier attempts failed with import-order, missing-schema, hook-timeout, and worker-timeout errors; those records are historical diagnostics"), and `checks/7f871ce5e237/` really does contain those failed records.

## Problems found (evidence required)
- **[D2, D5]** The delivery ships `astraupskill/original/src/lib/commerce/commerce.test.ts`, a byte-identical copy of the **pre-change** test file, inside the project tree. Vitest's default `include` collects it, and that copy still calls `execSync("npm run db:push")` / `db:seed` with the project's `DATABASE_URL` (`.env`: `file:./dev.db`). So plain `npm test` (`"test": "vitest run"`, `package.json:13`) pushes schema and reseeds the developer's canonical `dev.db` — the exact hazard `05-PRACTICE.md` warns against ("never point `DATABASE_URL` at canonical `dev.db`"). The snapshot belongs outside the Vitest include, or renamed away from `*.test.ts`.

## One-paragraph summary for the index
The *subject matter* here is the best CRUD material in the batch — refund ledgers in minor-unit integers, idempotency keys bound to request identity, validate-before-you-open-a-transaction, and a fixture that owns its own SQLite file — and the underlying bug fixes are real and correctly diagnosed (the original refund guard double-counted historical refunds against an already-decremented balance). The *teaching* is the weak part: nine files of unbroken prose with not a single code block, exercises that describe assertions instead of showing them, a README that repeats its navigation paragraph three times, and one claim that puts the order/warehouse checks outside the Prisma transaction when the code has them inside. It also ships a copy of the old test file where Vitest will run it, so a plain `npm test` reseeds your `dev.db`. Read it for the refund and idempotency concepts, but read the code alongside it and fix the vitest exclude before running anything.
