## Does it transfer? (D4, stated plainly)
**The ideas transfer; the stack does not, and the course does nothing to bridge the gap.** Every concept it teaches has a direct counterpart on the target stacks — `scoped_record()` is the same move as scoping an EF Core query by `TenantId` or a Prisma `where: { id, organizationId }`; Pydantic `model_config = {"extra": "forbid"}` is Zod `.strict()` or `[ApiController]` model binding with `MissingMemberHandling.Error`; SQLAlchemy's `__mapper_args__ = {"version_id_col": version}` is EF Core's `[Timestamp] rowversion` or a Prisma `version` column with a conditional `updateMany`; the ETag/`If-Match` handshake in `app/crud.py:100-110` is framework-independent HTTP and is arguably taught better here than in any of the Node projects in this batch. But a junior working toward JS/TS/C#/.NET will spend real hours on `venv`, editable installs, pytest fixtures, `Depends()` and SQLAlchemy session semantics that buy them nothing, and there is **not one mention of TypeScript, Node, Express, C#, .NET, EF Core or Zod anywhere in the nine files** (`grep -in "typescript|express|\.net|EF Core|C#|zod"` over `astraupskill/*.md` returns nothing). Read 02-CONCEPTS.md and 03-WORKED-CHANGE.md for the ideas; do not spend an evening running the Python.

## What Astra did well
- Authorization is taught as three separate checks and the code matches. 02-CONCEPTS.md: "A request to `/api/v1/dashboards/19` does not become authorized because the caller knows the ID… A cross-organization lookup returns 404, avoiding confirmation that the other organization's record exists." `app/crud.py:88-96` implements exactly that: `select(resource.model).where(model.id == record_id, model.organization_id == principal.organization_id)` then `404 Record not found`.
- Privilege escalation is treated as a first-class invariant, not an afterthought: "An `iam:write` scope is not permission to grant arbitrary privileges. The token and user creation services require the granted permissions to be a subset of the caller's own permissions" (02-CONCEPTS.md), with `tests/test_contracts_and_auth.py:112` parametrized over `["expired", "inactive", "demoted", "membership-removed"]` — the four ways a once-valid token should stop working.
- The verification record is the most self-critical in the batch. `astraupskill/evidence.json` separates `fullSuite: 105` from `focusedFinalRegressionRun: 18` and explains the arithmetic: "The focused run repeats 17 existing cases and adds one trace-alert stream regression." VERIFICATION.md states "No real webhook or Slack message was sent during verification. Outbox tests use fake senders and mocked DNS" and "A crashed claim can remain `sending`; an ambiguous request can remain `uncertain`. Neither is automatically replayed."
- It refuses to touch the user's data and says so repeatedly: "Existing user databases were not opened or migrated during this improvement. Migration behavior was verified against synthetic historical schemas", and the README tells the learner what to do instead ("do not replace or delete it to get past a startup error. Stop every process using it, make a private backup…").
- The original material is preserved rather than overwritten — `docs/original/` holds exact pre-change text including `docs/original/tests/test_mvp.py.txt`, so the one changed test expectation is inspectable.

## Problems found (evidence required)
- **[D4]** Off-stack for the stated goal. The project is FastAPI + SQLAlchemy + SQLite; the target learner wants React/Node/Next and ASP.NET/EF Core. No file in `astraupskill/` maps a single idea to those stacks (verified by grep, above), so the transfer the README promises — "the engineering skills transfer directly to inventory systems, support tools, internal dashboards" — is asserted, never demonstrated.
- **[D7]** 7,555 words over an application of ~2,400 lines in `app/` spanning five CRUD resources, ingestion, a trace graph, a bounded SQL executor, an alert engine and an outbox. 02-CONCEPTS.md alone is 1,096 words covering tenancy, permissions, four validation layers, transactions and concurrency. There is no reading-time estimate and no prerequisite list; a junior meeting `Depends()`, `version_id_col`, ETags and outbox semantics for the first time in one document will stall.
- **[D6, minor]** The claimed 106 Python cases cannot be confirmed read-only: only 62 `def test_` functions exist and the remainder comes from parametrization expansion, which requires collection to count. The claim is plausible and internally consistent (`evidence.json` shows `fullSuite: 105` plus one added regression), but VERIFICATION.md would be stronger if it stated "62 test functions expanding to 106 collected cases" rather than a bare 106.
- **[D3, minor]** The two "first session" experiments in `astraupskill/README.md` are excellent predict-then-run loops, but they are buried in the README; 05-PRACTICE.md exercise 1 ("Explain a saved query without changing code") is the only other place a prediction is explicitly demanded before an action.

## One-paragraph summary for the index
Technically the most thorough delivery in the batch and, judged purely as engineering, excellent: real multi-tenant scoping that returns 404 rather than 403 on a cross-organization ID, ETag/`If-Match` revisions backed by SQLAlchemy's version column, strict request contracts that reject unknown fields, deduplication placed *before* transformation inside the ingestion transaction, a bounded read-only SQL path, and a durable outbox whose verification honestly records that no real webhook was ever sent. The catch is the stack: this is FastAPI, Pydantic and SQLAlchemy, and the nine documents never once name a JavaScript or .NET equivalent for anything they teach. If your goal is React/Node/Next or ASP.NET/EF Core, read `02-CONCEPTS.md` and `03-WORKED-CHANGE.md` as a very good essay on CRUD invariants — tenancy, validation layers, transactions, optimistic concurrency, outbox — and then go implement those ideas in a project on your own stack. Do not spend an evening on the Python tooling unless you already know it.
