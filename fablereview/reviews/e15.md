## Does it transfer? (D4, stated plainly)
**Partially, and more than e14 does — but the course still never builds the bridge.** Three things here are stack-independent and genuinely worth a JS/.NET learner's attention: the HTTP semantics (`If-Match`/428/422/409 is the same contract in Express or ASP.NET — 428 Precondition Required for a missing header is a distinction most tutorials never make), the two-layer concurrency argument (check at the boundary *and* let the ORM add its own predicate, which maps exactly to EF Core `[Timestamp] rowversion` or a Prisma conditional `updateMany`), and the frontend half, which is plain `fetch` + form code in `app/static/app.js` — draft retention after a 409, sequence-number invalidation of stale search responses, and disabling controls until an operation completes are React problems too. What does not transfer is the whole backend idiom: FastAPI dependencies, SQLAlchemy sessions, Jinja templates, pytest fixtures. And as with e14, `grep -in "typescript|express|\.net|EF Core|C#|zod|react"` over `astraupskill/*.md` returns **nothing** — the README asserts "The same ideas transfer to other stacks" and then leaves the reader to do the translation unaided. Read it for the concurrency contract and the frontend recovery patterns; do not treat it as a stack-building exercise.

## What Astra did well
- The conflict contract is precise and the code is exactly as described. `app/main.py:168-184` implements `check_expected_version`: missing header -> 428 with the message "Send if-match with the version you reviewed before changing this record", `re.fullmatch(r'"?([1-9][0-9]{0,9})"?')` with a quote-balance check -> 422, version mismatch -> 409. It is called on ~10 routes including a *two-header* merge path (`:635-636` passes `if-match-source` for the second entity) — that is a genuinely mid-level detail.
- Defence in depth is real, not rhetoric. `app/models.py:21-28` defines a `Versioned` mixin whose `@declared_attr.directive __mapper_args__` returns `{"version_id_col": cls.version}`, inherited by 8 entities (`BusinessHours`, `Team`, `Customer`, `Channel`, `SLA`, `Ticket`, `AutomationRule`, `CannedReply`). 03-WORKED-CHANGE.md explains *why* both layers exist: "This second protection matters for code paths with independent sessions or future changes to transaction behavior."
- The conflict UX is the teaching point, and it refuses the easy answer: "Click 'Review latest while keeping draft.' … Because administration uses full replacement, accepting the new version and immediately saving could replace that newer note… This is deliberately a human review step. Automatically merging arbitrary text or always preferring the current tab would hide a product decision." (03-WORKED-CHANGE.md)
- VERIFICATION.md documents its own bug-finding loop rather than a clean narrative: an ambiguous administration selector label, a Playwright five-second assertion default that caused a timeout, low-contrast list text, a mobile screenshot captured before form initialization, and "an enabled Delete control whose handler was still busy refreshing after a save." It states the counting rule up front — "Repeated regression and clean-environment smoke cases are counted once" — and "A test that has been written but has not completed is not counted as passing."
- 06-SOLUTIONS-AND-REVIEW.md gives reasoning, not code: "It intentionally does not provide a paste-and-submit replacement for the work", and then teaches something real — "A good assertion compares actual ticket identifiers, not only the number of results. Two queries can return the same count while one contains an unauthorized ticket."

## Problems found (evidence required)
- **[D4]** Off-stack backend. The target learner wants React/Node/Next and ASP.NET/EF Core; this is FastAPI + SQLAlchemy + Jinja. No file in `astraupskill/` names a JS or .NET equivalent for `check_expected_version`, the `Versioned` mixin, `build_ticket_filters` or the receipt pattern, so all translation cost falls on the learner.
- **[D6, minor]** The headline "176 distinct passing checks" is not verifiable read-only: 76 test functions exist on disk and 17 `parametrize` decorators expand them to the claimed 156. VERIFICATION.md is transparent about the *union* method ("Union of full-01 and reply-timers-01 test identities; repeated regression cases counted once") but never states the function-vs-case distinction, so a skeptical reader counting `def test_` finds less than half the number.
- **[D7]** 6,290 words, and the application spans customers, tickets, messages, teams, channels, business calendars, SLAs, automation rules and canned replies. The README is honest ("Allow several focused sessions") but gives no hour estimate and no prerequisite list; business-calendar arithmetic and SLA timer semantics (`tests/test_business_time.py`, 12 functions) are a substantial domain detour for someone whose goal is CRUD fundamentals.
- **[D3, minor]** The course's best single asset — the 9 reviewed screenshots in `astraupskill/images/` — is only referenced from VERIFICATION.md's table. `03-WORKED-CHANGE.md`'s conflict walkthrough never points at `images/03-conflict-review.png`, which is a picture of the exact screen it describes.

## One-paragraph summary for the index
A help-desk application with the most precise concurrency contract in the batch: every mutating route demands an `If-Match` header and answers 428 when it is absent, 422 when it is malformed and 409 when the version moved, while a SQLAlchemy `Versioned` mixin adds a second, independent version predicate at the ORM layer — and the course explains why you want both. The conflict UI is equally well argued: on a rejected save the draft survives, a "Review latest while keeping draft" panel shows the stored record beside your edits, and the course explicitly refuses to auto-merge because that would hide a product decision. Verification is candid, listing the bugs its own screenshot review found (a Delete button still enabled while a refresh was in flight, low-contrast list text, a screenshot taken before form init). The obstacle is the stack: FastAPI, SQLAlchemy and Jinja, with no page anywhere mapping these ideas to Express, Prisma, EF Core or React. Read chapters 02, 03 and the frontend sections of 06 for HTTP concurrency and failure-recovery UX that apply everywhere, then build the equivalent on your own stack.
