# formforge — Fable review

- **Path:** `Desktop\formforge`  ·  **Wave:** 2  ·  **Stack:** pnpm 9.15.4 + Turbo monorepo; Fastify API, React + TanStack Query web, TypeScript 5.9, Vitest 4  ·  **Batch:** B18
- **Astra's change (one line):** Four bounded bug fixes with regression tests written first — (1) `InMemoryPublicationRepository.publish` now reads the existing slug's owner and throws a new `PublicationSlugConflictError` when the workspace or form differs, which the API maps to `409 {"code":"slug_unavailable"}`; (2) publication versions moved from a per-slug counter to a new `#byForm` index and snapshot IDs from the reconstructable `${workspaceId}:${formId}:v${version}` to `crypto.randomUUID()`, so publishing one form under a second slug no longer produces a duplicate ID that collided with submission idempotency keys; (3) the draft `PUT` and publish `POST` routes now reject `schema.id !== request.params.formId` with `400 form_identity_mismatch` before storing anything; (4) `useAutosave` moves its `requestSequence`/`latestRequest` increment out of the debounce callback and up to the edit itself, so an older in-flight save completing mid-debounce can no longer flip the status to "Saved" while a newer edit is still queued.

## What Astra did well
- These are four *real* bugs, found by reasoning rather than by linting, and the diff against the backup proves they existed. The slug takeover is the clearest: `backups/30217cacf1b9/packages/data/src/publications.ts` had no owner check at all — any workspace publishing to an existing slug simply appended to that slug's array and repointed the public address. The fix checks `versions[0]` and throws before either index is touched.
- The ID collision is the most interesting find and the course explains the cross-repository consequence precisely: the old ID was `${workspaceId}:${formId}:v${version}` with `version = versions.length + 1` *counted under the slug*, so form F published at slug A and again at slug B both produced `...:v1` — and the submission repository scopes idempotency by publication ID, so "the same caller key against two different snapshots" silently deduplicated. The test `'keeps version and identity distinct when one form publishes under another slug'` asserts exactly that: two `submit(.., "same-request", ..)` calls now both return `"created"`.
- The autosave fix is subtle and the test is genuinely a race test, not a timing sleep. `useAutosave.test.tsx` uses `vi.useFakeTimers()`, a `deferred<DraftSaveResult>()` for the first save, advances 300ms, clicks "Edit two", advances 100ms, resolves the *first* promise, and then asserts the status still reads "Changes queued" — and that the second call receives `expectedVersion: 1` (`expect(save.mock.calls[1]).toEqual([expect.objectContaining({ title: "Edit two" }), 1])`), proving the committed version was retained even though the status was suppressed. That last assertion is what separates a real fix from a status-only patch.
- The course refuses to let the learner believe the demo is wired up. README: "Seeing `useQuery` or an async function in the browser does not prove that it calls the API." I checked: `apps/web/src/App.tsx:112-116` `loadWorkspace` is `await Promise.resolve(); return workspaceId === demoWorkspace.id ? demoWorkspace : undefined;` — a fixture with a fake await, wrapped in `useQuery`. Most courses would have described this as "the client fetches the workspace."
- There is an **executable** lab. `astraupskill/labs/publication-trace.ts` uses `app.inject()` (no listening port, no external storage) and asserts versions 1 and 2 across a slug change, distinct IDs, 409 for another workspace's slug claim, 201 for independent submissions to both snapshots, and 400 for the identity mismatch — the exact sequence VERIFICATION claims it asserts. This is the only project in the batch where the learner can run the whole lesson as one command.
- 03-WORKED-CHANGE names the product decision it deliberately did *not* make: "an old slug still serves the latest snapshot published at that old slug. It does not automatically follow a new address. If you want redirect/rename semantics instead, specify and test them as a product change. Do not silently reinterpret stored history while fixing identity." That is senior judgment written down at a junior's reading level.
- Navigation is built in: every lesson opens with `[Course home] · [Previous] · [Next]` links, and the README has a per-lesson evidence + time-estimate table (60–90 min … 4–8 h). No other course in the batch does this.

## Problems found (evidence required)
- **[D5]** The documented gate does not run reliably on the target machine and the course knows it. README offers `pnpm.cmd gate` and then immediately a four-command fallback "On a machine with limited resources" (`--workspace-concurrency=1 exec vitest run --maxWorkers=2`, `turbo run lint typecheck build --concurrency=2`, …). VERIFICATION adds three more environment caveats: "The initial offline dependency installation lacked a required package", "A restricted filesystem invocation prevented the build tool from inspecting an ancestor directory", and "A cold, fully parallel baseline run exceeded one existing API test's five-second timeout." All honest, but a junior on a fresh machine has four ways to fail before reaching lesson 1, and the course never says which failure looks like which.
- **[D7]** The surface area is large for the stated audience ("Start with basic functions, objects, arrays and React components"). Lesson 1's reading table sends the learner across a pnpm workspace with four packages, Turbo, Fastify, TanStack Query, and a runtime schema parser. 7,432 words is the largest course in the batch and still cannot define pnpm workspaces, Turbo task graphs, or `app.inject()` — all of which appear as prerequisites rather than lessons.
- **[D4, scoping]** The delivered API stores everything in memory and has no authentication. The course says so twice ("The publishing header `x-workspace-id` demonstrates a workspace check; it is not authenticated identity. Draft routes do not have production authorization"), which is the right disclosure — but it means the ownership lesson is taught against a header the learner could trivially spoof, and the persistence half of CRUD (a database, transactions, migrations) is absent entirely. Practice item 4 and the capstone propose wiring the browser to the API; nothing proposes a real datastore.
- **[D2, residual]** `useAutosave` still advances `version.current` from a superseded request's result before the supersession check (`if (result.status === "saved") version.current = result.version; if (requestId !== latestRequest.current) return;`). This is deliberate and correct for the tested scenario — and the README calls it out ("The committed version is still retained for the next queued request") — but it means a *conflict* result from a superseded request is silently discarded with no record that the server disagreed. No test covers superseded-conflict, and no exercise asks about it.

## One-paragraph summary for the index
FormForge is the course to do if you want to see what a careful bug fix actually looks like on a real TypeScript monorepo. Astra found four genuine defects — a public slug that any workspace could take over, a publication ID built from a per-slug version counter that produced duplicate IDs and silently collided with submission idempotency keys, routes that stored a request body naming a different form than the URL, and an autosave whose stale in-flight response could report "Saved" while a newer edit was still debouncing — wrote a failing regression test for each first, then fixed them, and can prove all of it: 82 tests, five of them new, with counts that reconcile exactly against the files on disk. The course is also the most honest in the batch about what is fake: the React app's `loadWorkspace` is a fixture behind a `useQuery`, the storage is in-memory, and `x-workspace-id` is a header a caller can type, all stated up front rather than discovered later. It is also the most navigable — every lesson has previous/next links, a per-lesson evidence goal and a time estimate, and there is a single executable lab you can run to watch the whole publication story play out. Budget for friction: it is a pnpm + Turbo workspace with four packages and Fastify, the documented `pnpm gate` needs a reduced-concurrency fallback on a modest machine, and nothing here touches a real database.
