## What Astra did well
- Found a genuine authorization hole and fixed it correctly. The old `CanSystemTransition` was `map.ContainsKey(to)` — i.e. the background worker could trigger *any* legal edge including `Submitted -> Approved`, bypassing the Manager role. It now requires `roles.Length == 0`, which matches the table's own convention (`[ExpenseStatus.Reimbursed] = Array.Empty<UserRole>() // system-only`, `ExpenseStateMachine.cs:41`). The comment on line 18 documents that convention, so the fix is consistent with the design rather than invented.
- The command/queue ordering fix is well reasoned and well tested. `StartReimbursement` now takes the gate, validates the Finance edge, calls `TryEnqueue`, and only transitions on admission; `Full_reimbursement_queue_leaves_approved_expense_unchanged` and `Throwing_reimbursement_queue_leaves_approved_expense_unchanged` assert the expense is still `Approved` with no new history event.
- Rejected-operation tests assert *non-mutation*, not just the throw: `Reject_on_draft_does_not_change_reason_history_or_timestamp` captures `History.Count` and `UpdatedAt` before the call and asserts both unchanged; `Invalid_update_leaves_live_entity_unchanged` compares a full `Snapshot(expense)` record before/after.
- VERIFICATION.md volunteers its own defects, which is rare: "Lock entries are retained for the lifetime of the store, including deleted expense IDs" (an unbounded-growth leak Astra introduced), "The duplicate job has zero delay and does not force two threads to overlap", and "Receipt upload, `RefreshPolicy` and mutable readers remain outside that guarantee."
- Setup is honest about the toolchain mismatch: the project targets `net8.0` (confirmed at `backend/ExpenseManagement.Api.csproj:9`) while the machine had the .NET 10 SDK, so the commands set `$env:DOTNET_ROLL_FORWARD = 'Major'` and say why.

## Problems found (evidence required)
- **[D1]** `03-WORKED-CHANGE.md:3` claims the old code "discarded the returned `ValueTask`, and left the entity in `Reimbursing` even though no worker was admitted." The queue is built with `FullMode = BoundedChannelFullMode.Wait` (`BackgroundTaskQueue.cs:29`), so a discarded `WriteAsync` on a full channel does *not* drop the item — it parks a pending writer that completes when capacity frees. The real defects are the swallowed exception, the unbounded pending-writer set, and the ordering; the course's stated mechanism is wrong and would teach a junior an incorrect model of `Channel<T>.WriteAsync`. Neither `02-CONCEPTS.md` nor `04` ever mentions `BoundedChannelFullMode`.
- **[D3]** `05-PRACTICE.md` exercises 1–4 are almost entirely "add another test"; only exercise 5 asks for design reasoning, and no exercise asks the learner to make a production change and watch an existing test go red first. The predict step is one line at the end ("write the assertion first").
- **[D7]** `06-SOLUTIONS-AND-REVIEW.md` is 1,675 words — a third of the whole course — and is largely a complete fixture dump, while `01-CODEBASE-MAP.md` gets 353 words. The balance favors copyable answers over orientation.
- **[D4]** No persistence anywhere: `DataStore` is `ConcurrentDictionary`, there is no EF Core, DbContext, migration or SQL in the repo. The lock/transaction lesson is transferable in spirit but the learner never writes `SaveChangesAsync`, a transaction scope, or a concurrency token.
- **[D2, minor]** The test project was placed *inside* the API project's directory (`backend/ExpenseManagement.Api.Tests/`), forcing an `<Compile Remove="ExpenseManagement.Api.Tests/**/*.cs" />` block into `ExpenseManagement.Api.csproj`. It works, and VERIFICATION discloses it, but it is a layout a junior should not copy; a sibling `backend.Tests/` folder would have needed no csproj surgery.

## One-paragraph summary for the index
A good second .NET course on the theme "a CRUD command is more than a field write": one expense request touches fields, policy flags, audit history and an async job, so the failure boundary has to cover all four. The delivered change is real and includes a genuine security fix — the background worker could previously drive *any* legal state transition, including a manager-only approval — plus a per-expense gate shared by commands and the worker, and a non-blocking queue-admission check so a full queue can no longer leave an expense falsely `Reimbursing`. Ten new xUnit tests (the project had none) assert unchanged state after rejection rather than just the exception, and the verification file is candid about what it does not prove, including a lock-dictionary leak Astra introduced. Two caveats: its explanation of the original queue bug misstates how `Channel.WriteAsync` behaves on a full bounded channel with `FullMode.Wait`, and there is no database anywhere, so you learn locking without ever writing a transaction. Take it after CampusOps if you want more reps on state machines and worker authority; skip it if you need EF Core.
