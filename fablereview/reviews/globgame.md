## What Astra did well
- The code is a model CRUD implementation and would serve as a reference answer for half the rubric's target skills at once. `src/lib/puzzles/authoring.js:95-122` (`updatePuzzle`) reads the row inside `$transaction`, rejects a published edition, then does `updateMany({where:{id, version, publishedAt:null, isPublished:false}, data:{..., version:{increment:1}}})` and throws 409 on `changed.count !== 1` before replacing the child groups — read-check, conditional write, and child replacement in the right order.
- Audit retention is designed, not accidental: `prisma/schema.prisma:80-87` gives `PuzzleAudit` a bare `puzzleId String` with **no** `@relation`, so the `audit(tx, id, "DELETE", version+1)` call in `deletePuzzle` survives the cascade that wipes `PuzzleGroup`. That is a deliberate, teachable modelling decision.
- Verification is the strongest in this batch. The delivery ships raw logs (`checks/glob/final/model-tests.log` ends `# pass 34 / # fail 0`; `database-tests.log` `# pass 10`; `browser.json` `stats: {expected: 9, unexpected: 0, flaky: 0}`), two reviewed screenshots in `astraupskill/images/`, a seed-run and a seed-repeat log, and a `postgres-stop.log` proving the helper cluster was torn down. The notes field even records a failure that was found and fixed ("Initial browser run found Next internal-URL origin mismatch").
- The database suite tests rollback for real rather than by mock: `tests/database.test.js:155` installs a temporary plpgsql trigger `reject_test_audit()` that raises on `NEW.action = 'UPDATE'`, then asserts title, version, categories and audit count are all unchanged. `03-WORKED-CHANGE.md` explains exactly why: "Checking only the HTTP status would not establish this invariant."
- Limits are stated in six separate bullets in the delivery JSON *and* restated in `VERIFICATION.md` — shared token is not accounts, public payload exposes answers so the client is not an anti-cheat boundary, the migration targets an empty learning database, no crash/power-loss testing.
- The rewritten project `README.md:10-30,45-51` gives a genuinely reproducible setup: `npm ci`, `npm run prisma:generate`, set `DATABASE_URL` and `GLOBS_AUTHOR_TOKEN`, `npm run prisma:deploy`, `npm run dev`, plus `POSTGRES_BIN` guidance and the exact Windows default path.

## Problems found (evidence required)
- **[D3]** **There is not one line of code in the entire course.** `grep -c '```' astraupskill/*.md` returns 0 for all nine files. Nine chapters of continuous prose describe transactions, conditional writes and validators without ever showing one. A junior cannot pattern-match from this; they must reverse-engineer every idea out of `authoring.js` themselves. Compare with the appmakertrack course in this same batch, which inlines the exact function it discusses.
- **[D3]** There are no line references or file:line anchors anywhere — only bare links like `[updatePuzzle](../src/lib/puzzles/authoring.js)` (`03-WORKED-CHANGE.md:7`), which drops the reader into a 240-line file.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` is titled "Review the reasoning behind the solution" and contains **no solutions** — 448 words of design commentary for six practice tasks. There is nothing to check your work against, no worked answer, no test to run.
- **[D7]** The practice sequence is mid-to-senior, not junior. `05-PRACTICE.md` task 3 is "Replace the shared local workshop token with an explicit account/session design … Test another author's identifier, a revoked session, and a role change"; task 4 is a durable idempotency-receipt design with concurrent-request tests; task 5 is a transactional outbox. Each is a multi-day project with no scaffolding, no starter code and no acceptance test. Tasks do not escalate from guided to independent — they start independent.
- **[D7]** Senior vocabulary is used without definition: "repeatable-read transaction", "canonical request fingerprint", "outbox row records intent", "exactly once", "CSRF assumptions", "offset pagination still shifts" (all in `06-SOLUTIONS-AND-REVIEW.md`). No glossary chapter exists.
- **[D3]** No predict-then-run loop with concrete expected output. `03-WORKED-CHANGE.md` says "Expect a conflict, retained fields, and no category replacement" but never gives the status code, response body shape or the SQL/Prisma call to look for — all of which exist in the code (`409`, "Puzzle changed. Keep your draft and load current data before retrying.").
- **[D4, minor]** The project is plain JavaScript with `jsconfig.json`; a learner targeting the TS/React job market gets the CRUD patterns but no type-contract practice. Nothing in the course says so.
- **[D2, minor]** Much of the diff against the backup is Prettier reflow (e.g. `src/lib/game/engine.js:133-140,161,201,231` are pure line-wrapping changes), which inflates the apparent size of the change and makes the real edits harder to find in review.

## One-paragraph summary for the index
The *code* here is the best CRUD reference in the batch: a whole authoring feature added to a client-only puzzle game, with every write wrapped in a Postgres transaction, optimistic concurrency via a `version` column and conditional `updateMany`, lifecycle rules that make published editions immutable, an audit table deliberately modelled without a foreign key so its rows survive deletion, `RepeatableRead` pagination, a real migration, and an idempotent seed — all of it verified by 34 model tests, 10 tests against a throwaway PostgreSQL cluster (including a rollback proven with a plpgsql trigger), and 9 Chromium workflows, with the raw logs and screenshots shipped alongside. The *course* does not live up to it: 3,935 words containing zero code blocks, zero line references, a "solutions" chapter with no solutions, and a practice list whose second half (individual accounts, durable idempotency receipts, a transactional outbox) is senior work with no scaffolding. Read this one as a code-reading exercise — open `src/lib/puzzles/authoring.js` and `tests/database.test.js` next to the chapters — and treat the practice list as a menu, not a sequence.
