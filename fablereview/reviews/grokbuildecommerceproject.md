## What Astra did well
- The idempotency implementation is the real article, and it is the single best thing in this batch to learn from. `backend/src/repositories/orderRepository.ts:84-104`: advisory transaction lock on `userId + ":" + requestId` **before** reading the receipt, then `order.findUnique({ where: { userId_checkoutKey: … } })`, then a fingerprint comparison that returns `replayed: true` for the same cart and a 409 for a different one. The unique constraint is kept as "a final backstop" rather than the primary mechanism, and the course says so.
- Deadlock avoidance is deliberate and explained: `sortedItems()` sorts by product ID, and `lockProduct` issues `SELECT id FROM "Product" WHERE id=$1 FOR UPDATE` in that order (`orderRepository.ts:20-41, 118`). Most juniors never learn why lock ordering matters; this shows it in ~15 lines.
- Money is handled correctly — `Prisma.Decimal` accumulated with `.add(product.price.mul(item.quantity))` and a total bound check against `"9999999999.99"` (`orderRepository.ts:105-142`). `04-TESTING-AND-DEBUGGING.md` explicitly tests "0.10 plus 0.20, excess fractional precision, and an aggregate order exceeding its storage bound" and notes "Valid individual prices do not guarantee a valid total."
- The lost-response test is a genuine end-to-end proof, not a simulation of one. `browser-tests/commerce.spec.mjs:264` "a lost checkout response can retry the same key without another order" — and `04` makes the methodological point explicitly: "Do not simulate uncertainty merely by returning a 503 before the request reaches the API. That tests rejection handling, not recovery of an already committed order."
- Evidence is real and from one run: `checks/commerce-workspace/full-final/backend.json` `numPassedTests: 55, numFailedTests: 0`; `frontend.json` 8/8; `setup-tests.log` `# fail 0`; `browser-tests.log:19` `14 passed (1.3m)`. That is 80, matching `results.json` and the delivery.
- `VERIFICATION.md` lists limits that would be easy to hide: the displayed cart total is only an estimate because checkout uses current server prices; "Docker configuration was written but not exercised with a daemon"; "Losing an uncertain checkout key and starting again can create another order, so review order history before unlocking a failed attempt." That last one is an admission of a real residual hole in its own headline feature.

## Problems found (evidence required)
- **[D7]** This is not a junior course. `05-PRACTICE.md` task 3 asks the learner to "Model pending, accepted, rejected, and uncertain provider outcomes … Use durable intent, provider idempotency where available, and reconciliation rather than holding a database transaction open across a network call. Demonstrate the crash window after provider acceptance but before the local receipt is saved." That is a senior distributed-systems exercise. `02-CONCEPTS.md` opens on three simultaneous identity concepts (subject, record version, retry key) with no warm-up.
- **[D3]** All four practice tasks are open-ended designs and `06-SOLUTIONS-AND-REVIEW.md` provides "review reasoning", not solutions. A learner who attempts task 1 (price-confirmation quote) has nothing to check their answer against — no reference diff, no reference test. The rubric's "solutions kept separate from exercises" is satisfied only because there are effectively no solutions.
- **[D5/D6]** The evidence does not ship with the project. `astraupskill/` contains the 9 markdown files and `images/` only — no `evidence/` directory. `VERIFICATION.md` asserts "80 checks" and the learner has to take it on faith; the JSON reports live outside the repo at `AstraOrganized2/astra-remaining-improvements/checks/commerce-workspace/`.
- **[D2, residual]** `backend-tests.log:87,113,139` shows three `"status":500,"event":"request_failed"` entries during the passing run. These are the deliberate injected-audit-failure cases, so they are expected — but a 500 is the wrong status for a synthetic rollback test to leave in the log, and neither `04-TESTING-AND-DEBUGGING.md` nor `VERIFICATION.md` tells the learner these log lines are intentional. A junior reading the log will think the suite is masking failures.
- **[D3, minor]** No chapter asks the learner to remove a safeguard and watch it break. The advisory lock, the `FOR UPDATE` ordering and the fingerprint check are each explained but never falsified.

## One-paragraph summary for the index
The best treatment of checkout reliability in the whole collection: a real advisory-lock + durable-receipt + payload-fingerprint idempotency design, decimal money that is actually tested at the precision boundary, product row locks taken in sorted order to avoid deadlock, immutable order-line snapshots, and cancellation that restores inventory exactly once. All 80 checks — including 14 Chromium scenarios and a genuine lost-response retry through the real UI — are backed by machine-readable reports from a single run against a disposable PostgreSQL 18 cluster, and the verification chapter volunteers the holes it did not close. The catch is difficulty: the concepts chapter opens with three overlapping notions of identity and the practice tasks ask for payment-adapter crash windows and quote expiry, with review heuristics instead of solutions. Treat it as the capstone of a CRUD path rather than an entry point, and read `03-WORKED-CHANGE.md` before anything else.
