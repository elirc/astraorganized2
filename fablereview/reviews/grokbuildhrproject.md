## What Astra did well
- The defect it repairs is the single most valuable one a junior can internalise, and it was genuinely in the starter: `backups/baf8258948be/backend/src/routes/leaveRoutes.ts:22` reads `const { approverId, status } = req.body;` and `services/leaveService.ts:17` writes `{ status, approvedBy: approverId }` — the client names its own approver and overwrites any prior decision. The replacement derives the actor from the token, re-reads the reporting relationship from the database, rejects self-approval, and requires both the captured version *and* `PENDING` state.
- Two-layer overlap protection, correctly built and correctly explained. `backend/prisma/migrations/202609090001_hr_workspace/migration.sql:140-143` creates `btree_gist` and `EXCLUDE USING gist ("employeeId" WITH =, daterange("startDate","endDate",'[]') WITH &&) WHERE ("status" IN ('PENDING','APPROVED'))`, while `leaveRepository.ts:52-71,130,163` does the application-level check under an employee row lock (`scope.ts:94`, `SELECT id FROM "Employee" WHERE id=$1 FOR UPDATE`). `02-CONCEPTS.md` states the division of labour precisely: "The application check provides a clear error; the database constraint protects the invariant."
- The migration carries real domain CHECK constraints, not just types: `LeaveRequest_dates_valid` bounds the span to under 366 days, `Employee_not_self_manager` uses `IS DISTINCT FROM`, and the three `version > 0` checks. Most teaching projects put none of this in the database.
- `03-WORKED-CHANGE.md` ends with an actual reproduce-the-race procedure — create fictional leave, open manager and HR tabs, decide from the manager tab, then attempt the HR decision from the stale baseline, and verify "the conflict, unchanged accepted decider, retained HR note, and unchanged audit count for the rejected attempt". That is the predict-run-verify loop most of this batch lacks.
- The version/state distinction is taught explicitly rather than conflated: "A second attempt using version two also cannot decide an already terminal request because the PENDING-state rule is independent from the version rule. Each protects a different invariant."
- Honest verification: `VERIFICATION.md` discloses that "the browser rerun followed a locator correction for populated textareas. No failed assertion was removed", that Docker Compose "was not exercised with a daemon", that "New employee records deliberately have no login password", and that the `Review` model exists in Prisma but has no implemented CRUD.

## Problems found (evidence required)
- **[D2]** `chartLock` (`backend/src/repositories/employeeRepository.ts:21-23`) takes `pg_advisory_xact_lock(74219801)` — a single hard-coded constant, so *every* employee mutation in the whole database serializes against every other one, not just those touching the same manager chain. That is a correct-but-blunt choice, and `02-CONCEPTS.md` describes it only as "a transaction-level advisory lock while validating the manager chain" without mentioning that it is a global mutex. A junior copying this pattern into a larger system will create a throughput cliff and not know why.
- **[D5/D3]** The starter code is not shipped with the course. `astraupskill/` has the 9 markdown files and `images/` — no `snapshots/` and no `evidence/`, unlike master2/3/4 which ship exact `*.before.txt` files. `03-WORKED-CHANGE.md` opens "The starter accepted an `approverId` in a request body…" and the learner has no way to see that code; it exists only in `AstraOrganized2/astra-remaining-improvements/backups/baf8258948be/`. The same applies to the 76-check evidence, which lives in `checks/hr-workspace/`.
- **[D6, minor]** The 76 is a composite of two runs: backend/frontend from `full-first/` and the 11 browser scenarios from `browser-final/` after the locator fix. The delivery's `checks.command` says so, but no single green run of all 76 was recorded.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` is review reasoning, not solutions. All three `05-PRACTICE.md` tasks are open-ended designs; task 3 ("Introduce reviews as an actual workflow … Include self-review and unrelated-manager denial tests, concurrent submit tests, and a forced audit failure") is a multi-day vertical slice with nothing to check an answer against.
- **[D7]** The concepts chapter moves from roles to a state machine to interval algebra to advisory locks to graph-cycle invariants in ~700 words. The material is correct and the mermaid state diagram helps, but a junior will need the `02` chapter split across several sessions; nothing in the course signals that.

## One-paragraph summary for the index
Take this one for authorization and for time intervals. The starter let a client POST `approverId` and approve its own leave; the repaired version derives the actor from the token, re-reads the reporting relationship from the database, blocks self-approval, and treats a decision as a version-conditional transition out of `PENDING` — with the course carefully separating the version rule from the state rule because each protects a different invariant. The leave-overlap work is the standout: inclusive calendar semantics enforced twice, once in application code under an employee row lock for a readable error and once by a PostgreSQL `EXCLUDE USING gist` partial constraint that survives writes bypassing the repository. All 76 checks are backed by real reports against a disposable PostgreSQL 18 cluster and the limits chapter is candid about what is not implemented. Its gaps are packaging rather than substance: the starter code and the evidence files it references live outside the project folder, and the three practice tasks ship with review heuristics instead of answers.
