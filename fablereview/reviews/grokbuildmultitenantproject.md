## What Astra did well
- The "before" is the perfect teaching artifact and it is real: `backups/01e135926859/backend/src/middleware/tenantContext.ts:17-18` is literally `// For learning/demo:` followed by `req.currentOrgId = (req.headers['x-org-id'] as string) || 'demo-org';`, and `projectController.ts:6` repeats the `|| 'demo-org'` fallback. `03-WORKED-CHANGE.md`'s opening line — "A comment saying data was isolated could not establish that behavior" — is exactly right and exactly demonstrable.
- The 24 integration tests are the most convincing tenant-isolation suite in the batch, and they are named after properties rather than endpoints: "removes access after membership revocation without trusting old JWT roles" (`:154`), "scopes single reads and writes even when the user belongs to both tenants" (`:179`), "enforces tenant parent matching in the database itself" (`:362`), "rolls back project create update and delete when audit fails" (`:383`), "uses literal wildcard search and stable bounded pages" (`:441`). They run real Express over a real disposable PostgreSQL via supertest.
- Defense in depth again shows up in the schema, not just the code: `migration.sql:113` `ALTER TABLE "Task" ADD CONSTRAINT "Task_projectId_organizationId_fkey" FOREIGN KEY ("projectId","organizationId") REFERENCES "Project"("id","organizationId")`, and there is a test (`:362`) whose whole purpose is to prove the database rejects a mismatched parent independently of the repository.
- `04-TESTING-AND-DEBUGGING.md` teaches test *methodology*, not just commands: "These assertions inspect returned values and persisted rows rather than only spying on helper calls"; "The competing-writer tests issue two HTTP updates with the same version and require one accepted response and one conflict. A sequential happy-path test would not demonstrate that property"; and the audit-rollback cases "install a PostgreSQL trigger that rejects audit insertion". It even explains why the non-ASCII password fixture uses a Unicode escape "so shell encoding cannot silently change the tested value".
- `03-WORKED-CHANGE.md` closes with a layered argument a reviewer can actually use — authentication / membership / role policy / scoped predicates / captured versions / transactions / UI draft retention, "Each layer answers a different question. Removing any one weakens the feature even if a simple create-and-list demo still appears to work."

## Problems found (evidence required)
- **[D6]** The evidence trail is misleading if read at face value. `checks/tenant-workspace/final/frontend.json` reports `numFailedTestSuites: 2, numPassedTests: 4, numFailedTests: 2` — i.e. the directory named `final/` records a run where two frontend tests failed. The genuinely final green run is in the differently-named `verified/` directory (`verified/frontend.json` 6/6, `verified/backend.json` 36/36, `verified/browser-tests.log:15` "10 passed", `verified/setup-tests.log` "# pass 3"). `VERIFICATION.md` never mentions the earlier failure or which directory is authoritative — unlike this batch's master2/3/4 and `grokbuildhrproject`, all of which explicitly narrate their discarded runs. The 55 figure is true, but a reviewer following the obvious path lands on the wrong file.
- **[D5/D3]** Nothing from the "before" ships with the course. `astraupskill/` holds the 9 markdown files and `images/` only — no `snapshots/`, no `evidence/`. `03-WORKED-CHANGE.md` describes the `|| 'demo-org'` starter and `VERIFICATION.md` cites 55 checks, and neither is inspectable from inside the repository; both live under `AstraOrganized2/astra-remaining-improvements/`.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` is review reasoning rather than solutions, and all four `05-PRACTICE.md` tasks are open-ended designs. Task 3 ("Add durable create idempotency … Store a normalized payload fingerprint and accepted identity transactionally … concurrent identical requests create one record") is a serious distributed-correctness exercise with acceptance criteria but no reference implementation — even though `grokbuildecommerceproject` in this same batch contains a working version of exactly that. The two courses never cross-reference.
- **[D7]** The course assumes a reader who already knows what a JWT `aud`/`iss` claim is, what an optimistic version is for, and why count and list must share a read transaction. `02-CONCEPTS.md` introduces selection-vs-authorization, identity-vs-version, and cache scoping in the first three paragraphs. Correct and well written, but it is mid-level material presented at mid-level pace.
- **[D2, minor]** There is no dedicated unit test for `middleware/tenantContext.ts` or `middleware/auth.ts`; they are exercised only indirectly through the integration suite. Given that the entire lesson is about that boundary, a direct test of "membership absent -> 401 before any repository call" would be the natural first test to show a learner.

## One-paragraph summary for the index
This is the course to read when you want to understand what multi-tenancy actually costs. The starter "isolated" tenants with a comment and `req.headers['x-org-id'] || 'demo-org'`; the rebuilt version verifies an expiring token, looks up the caller's membership in the *selected* organization on every single request, puts the organization predicate on every read and write, enforces the parent relationship a second time with a composite foreign key in PostgreSQL, and keeps versions, audit rows and the mutation in one transaction. Its 24 integration tests run real HTTP against a disposable PostgreSQL cluster and are named after properties — membership revocation, cross-tenant reads by a dual-member user, audit-failure rollback via a real trigger, competing writers at the same version — which makes the test file itself worth reading as a checklist. Two caveats: the practice tasks come with acceptance criteria but no solutions, and the evidence directory named `final/` is *not* the final run (the green 55-check run is in `verified/`), which the verification chapter never explains.
