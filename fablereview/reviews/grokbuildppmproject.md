## What Astra did well
- The bug is the single most valuable CRUD bug a junior can learn, and the "before" is preserved verbatim so you can see it. `astraupskill/snapshots/taskRoutes-before.ts.txt` shows `createTaskSchema.partial().parse(req.body);` on its own line with the result discarded, and `snapshots/taskService-before.ts.txt` shows `export async function updateTask(id: string, data: any) { … prisma.task.update({ where: { id }, data }) }`. Seven exact before-snapshots ship inside the course folder.
- The repair fixes the *root* boundary rather than the symptom: validation moved down into `backend/src/services/taskService.ts:31-48` (`.strict()` on both schemas, `.refine` rejecting an empty update), so a future job or CLI caller is protected too — and the course says exactly that ("The repaired service also parses direct callers because HTTP validation alone cannot protect a future job or CLI", 06-SOLUTIONS-AND-REVIEW.md).
- Error classification is taught with a real distinction, not a slogan. `taskService.ts:104-106` defines `isMissingRecord` as `error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2025'`; the old code's bare `catch { return null }` turned a database outage into a 404. Exercise 3 asks the learner to argue why "a catch-all false result is a correctness bug rather than merely an observability inconvenience."
- Evidence is genuine, unedited tool output. `astraupskill/evidence/backend-test-04.log` ends with `Tests 8 passed (8)` and `frontend-test-03.log` with `Tests 6 passed (6)` — 14 total, exactly the claim. The log even retains a `stderr / Unhandled error: Error: portfolio database outage` block from a deliberate outage test rather than being cleaned up.

## Problems found (evidence required)
- **[D1]** `astraupskill/README.md` says "The bounded repair fixes a dangerous boundary in `backend/src/routes/taskRoutes.ts`, `controllers/taskController.ts`, and `services/taskService.ts`." `backend/src/controllers/taskController.ts` is byte-identical to `astraupskill/snapshots/taskController-before.ts.txt` (`diff` reports no difference) and does not appear in `deliveries/475084a31c00.json`'s file list. It still does `taskService.updateTask(req.params.id, req.body)` (`taskController.ts:42`) — which is now safe only because the service validates. A learner told the controller was repaired will look for a change that is not there.
- **[D2]** The whole backend suite mocks Prisma at the module boundary, so nothing proves persistence, foreign keys or tenant isolation. VERIFICATION.md admits it ("A mock call cannot prove foreign-key enforcement or persistence durability"), but it means the delivered "CRUD" is a validated write *argument*, not a validated write. The app after the change still has no ownership check, no pagination, and `limits` concedes "the demo JWT secret fallback remain[s]".
- **[D3]** Exercises 2, 3, 5 and 6 ask the learner to write code that is already sitting in the working tree in final form — Exercise 2's requested schema is `taskService.ts:37-48` verbatim, and 06-SOLUTIONS-AND-REVIEW.md reprints it identically. There is no "check out the before-snapshot into a scratch file and work there" instruction, so the honest path is spoiled by default.
- **[D7]** 01-CODEBASE-MAP.md is the shortest file (357 words) and the frontend is barely mapped; the course leans on the reader already knowing Express middleware ordering and `next(err)` semantics. `asyncHandler` is introduced in 03-WORKED-CHANGE.md without first explaining why an `async` Express 4 handler's rejection is silently dropped — that is the crux for a junior.

## One-paragraph summary for the index
A short, sharp course built around one of the highest-value bugs in CRUD web development: a PATCH route that validates the request body and then throws the parsed result away, letting arbitrary keys ride `req.body` into `prisma.task.update`. The repair is exactly what you would want a mid-level engineer to do — move strict Zod schemas down into the service so every caller crosses the trust boundary, make the parsed value the write argument, distinguish Prisma `P2025` from a real outage instead of swallowing both, and add async error forwarding — and seven byte-exact "before" snapshots let you read the original mistake. It is narrower than it sounds: Prisma is mocked throughout, so nothing here proves persistence, foreign keys or tenant isolation, and the app still has no authorization or pagination. Do it as a focused two-to-three hour drill on validation boundaries and error classification, not as a full CRUD app build, and copy the before-snapshots into a scratch directory first so the exercises are not pre-answered by the delivered code.
