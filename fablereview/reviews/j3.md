## What Astra did well
- The headline defect is real and is the single most useful thing a junior can learn about service boundaries. `backups/d0778f38946f/src/bankapp/service/BankService.java:53-55` is literally `public BankAccount getAccountById(String accountId) { return accountsById.get(accountId); }`, and `getAllAccounts()` at :47 copies only the list. The course README says exactly this: "Copying only the surrounding list did not solve that problem, because the list still contained the same mutable objects."
- The transfer implementation teaches ordering: `src/bankapp/service/BankService.java:107` builds **both** `Transaction` values (which validate on construction) before calling `decreaseBalance`/`increaseBalance`, so a rejected transaction cannot leave a balance moved with no history.
- Concurrency is tested for real, not asserted: `test/bankapp/RegressionTests.java:50-53` runs 64 withdrawals across an 8-thread pool behind a `CountDownLatch` gate and asserts the account cannot overdraw — matching both the VERIFICATION wording ("64 competing withdrawals") and the spec environment ("eight-thread withdrawal competition").
- VERIFICATION.md is the most self-critical document in the batch. It records that "Six initial regression checks failed against the original source", that "restricted compiler access produced a resource-close error; reviewed full-access verification succeeded", and that the footer "is not a checksum or tamper-proof signature". It also warns "do not alternate old and new programs against the same directory" after migration.

## Problems found (evidence required)
- **[D2]** The persistence ordering is the weaker one, and it is the opposite of what J1 and j2 in this same batch teach. `src/bankapp/App.java` mutates through `bankService` and *then* calls `saveData()` (lines 101, 134, 148, 166, 203, 220), and the delivery admits it: "Commands mutate memory before saving; save failure exits CLI without success but the service has no persistence rollback unit of work." So a failed save leaves in-memory state ahead of disk. Astra converts this into `05-PRACTICE.md` exercise 4 ("Make command persistence one unit of work"), which is honest, but the shipped code is a weaker demonstration than its sibling projects.
- **[D2]** No cross-process protection. `BankService` is `synchronized` per instance only; VERIFICATION states "Two independent services or processes can still race when saving the same file, and the file format has no compare-and-swap version protocol." J1 and j2 both implemented a cooperative lock + baseline compare and proved it with two racing JVMs; j3's seven CLI scenarios are sequential, so the batch's most valuable concurrency demo is absent here.
- **[D4]** Off the target stacks: Java CLI, no HTTP, no browser, no database, no auth (delivery limit 1). Exercises 5 and 6 (`Build a database-backed HTTP adapter`, `Add authenticated ownership and idempotent commands`) are design-only.
- **[D7]** `test/bankapp/RegressionTests.java` compresses 28 tests into 85 lines of one-statement-per-line Java (e.g. line 51 declares the executor, latch and future list in a single statement). 04-TESTING-AND-DEBUGGING sends learners into this file.
- **[D8]** Shares the Java-trio framing template. `05-PRACTICE.md` opens "These are proposed extensions, not delivered features. Start each with an observable contract and a failing test. Preserve existing learning data and use a separate directory for format experiments" — the same three-beat opening as J1 and j2 with the nouns swapped.

## One-paragraph summary for the index
Read this for one crisp lesson: a service that hands out its own mutable objects has no rules. The original `getAccountById` returned the live account, so any caller could change a balance without producing a transaction; the rewrite returns detached copies, validates money precision, builds both sides of a transfer's history before touching a balance, and writes accounts and transactions together as one atomically replaced snapshot instead of two files that could drift apart. Evidence is solid — 28 regression tests including 64 threaded withdrawals that cannot overdraw, plus seven scripted CLI runs — and the verification document is refreshingly self-critical. Its two real weaknesses are acknowledged rather than fixed: commands still mutate memory before the save succeeds, and there is no cross-process protection, both of which its sibling projects J1 and j2 do implement. Do j3 after those two and treat its practice ladder as the real work.
