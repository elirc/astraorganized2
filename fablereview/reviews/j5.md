## What Astra did well
- The headline fix is a *found* bug, not an invented one, and the course leads with it: "The original implementation failed this question for the ordinary case of an empty optional note" (`astraupskill/README.md`). `VERIFICATION.md` names all four originally-failing tests (empty note, non-rejecting malformed row, duplicate IDs overwriting manager state, sub-cent precision accepted). That is the strongest pedagogical hook in the batch — a junior sees a defect, its reproduction and its guard.
- `ExpenseFileStorage.save` (`src/expensetracker/ExpenseFileStorage.java:56-75`) shows the right ordering explicitly and comments why: `List.copyOf` snapshot → re-validate through a throwaway `ExpenseManager` → build all lines → write temp → `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)` in a `try/finally` that deletes the temp. The comment "invalid input cannot truncate existing data" is the actual invariant, not decoration.
- The escape/split pair (`escape`/`unescape`/`splitPreservingEscapes`, lines 100-178) is a hand-rolled but correct serializer with an explicit "Incomplete escape sequence" rejection — an excellent small example of "your storage format is a contract".
- The practice ladder attacks a limitation of Astra's *own* delivered code rather than a generic wishlist: `05-PRACTICE.md` §2 — "Today `nextId` is reconstructed from the maximum remaining ID. Deleting the largest record and restarting can reuse that ID" — and `VERIFICATION.md` admits the same thing. Exercises and solutions are in separate files, and `06-SOLUTIONS-AND-REVIEW.md` opens with "Use these notes after attempting…" and gives design directions plus an explicit weak-vs-strong contrast ("A weak solution always prints `Saved` after calling a method that swallowed an exception").

## Problems found (evidence required)
- **[D4]** Off-stack. The entire artifact is Java; the target stacks (React/Node/Next/TS, C#/.NET) appear only as prose destinations in `05-PRACTICE.md`. No HTTP handler, no schema, no TS/C# code is produced or shown, so the transfer work falls entirely on the junior.
- **[D5]** `astraupskill/README.md` says "With no override, the script uses the project's `data/expenses.txt`" — there is **no `data/` directory in the project** (`ls` shows only `.gitignore`, `astraupskill`, `README.md`, `run.ps1`, `src`, `test`). The behavior is benign (`load()` returns an empty list when `Files.notExists`, and `save()` calls `Files.createDirectories(parent)`), but the doc reads as if a seeded fixture exists and none does. Same for the suggested `.\data\learning-expenses.txt`.
- **[D5]** PowerShell-only runner; no macOS/Linux command is given anywhere. `run.ps1` does at least fall back to `$env:JAVA_HOME` (line 3), which `j4` does not.
- **[D7]** `06-SOLUTIONS-AND-REVIEW.md` jumps to "keep the saved records and next-ID metadata in the same atomic snapshot. Writing the counter to a second unrelated file introduces a two-write consistency problem" without ever defining *two-write consistency problem* / dual-write. That is exactly the concept a junior needs named and unpacked (it is the same problem as the outbox pattern in the `task-queue-system` course in this batch) — cross-reference it.
- **[D1 — minor]** `VERIFICATION.md` points at "the repository's `astrdocs/REMAINING_PROJECTS_IMPLEMENTATION_REPORT.md`" from inside the project folder; that path is only resolvable relative to `AstraOrganized2`, not to `j5`. A learner reading the course in place cannot follow it.

## One-paragraph summary for the index
The best *teaching* artifact of the three Java experiments in this batch: Astra found a real data-loss bug (a blank optional note disappearing on reload), wrote the failing test first, fixed it, and then hardened the whole load/save path so a malformed file fails loudly instead of quietly dropping your records. The course explains why validate-then-serialize-then-atomically-replace is the ordering that matters, keeps exercises and solutions in separate files, and — rare for this kind of deliverable — the practice ladder attacks a limitation of Astra's own code (IDs can be reused after you delete the newest record) that `VERIFICATION.md` also admits. Two caveats: it is Java, so nothing here compiles in your Node or .NET job, and the docs reference a `data/` fixture directory that does not exist. Read it for the persistence-correctness reasoning, then immediately redo exercise 1 and 5 in Express or ASP.NET so the habits land on your actual stack.
