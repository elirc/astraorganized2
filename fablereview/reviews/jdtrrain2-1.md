## What Astra did well
- The omission / explicit-null / no-op distinction — the single most common CRUD PATCH bug — is implemented correctly and taught explicitly. `src/app/api/issues/route.js` keeps `Object.prototype.hasOwnProperty.call(ctx.body, field)` checks, `delete updates[field]` when the normalized new value equals the old, and `if (Object.keys(updates).length === 0) return { issue: existing }`. `06-SOLUTIONS-AND-REVIEW.md` Exercise 6 names the trap: "Numeric zero is retained as a real value because comparisons use nullish semantics, not truthiness."
- Side effects were genuinely moved inside the transaction rather than merely reordered. The backup had `await Promise.all(activityTasks)` *after* `prisma.issue.update` and a separate `prisma.notification.create`; the new code builds inert `activityData` objects and then inside `$transaction` does `tx.issue.update`, `createIssueActivity({...activity, client: tx})`, `tx.notification.create`. The enabling change is one line in `src/lib/server/activity.js:13` (`client = prisma` parameter) — a clean, teachable seam.
- Bulk sprint planning went from "update everything, then log" to validate-then-write: the new `$transaction` loads all issues by ID, rejects with 404 if `issues.length !== issueIds.length` or any `projectId` differs, then updates only the rows whose `sprintId` actually changes and returns `{ success: true, changed: result }`. Duplicate IDs are rejected up front (`new Set(issueIds).size !== issueIds.length`).
- Error transport is fixed at the framework layer: `src/lib/server/api.js:56-61` only trusts `error.status` when it is an integer in 400–499 and otherwise emits `Request failed` with 500, so a Prisma or SQL message can no longer reach the client. Exercise 5D drills exactly this with a 422 and a 302.
- Verification is candid to the point of listing its own unrepaired defects: "Move activity remains outside its transaction; POST creation retains earlier relation and side-effect gaps. PATCH has no expected-version check, so concurrent editors can overwrite one another" (`VERIFICATION.md`). I confirmed both — `createIssueActivity` in `src/app/api/issues/move/route.js:70` is after the `await prisma.$transaction(...)` block, and there is no version column or `If-Match` anywhere.
- Setup is pinned and non-destructive: Node 22.16, pnpm 10.18, `pnpm install --frozen-lockfile`, a placeholder `DATABASE_URL`, and an explicit "Do not run db:reset while reproducing this review".

## Problems found (evidence required)
- **[D3]** Solutions are not kept separate from exercises. `05-PRACTICE.md` prints the answer immediately under each prompt — "**Exercise 5A: …** … The solution is to validate the type and meaning while building `updates`. A nullable relation allows only null or a trimmed nonempty string…" — which removes the point of the separate `06-SOLUTIONS-AND-REVIEW.md` answer key. A learner reading top to bottom never gets to attempt 5A.
- **[D2]** `toPosition` is validated twice with two different, drifting rules. `src/app/api/issues/move/route.js:21-23` inline-rejects non-safe-integers, and `boundedInsertAt` in `src/lib/server/issue-input.js:19-23` re-validates and clamps. The inline check allows `undefined` through, the helper maps `undefined` to 0 — two sources of truth for one field, and the course presents only the helper as "the boundary".
- **[D2]** Inside the move transaction, all sibling rows are rewritten with `Promise.all(nextOrder.map((entry, index) => tx.issue.update(...)))` (`move/route.js:50-62`). Parallel writes on one interactive Prisma transaction client are not ordered and scale as O(column size) per drag; the course calls the algorithm "designed for this small implementation" but never flags the `Promise.all`.
- **[D2]** The target-column check performs a nested query inside a boolean expression: `targetColumn.boardId !== (await tx.board.findUnique({ where: { projectId: ctx.state.project.id } }))?.id` (`move/route.js:32`). Correct, but it re-queries the board on every move and is hard to read; a named `const board = await tx.board.findUnique(...)` above would be both clearer and cheaper.
- **[D7]** The test harness is advanced for the target learner: `tests/issue-routes.test.mjs` uses `vm.SourceTextModule` behind `--experimental-vm-modules` to load real route modules with stubbed Prisma/NextResponse/identity. `04-TESTING-AND-DEBUGGING.md` explains the placement, but a junior will not be able to write a second harness like this unaided, and no simpler alternative (e.g. exporting the pure `buildUpdates` logic) is offered.
- **[D7]** No glossary. "Transaction client", "post-commit event", "sanitized status", "scoped relation", "nullish semantics", "expected-version precondition" all appear without definition.
- **[D1, minor]** `README.md` says "`boundedInsertAt` … rejects `null`, booleans, arrays, blank strings, fractions, and negatives". True, but the same file describes `parseOptionalSafeInt` as turning "optional values into `null` or safe integers" without mentioning that an **empty string also becomes `null`** (`issue-input.js:11`) — i.e. `storyPoints: ""` silently clears the field. That behaviour deserves a sentence.

## One-paragraph summary for the index
A tight, honest course built around the three bugs that break real PATCH endpoints: unvalidated field types, relations that are never checked against the caller's project, and side effects (activity rows, notifications) written outside the transaction that owns the update. The fix is small enough to read in one sitting — one new helper file, a `client = prisma` parameter on the activity writer, a `ClientError` class — and the answer key in chapter 6 walks through nine exercises naming real field names, real status codes and real values (`parseOptionalSafeInt("0")` returns 0; `boundedInsertAt(99, 2)` returns 2). Eleven tests load the actual route modules through `vm.SourceTextModule` with stubbed Prisma and are backed by a shipped log; the verification chapter volunteers what is still broken (move activity outside its transaction, no expected-version check on PATCH, POST creation untouched) instead of hiding it. Two caveats: chapter 5 prints its own solutions right under each exercise, so cover them before you read; and the VM-based test harness is more advanced than anything a junior will write unaided.
