## What Astra did well
- **The tests would have failed before the fix, and Astra proves it.** `VERIFICATION.md`: "six regression cases ran against the old socket behavior. All six failed, reproducing multi-tab presence loss, duplicate join notifications, sends without joining, identity switching on one connection, partial message writes after receipt failure, and tied-timestamp read overreach." The delivery JSON independently records `initialRegressionRun: {tests: 6, failed: 6}`. That is the red-green evidence most of these deliverables lack.
- **The rollback test uses real failure injection, not a mock.** `test/socket.test.cjs:105` creates `CREATE TRIGGER fail_receipt BEFORE INSERT ON read_receipts BEGIN SELECT RAISE(ABORT, ...) END;` and then asserts message count, room row and absence of broadcast — exactly the "protect the business effect, not the `ok` flag" standard `03-WORKED-CHANGE.md` claims for it.
- **The transaction boundary in the code matches the lesson.** `server/src/socket.js:58-70` `const saveMessage = db.transaction((state, payload) => {...})` covers insert + `updateRoom` + `markRead`, and the handler broadcasts only after it returns, with the comment "Only committed records are broadcast or acknowledged as successful." A junior can read the invariant straight off the code.
- **Limits are stated aggressively and repeatedly.** README and `VERIFICATION.md` both say the demo session is caller-controlled, that this is "a consistency repair rather than production authentication", that React effects were "source-reviewed and built; no live browser interaction test", and that sends still lack an idempotency key. The delivery JSON's `limits` array says the same five things — doc and evidence agree, with no browser claim anywhere.

## Problems found (evidence required)
- **[D2 — real, unmentioned]** `mark_read` reads then writes outside one transaction: `server/src/socket.js:132-139` runs the target lookup and the `SELECT id FROM messages …` range query *before* opening `db.transaction(() => { for (const row of rows) markRead.run(...) })`. A message inserted between the range read and the write is silently excluded from the receipt batch. This is the exact TOCTOU pattern the course teaches against three sections earlier, in the same file, and neither `03-WORKED-CHANGE.md` nor `VERIFICATION.md` mentions it.
- **[D5]** All 9 course files begin with a UTF-8 BOM (`﻿# Live chat…`). 9/9 files in this project carry it, while `j4`/`andie`/`astra2` have none — so this is a per-project artifact, not a house style. It renders as a stray glyph in several markdown viewers and breaks a literal grep for `^# `.
- **[D5]** Every command is Windows-specific PowerShell (`npm.cmd ci`, `npm.cmd run install:all`). Nothing tells a macOS/Linux learner to drop the `.cmd`, and the README does not pin Node with an `.nvmrc`/`engines` field — it only says "Use Node 22" in prose while the evidence JSON pins 22.16.0/npm 10.9.2.
- **[D7]** The prerequisite bar is genuinely mid-level despite the README's "You do not need to be a networking specialist": the learner must already be comfortable with React effects/cleanup, Socket.IO rooms and acks, SQLite transactions and `rowid` semantics. Concepts like "ordering barrier", "read-through", "tie-breaker on rowid" are used without a glossary. This is the last course in the path, not an early one.
- **[D1 — minor]** README says "The server's ordinary database remains `server/data/chat.db`" — true (`server/src/db/database.js:6`), but a populated `chat.db`, `chat.db-shm` and `chat.db-wal` are committed in the project tree, so a learner's first run is not against an empty database as the walkthrough implies. Also `client/.env` (not just `.env.example`) is present in the tree.

## One-paragraph summary for the index
This is the strongest artifact in batch B17 and belongs in the main sequence. It is real Node + Express + Socket.IO + SQLite + React code, and Astra used it to teach the three things that separate a junior from a mid-level CRUD engineer: put the whole business effect in one transaction and broadcast only after commit; never trust a client-supplied identity on an already-established connection; and know that "same timestamp" is not "same position", so your read-through and your pagination cursor need a real tie-breaker. The evidence is honest in both directions — six tests written against the *old* code all failed, thirteen pass now, and the docs say plainly that the React changes were only source-reviewed and that none of this constitutes authentication. Expect it to be demanding: you need React effects and SQL comfort before starting, and there is one leftover read-then-write race in `mark_read` that the course does not mention — finding it yourself is a good final exercise.
