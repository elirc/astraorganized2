## What Astra did well
- **The bug it fixes is real, destructive, and verifiable against the backup.** Old `server/src/routes/campaigns.js:102-104` had `catch (error) { … db.prepare('DELETE FROM campaigns WHERE id = ?').run(campaignId); }` — a Redis hiccup deleted work the user had already been told was accepted. The second bug is just as instructive: old `server/src/lib/validation.js:28` did `return res.status(400).json({...})`, which returns the truthy Express response, so every caller's `if (!data) return;` guard silently failed and the route kept executing after the 400. Both are diffable in two minutes.
- **The outbox implementation is textbook-correct, not a gesture.** `server/src/lib/outbox.js:4-12` persists the `jobId` *before* any broker call and pins `removeOnComplete:false, removeOnFail:false` with the comment "Keep IDs available for deduplication if enqueue succeeds but its acknowledgement is lost." `:34-40` marks dispatch and promotes the job in one `db.transaction`, with `WHERE queue_job_id = ? AND status = 'pending'` so a worker that already moved the row to active/completed is not clobbered. `:20` and `:62` guard overlapping ticks (`if (running …) return`) and `timer.unref()`.
- **The tests name failure windows, not functions.** `outbox.test.cjs` includes `'uncertain enqueue result retries the same ID without creating a second logical job'`, `'tracking exists before dispatch and a fast completed worker is not reset to queued'`, and `'dead-letter broker failure does not erase the durable operator record'`. These read as a specification of the at-least-once contract.
- **The biggest honesty test in the batch, passed.** Redis and Docker were both unavailable, and Astra says so in the course README itself, not buried in an appendix: "The verification environment had no running Redis service, and Docker's daemon was unavailable… This is not a claim that BullMQ worker execution or a live browser was tested." `04-TESTING-AND-DEBUGGING.md:3` repeats it ("it does not replace a real BullMQ/Redis integration test") and `07-TRACE-LAB.md:3` splits the lab into an executed half and a proposed half. The delivery JSON `limits` array matches word for word.

## Problems found (evidence required)
- **[D5]** The half of the course that demonstrates the *point* of an outbox cannot be run from the instructions given. `astraupskill/README.md` says only "start a disposable Redis service using your normal development setup", and `07-TRACE-LAB.md:25` repeats "Start Redis with your normal local development procedure". A junior on Windows without Docker — which is precisely the environment Astra itself hit — has no path: no `docker run` line, no `docker-compose.yml`, no Memurai/WSL note, no fallback. The trace lab's outage experiment, BullMQ retry observation and browser behavior are therefore unreachable for the learner as written.
- **[D7]** Topic altitude is high for the stated audience. Dual writes, dispatch intent, at-least-once delivery, job-ID deduplication, worker projection and dead-letter reconciliation are mid-level distributed-systems material. `02-CONCEPTS.md` does define its terms, but a junior who is still shaky on "why is this UPDATE in a transaction" will not get value from `'failure to mark dispatch after enqueue retains retryable intent and the same queue ID'`. Nothing in the README states a prerequisite or suggests doing the KDS course first.
- **[D5/D6 — weaker baseline than its siblings]** Only 2 of the eventual 19 tests were run against the pre-fix code (`initialRegressionRun: {tests: 2, failed: 2}`), versus 6/13 for live-chat and 11 (8 failing) for the KDS. The other 17 tests were written against the new implementation, so they are specification tests rather than regression proofs. `VERIFICATION.md` discloses the two-test baseline honestly but does not draw this distinction for the learner.
- **[D5]** Windows-PowerShell-only commands throughout (`npm.cmd ci`, `npm.cmd test --prefix server -- --test-reporter=tap`), Node pinned only in prose, no `.nvmrc`/`engines`.
- **[D5 — minor]** All 9 `astraupskill/*.md` files carry a UTF-8 BOM (`﻿# Task queue:…`).
- **[D2 — acknowledged but unmentioned in the chapters]** `outbox.js` retains every dispatched row (`removeOnComplete/removeOnFail: false` plus no delete of `queue_outbox`), so both the broker and the outbox table grow without bound. `VERIFICATION.md` concedes "Retained broker/outbox records need an operational cleanup policy", but `05-PRACTICE.md` does not make it an exercise, and it is the first thing that would hurt in production.

## One-paragraph summary for the index
The most advanced course in batch B17 and the one with the most valuable single idea: you cannot put a database commit and a call to another system in the same transaction, so you write the *intent* to your own database first and dispatch it afterwards. Astra found the textbook version of getting this wrong — a broker outage triggered `DELETE FROM campaigns`, destroying work the API had already accepted — and replaced it with a real transactional outbox with stable job IDs, safe retry on uncertain acknowledgements, and a status guard so a fast worker is not clobbered by a late dispatch mark. Nineteen tests with a retained TAP log back the application contract, and the course is refreshingly blunt that Redis and Docker were unavailable, so BullMQ execution and browser behavior were never run. That is also its main flaw as a learning artifact: the Redis half of the trace lab has no setup instructions beyond "use your normal development procedure", so plan to stand up Redis yourself. Take it as an elective after a single-database transactions course, not as a first or second course.
