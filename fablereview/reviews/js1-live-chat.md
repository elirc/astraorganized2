## What Astra did well
- The lifecycle fix is the real lesson and it is one juniors hit constantly. The backup had `const server = createServer(app)`, `wss.on("connection", async …)` and a bare `server.listen(...)` at module scope; `grep -c startRuntime backups/57/server/src/index.ts` returns **0**. Importing that module from a test would bind a port, open a LISTEN connection and leave a reconnect timer running. `stopRuntime()` now terminates sockets, closes `wss` and the HTTP server, `end()`s the listener client and clears the retry timer. `02-CONCEPTS.md` states the principle plainly: "Starting listeners at module import makes tests unexpectedly bind ports and retain database connections. Explicit lifecycle functions put those side effects under caller control."
- The validation change is a genuine correctness fix, not just tightening. `String(req.body.slug ?? "").replace(/[^a-z0-9-]/g, "-")` silently turned `"bad slug"` into a *different valid* room `"bad-slug"`; the new regex rejects it with a 400. The test asserts exactly that (`{ slug: "bad slug", name: "Room" } -> 400`) and then that a duplicate slug returns **409**, so both the coercion bug and the conflict path are covered.
- Crash-proofing is done at two layers and the course explains why they are different: `maxPayload: 16384` bounds memory at the frame level, and the per-event `typeof event.author !== "string" || typeof event.body !== "string"` guard checks protocol shape. "Parsing JSON checks syntax; checking type, author and body checks the protocol shape" is a distinction worth a junior's time.
- The integration test is honest about what it proves: it opens a real `ws://` connection, waits for the `presence` event, sends three malformed frames (`"{"`, `"null"`, `{type:"message", author:3, body:{}}`), then sends a valid message and waits for the broadcast — and finally re-reads `GET /api/rooms/study/messages` over HTTP to confirm the row actually persisted. It tests the notify->broadcast path end to end rather than asserting a mock was called.
- Verification is honest and notably *not* inflated: VERIFICATION.md says "Automated test cases: **2**" — the smallest count in the batch, stated plainly rather than padded. `batch04/logs/57-tests.log` = `# tests 2 # pass 2 # fail 0`; `browser-checks.json` shows `{"project":"57", "passed":true, "api_requests":2}`; all 16 manifest hashes match disk.

## Problems found (evidence required)
- **[D2]** The two tests are order-coupled. Test 1 creates the room with slug `"study"`; test 2 opens `ws://…/?room=study` and assumes it exists. Run test 2 alone (`--test-name-pattern "malformed socket"`) and it fails on a room that was never created. `07-TRACE-LAB.md` half-acknowledges this ("Tests may share a deliberate fixture within one suite") but the fixture should be created in `before()`, not by a sibling test.
- **[D4]** Only two tests, and neither covers the CRUD-shaped part a junior most needs: there is no test that message history paginates, that a long body is rejected at the HTTP layer, or that a disconnected client's recovery returns the right rows. The 16KB `maxPayload` and the 2000-char body bound are asserted nowhere. The lesson's centre of gravity is WebSocket/LISTEN plumbing rather than validation/ownership/transactions, which makes it the least transferable project in the batch for CRUD upskilling.
- **[D7]** This is the hardest project in the batch for a junior and the course does not ramp into it. `02-CONCEPTS.md` introduces "A database trigger produces a notification, the dedicated LISTEN connection receives it, and the process broadcasts to sockets in that room" in one sentence with no prior explanation of what `LISTEN/NOTIFY` is, why a *dedicated* connection is needed (a pooled client would be handed back), or what happens to a notification with no listener attached. The trigger itself (`server/db/schema.sql:29-44`, `notify_new_message` + `messages_notify`) is never shown in the course.
- **[D3/D1]** `07-TRACE-LAB.md` repeats one identical paragraph under all six "Boundary" headings, each pointing at `server/src/index.ts` and `connectSocket` — including Boundary 1 and 2, which describe the React client, and Boundary 5 ("The storage boundary commits or rejects"), which is the `INSERT` and the trigger, not `connectSocket`.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` gives the identical **Review:** paragraph for all four exercises.
- **[D8]** `04-TESTING-AND-DEBUGGING.md` carries the shared cross-project paragraph naming Questboard, DevDeck and Live Chat — odd here, since this *is* Live Chat, so the course refers to itself in the third person alongside two projects that do not exist in this repo.
- **[D5]** `package.json` declares all dependencies as `"latest"` with no lockfile (VERIFICATION.md discloses this). `batch04/checks.json` shows the recorded run used `node <impl>/node_modules/...` against `stage/57`, so the documented `npm install && npm test` in this folder was not itself executed.

## One-paragraph summary for the index
A chat app where messages are written to PostgreSQL, a trigger fires `pg_notify`, a dedicated LISTEN connection picks it up, and the process broadcasts to the room's WebSockets. Astra's change is mostly about testability and robustness: module-scope `server.listen()` became explicit `startRuntime()`/`stopRuntime()` so importing the app no longer binds a port or leaks a timer, malformed frames can no longer crash the connection handler, and a room slug that used to be silently coerced (`"bad slug"` -> `"bad-slug"`) is now rejected with a 400. The integration test opens a real socket, throws three malformed frames at it, then proves a valid message both broadcasts and persists. Take this one as an elective *after* the core CRUD projects: it is the batch's least CRUD-shaped lesson, it has only two tests and they are order-coupled, and the course drops `LISTEN/NOTIFY` on you in a single sentence without ever showing the trigger it depends on.
