## What Astra did well
- **The SQL change is exactly right and is the whole lesson.** The old query selected straight from `daily_metrics` with `WHERE day >= CURRENT_DATE - $1::int` (`backups/30/server/src/index.ts:34-40`), so a day with no events simply did not exist as a row — and then `AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` averaged over the *last 6 rows that existed*, not the last 6 calendar days. The rewrite builds a `calendar` CTE from `generate_series`, `LEFT JOIN`s the view, `COALESCE`s to zero, and only then applies the window functions. `07-TRACE-LAB.md` states the principle cleanly: "SQL GROUP BY only produces groups present in the input… generate_series supplies the calendar spine. LEFT JOIN keeps Tuesday, and COALESCE converts the missing aggregate to zero. Only then does a ROWS window correspond to calendar days. The order of these operations is part of correctness."
- **The off-by-one in the window bounds was fixed too**, and consistently: both routes now use `CURRENT_DATE - ($1::int - 1)` with an explicit `AND day <= CURRENT_DATE` upper bound, so `days=3` means three days, not four, in both the series and the summary. Test 1 asserts `daily.length === 3`.
- **The test is a real end-to-end SQL assertion.** `test/feature.test.ts:6-11` truncates events, inserts three purchases on `CURRENT_DATE-3 / -2 / 0`, refreshes the materialized view, then asserts the exact arrays for revenue, cumulative, moving average and delta — including the zero-filled middle day and a `null` first delta. That is the right way to test window functions.
- `asyncRoute` is a genuine fix: Express 4 does not route rejected promises to error middleware, so a DB failure in any of these handlers previously hung the request.
- **Reproducibility is the best in the batch, tied with org-explorer.** `VERIFICATION.md` "Reproduce" gives exact PowerShell for both `DATABASE_URL` and `ASTRA_TEST_DATABASE_URL`, explains why it bypasses the `db:setup` script's POSIX `$DATABASE_URL` expansion, requires pgcrypto, and describes the per-run disposable schema. `test/database.ts` refuses any database not named `astra_test_*` and strips `DROP`/`CREATE EXTENSION` from the teaching schema before loading it.
- Limits are stated where they matter: the trace lab explains that the first moving-average point is a one-day average and not a hidden seven-day warm-up, that cumulative totals reset at the window boundary, and that the first delta is null.

## One-paragraph summary for the index
The code change here is one of the two best in the batch and teaches something genuinely important: a `GROUP BY` only produces the groups that exist in your data, so a "7-day moving average" computed over rows rather than over calendar days is quietly wrong on any day with no events. The fix — a `generate_series` calendar spine, `LEFT JOIN`, `COALESCE` to zero, *then* the window functions — is the canonical answer, and the test asserts the exact revenue, cumulative, moving-average and delta arrays against a real Postgres instance in a disposable per-run schema. The setup instructions are the most followable in the batch. But do not start here: the worked fixture quoted in all seven chapters, including `VERIFICATION.md`'s "Tested behavior" section, uses numbers (10/0/20 -> 10, 5, 10) that contradict the actual test (10/0/30 -> 10, 5, 13.33), and chapter 7 contradicts itself within a dozen lines. Have someone correct the fixture first; it is a find-and-replace, after which this is core-path material.
