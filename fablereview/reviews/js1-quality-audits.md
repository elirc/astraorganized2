## What Astra did well
- The code change is a genuine reliability fix, not cosmetics. `server/src/index.ts:107-125` now holds the whole status transition inside one transaction client: `SELECT * FROM items WHERE id=$1 FOR UPDATE`, an equality guard (`if (current.rows[0].status === status) return current.rows[0];`), then the UPDATE and the `activity_entries` INSERT on that same client. An audit failure therefore rolls the status back.
- A real latent bug was found and fixed in `server/db/schema.sql`. The seed used `json_to_recordset(...) AS x(... due_date text ...)` while every JSON object supplies `"dueDate"`. `json_to_recordset` matches by key name, so every seeded due date was silently NULL. The column is now quoted `"dueDate"` and the cast is `"dueDate"::date`.
- The tests exercise the changed behaviour instead of asserting that calls happened. `test/workflow.test.ts` creates a PL/pgSQL trigger that raises on `kind='status'` inserts, asserts the PATCH returns 500, then `deepEqual`s the record and asserts a history length of 1 — a real rollback observation. Another test fires two concurrent PATCHes with `Promise.all` and asserts exactly one `status` history row.
- Test isolation is thought through. `test/database.ts` refuses any database whose name does not start with `astra_test_`, creates a per-run schema `astra_<uuid>`, strips `DROP ...`/`CREATE EXTENSION` from the teaching schema, points `DATABASE_URL` at that schema via `options=-c search_path=...` **before** importing the app, and drops the schema on close.
- Verification is honest and checkable. All 19 delivered files for stage 47 hash-match `delivery-manifest.json` `after_sha256` (I re-hashed all 190 files in this batch: 190 match, 0 mismatch). `logs/47-tests.log` reports `# tests 4 # pass 4 # fail 0`, matching "Automated test cases: **4**" in VERIFICATION.md, and `logs/47-browser.png` / `logs/47-mobile.png` back the Chromium and responsive claims.

## One-paragraph summary for the index
This course teaches one of the most valuable CRUD lessons a junior can learn: how to make a status change and its audit-trail write atomic, and how to prove it. The underlying change is real — a row-locked transaction in `server/src/index.ts`, a repeatable-read snapshot for count plus page, a calendar-date type parser, and a genuine seed bug where `json_to_recordset` silently produced NULL due dates — and the 4 delivered tests actually observe rollback by injecting a PL/pgSQL trigger. Setup needs a local PostgreSQL you create yourself, and the README omits the `CREATE DATABASE` and `pgcrypto` steps, so budget time for that. The main weakness is that the prose is a template: most of it is identical to the other nine JS1 courses with the nouns swapped, and roughly a fifth repeats inside the course itself. Do this one for the transaction and pagination lessons, but do not work through more than one or two courses from this family.
