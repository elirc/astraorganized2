## What Astra did well
- The lesson is the right one for a junior and the concepts chapter states it cleanly without hand-waving: "Authentication asks which user the request represents. Authorization asks whether that user may access this note. Finding a note by ID alone is insufficient: the owner predicate must also match. Returning the same 404 for a missing and another user's note keeps the response consistent." That last point — not leaking existence through a 403/404 split — is exactly the detail juniors get wrong, and the code does it (`findOwnedNote(id, userId)` + a single `404 "Note not found."` at `server/server.js:96`, `:115`, `:125`).
- The test proves ownership behaviourally rather than structurally: it registers two users up front (`a@example.com`, `b@example.com`), then drives every operation with each token. It does not assert "the middleware was called".
- The malformed-credential test is well chosen: `for (const password of [{}, [], 3, "x".repeat(129)])` must all 400 on register, `{email: {}, password: []}` must 401 on login (not 500), and — the nice one — `email: "A@example.com"` must still log in at 200, which is what proves normalization is applied on *both* sides rather than only at register.
- `02-CONCEPTS.md` calls out a subtlety most courses miss: "Passwords are not trimmed, because spaces are part of the user's chosen credential", contrasted with emails which are. That is a real design decision explained, not a rule recited.
- Verification is honest: `batch04/logs/56-tests.log` = `# tests 3 # pass 3 # fail 0`; the VERIFICATION table claims only build / tests / Chromium (no typecheck row — correct, this is a plain-JS project); `browser-checks.json` has `{"project":"56","passed":true,"api":"actual isolated HTTP server","api_requests":5}`; all 19 manifest `after_sha256` values match disk.

## Problems found (evidence required)
- **[D2]** The change is the least ambitious in the batch. Ownership checks, token issuance and logout revocation all **already existed** in the backup (`backups/56/server/server.js` has `findOwnedNote`, `tokens` map and the logout handler); Astra added input typing plus one new endpoint. The README Scope sentence "Owner checks protect read, update and delete; logout revokes its token" reads as new work but describes pre-existing behaviour — only the `GET /api/notes/:id` half of the read path is new.
- **[D2]** Sessions are a plain in-memory `Map` with no expiry and `scryptSync` is synchronous on the request thread. The course does disclose this ("in-memory sessions, open CORS and synchronous hashing… rate limits, session expiration… remain separate improvements"), so it is not dishonest — but it means the "secure" in the project name is doing a lot of work, and a junior gets no exposure to token expiry, which is table stakes for real CRUD auth.
- **[D3/D1]** `07-TRACE-LAB.md` has six "Boundary" headings carrying the **same paragraph six times**, each pointing at `server/server.js` and `requireAuth` — including Boundary 1 and 2, which describe the React client in `client/src/App.jsx`. `requireAuth` is not involved in serializing a form.
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` repeats one identical **Review:** paragraph under all four exercises.
- **[D8]** `04-TESTING-AND-DEBUGGING.md` carries the shared cross-project paragraph ("Questboard uses Vitest and simulated browser storage; DevDeck uses Vitest with fake-indexeddb… Live Chat also tests a real WebSocket and PostgreSQL notification"), none of which is in this repo. Outside the auth-specific sections of `02-CONCEPTS.md`, the chapter scaffolding is the same text as the six sibling JS1 courses.
- **[D5]** `package.json` declares every dependency as `"latest"` with no lockfile. `batch04/checks.json` shows verification ran `node <impl>/node_modules/vite/bin/vite.js build` and `…/tsx/dist/cli.mjs --test <stage>/56/test/notes.test.js` from Astra's shared workspace — the documented `npm install && npm test && npm run build` in this folder was never executed, and the added `"test": "node --test test/*.test.js"` relies on a shell glob that cmd.exe (npm's Windows default) does not expand.

## One-paragraph summary for the index
A small in-memory notes API that is the batch's dedicated lesson on the difference between authentication and authorization — and it teaches the part juniors most often get wrong: a note is found by `(id, ownerId)`, never by id alone, and another user's note returns the same 404 as a missing one so existence does not leak. Astra's change hardened the credential path so a JSON object or array can no longer reach `scryptSync`, made email normalization symmetric between register and login, bounded title/body, and added the missing owner-scoped single-note read. The three tests register two real users and drive every operation with both tokens, which is the right way to prove ownership. Caveats: sessions never expire and hashing is synchronous (the course says so), the "Scope" section implies ownership checks were new when they already existed, and chapter 7 repeats one paragraph six times pointing everything at `requireAuth`. Worth doing early in the path, then extend it with token expiry yourself.
