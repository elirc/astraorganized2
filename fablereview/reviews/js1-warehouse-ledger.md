## What Astra did well
- This is the most valuable change in the batch and it fixes a defect the backup really had. Before: `POST /api/movements` opened a transaction, called `balanceOf(...)` (a plain `SUM(delta)` read) and inserted if the balance sufficed — two concurrent requests both read 40 and both spent 30. After: `lockProduct(client, input.productId)` takes a row lock first, and the comment in `server/src/index.ts:~309` explains *why* the lock is on the product and not the warehouse: "This also serializes opposing transfers without taking warehouse locks in different orders" — i.e. deadlock avoidance by consistent lock ordering, stated plainly.
- The concurrency test is a real one, not a mock: `test/ledger.test.ts:47` fires `Promise.all([...])` of two `delta: -30` issues against 40 on hand and asserts `results.map(r => r.status).sort()` deep-equals `[201, 400]`, then reads `SUM(delta)` from the database and asserts it is exactly `10`. Either request may win; the invariant is what is asserted.
- The transfer test injects a `BEFORE INSERT` trigger that raises on the credit leg (`reason = 'force failure'` and `delta > 0`), asserts a 500, asserts the movement count is *unchanged* (so the debit rolled back too), then removes the trigger and asserts a real transfer leaves total stock conserved. That is a genuine atomicity proof.
- Validation went from "coerce and hope" to "reject": `Math.trunc(Number(data.delta))` became `typeof delta !== "number" || !Number.isInteger(delta) || delta === 0 || Math.abs(delta) > 2147483647`, and the bound is explicitly tied to the SQL `integer` column. `parseReason` rejects a non-string instead of `String(undefined)`-ing it, and `isUuid` stops a malformed id reaching the query.
- The course prose is genuinely about *this* domain. `02-CONCEPTS.md` opens "An append-only ledger represents corrections with new entries. Receiving 10 adds +10; issuing 3 adds -3; the balance is 7… Deleting a movement to correct a mistake would erase the explanation of how stock arrived at its current value" — first-principles, project-specific, and it correctly separates "a transaction" from "a lock", which is exactly the confusion this lesson exists to fix.
- Verification is honest: `batch04/logs/55-tests.log` = `# tests 3 # pass 3 # fail 0`, build/typecheck/browser entries all present, and all 18 manifest `after_sha256` values match the files on disk.

## One-paragraph summary for the index
Do this one. A warehouse stock ledger where the balance is `SUM(delta)` over an append-only movements table, and where the original code let two concurrent issues both spend the same stock because it read the balance without holding a lock. Astra's fix takes a `FOR UPDATE` row lock on the *product* before every read — chosen deliberately so that opposite transfers can never acquire warehouse locks in conflicting orders — and the three tests prove it the right way: two simultaneous `-30` issues against 40 on hand must come back `[201, 400]` with a final balance of exactly 10, and an injected failing trigger on the credit leg of a transfer must leave the movement count unchanged. The concepts chapter is written for this domain rather than assembled from a template, and every claim I checked (line 311, the seed value of 40, the `Number.isInteger` rule, the three test counts) matched the code and the batch logs. The only real weakness is chapter 7, whose six "boundaries" repeat one paragraph and all point at the same function — read the source and the test file instead.
