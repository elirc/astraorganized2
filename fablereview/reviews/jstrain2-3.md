## What Astra did well
- The first working session in `astraupskill/README.md` is the single best junior exercise in this batch: create a number property with value `0` and an unchecked checkbox, export, find `0` and `false`, then "Explain why code such as `value || \"\"` would hide both, while `value ?? \"\"` preserves them. This small example connects JavaScript truthiness, HTML form behavior, JSON types and database persistence." The code backs it up — `src/components/DatabaseBlock.js:137,152` use `row.values[prop.id] ?? ""`.
- It teaches the distinction juniors most often miss — rendered vs. committed: "The reload matters: a value on screen alone proves only that React rendered it, not that a transaction committed it."
- The save-session tests are genuinely hard-won behavior, not smoke tests. `test/session.test.mjs` includes "typing while a save is in flight remains a newer unsaved draft", "a stale write retains its draft and cannot automatically retry before review", "a lost response can be reconciled as already accepted without repeating the write", "failed local persistence warns separately and does not turn an accepted server save into failure", and "review refuses to merge drafts into a different server workspace instance". Those are the real failure modes of an autosaving editor.
- The browser evidence is real and self-limiting: a Playwright/Chromium harness that boots the production Next server on a temporary loopback port against a throwaway SQLite file, with 25 named workflows including "real two-tab stale write refused with local draft retained" and "one tab acceptance does not clear another tab retained IndexedDB draft". VERIFICATION states the harness "never opens the original project's user database" and that "A failing harness run is retained as diagnostic evidence rather than counted as a passing workflow."
- It admits finding and fixing a bug *during* verification: "a later run exposed a real stale save-status bug when a view was changed back to the already accepted setting. That behavior was fixed and added to the Node regressions before the final run." The intermediate logs in `checks/jstrain23/` corroborate this (`backend-02.log`: `# tests 95 / # pass 94 / # fail 1`, then `backend-03.log`: 95/95, then `final-01.log`: 97/97).
- Exercises escalate properly and each carries acceptance criteria, ending with two deliberately senior ones (durable operation receipts for imports; extracting one resource out of the JSON document into relational tables) that are clearly labelled "exercises for you to implement ... They are not claims that the features already exist."

## Problems found (evidence required)
- **[D4]** There is **no TypeScript anywhere** — `find . -name "*.ts" -o -name "*.tsx"` returns nothing outside `node_modules`; the project uses `jsconfig.json` and `.js`/`.mjs`. Half the target curriculum is TypeScript, and the course's own concepts (typed record properties, schema validation, contract changes) are exactly where TS would pay off. The course never mentions the absence or suggests a typing exercise.
- **[D7]** 7,441 words with no per-chapter time estimates (compare meterforge, which gives 60–90 min per chapter). `02-CONCEPTS.md` alone is 1,050 words of dense prose covering identity, relationships, draft vs. accepted validity, transactions, revisions and conflict review.
- **[D7]** Exercises 5–6 (`05-PRACTICE.md`) — design an idempotency/receipt protocol with fingerprinting and retention policy, and migrate one resource from the JSON document into relational tables — are senior work. `06-SOLUTIONS-AND-REVIEW.md` (841 words for six exercises) gives design outlines and reviewer questions, not solutions, so a junior stuck on #5 has no way forward.
- **[D2, minor]** `scripts/browser-check.py` packs 25 workflow assertions into 128 lines using semicolon-chained one-liners (line 83 is a single line containing an `assert`, an `expect(...).to_have_value(...)` and a `passed(...)` call). The course points learners at this harness as the model for browser verification; it is close to unreadable and unmaintainable as written.
- **[D2, minor]** `scripts/setup.mjs` accepts both `node scripts/setup.mjs "Owner"` and the README's `npm run setup -- --owner "Learner"` only because of a one-line alias (`if (args[0] === "--owner" && args.length === 2) args.shift();`), while the script's own usage string documents neither `--owner` form. A learner who mistypes gets a usage message that does not match the README.
- **[D3, minor]** The pre-existing `_learning/` tree (architecture notes, glossary, per-file guides) is preserved but its claims now describe the old implementation; the course says original text is "historical reference", yet a learner browsing the repo will hit `_learning/guides/src/lib/workspaceStore.js.guide.md` with no in-file marker that it is stale.

## One-paragraph summary for the index
The strongest JavaScript course in this batch and the one that best captures what makes real CRUD hard on the front end: the gap between what React has rendered, what the user has typed, what IndexedDB has kept and what SQLite has actually committed. It runs on a genuine Next 16 workspace app with bearer auth, whole-document schema validation and revision-checked atomic writes, and the save-session tests read like a catalogue of every autosave bug you will ever ship — stale writes, lost responses, drafts from a different workspace, a failed local save masquerading as a failed server save. The evidence holds up completely: 97 Node tests match the run log file by file, 25 named Playwright workflows drive the production server against a throwaway database, and Astra reports a bug the harness found late and the regression it added for it. The weak spots are level and language: the last two exercises are senior design work with only outlines for answers, there are no time estimates, and the entire project is plain JavaScript with no TypeScript at all — so pair it with a TS course rather than treating it as the whole JS/TS half of the path.
