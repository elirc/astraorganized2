## What Astra did well
- The lesson is precisely targeted and correct for a TypeScript codebase: types vanish at runtime, so a store setter reachable from a form, a stale tab or a browser extension needs guards. The doc comment in `src/lib/deliveryValidation.ts:23-25` says it in one sentence — "Keep persisted proof data bounded and structurally safe even when a caller is JavaScript, a stale form, or a browser extension rather than TypeScript."
- The two mutations are treated differently and the distinction is justified: an unknown *domain choice* is rejected (`recordFailure` returns `false` and writes nothing), while malformed *optional* fields are dropped and the delivery still records. `VERIFICATION.md` states the rule explicitly — "Optional malformed fields are dropped; invalid domain choices are rejected."
- The new store test asserts the whole state transition, not just a return value: `tests/store.test.ts` checks `stopOf(store, other).status` is still `'pending'`, that `log(store)` still has length 1 after a rejected failure, and that a 700-character note is stored at exactly 500 in **both** the stop proof and the activity event — proof/event parity, which is the kind of thing that silently drifts.
- `evidence.json` is machine-readable and unusually disciplined: per-gate command arrays, `exitCode`, `elapsedSeconds`, log paths, and a `counting` field that says "typecheck, lint and build are additional gates, not added to the case count" — i.e. it refuses to pad the 222.
- Failures during the work are reported rather than hidden. `VERIFICATION.md` §"Build correction and earlier failures": a Turbopack run failed on an extended Windows dependency path in the PostCSS transform, a webpack attempt then exposed a TypeScript narrowing error in the new validator, which was fixed; and the chapter links the official Tailwind `source()` documentation for the fix it chose.
- It declines to overclaim reproducibility: "The final verification used the installed staged dependencies; it does not claim a separately captured clean pnpm install."
- Practice is prediction-first and ends in design: exercise 2 asks the learner to write the expected sanitizer output for `{ method: 'door', recipientName: '  Jo  ', note: ' ', photo: 'blob:camera' }` *before* running anything, and exercise 6 asks them to re-express the same contract as a server route with a schema parser.

## Problems found (evidence required)
- **[D2]** An existing test was weakened. `tests/store.test.ts:488-492` previously did `const mod = await import('@/store/useAppStore'); const big = 'x'.repeat(mod.PHOTO_BUDGET_BYTES - 100)`; it now hardcodes `'A'.repeat(1_499_960)`. The test no longer tracks `PHOTO_BUDGET_BYTES` (`useAppStore.ts:520` = `1_500_000`), so changing the budget will silently stop testing the boundary. The rewrite was necessary — the sanitizer rejects the old `'x'.repeat(...)` string because it is not a data URL — but the constant should have been kept.
- **[D2]** The photo pattern is stricter than real data URLs. `deliveryValidation.ts:39` uses `/^data:image\/[a-z0-9.+-]+;base64,[a-z0-9+/]+=*$/i`, which rejects any base64 payload containing a newline or whitespace (legal in some encoders) and any non-base64 data URL. The user-visible effect is a silently missing delivery photo, with `recordDelivery` still returning `ok: true`. Nothing in the course lists this as a limit; `VERIFICATION.md` only says image checks "validate data URL structure and size policy, not decoded pixels, MIME truth or media safety".
- **[D2]** The delta is small relative to the app: one new 48-line file, ~8 changed lines in the store, one CSS line, one new 3-test file. The batch's headline "222 tests" is almost entirely pre-existing coverage that Astra re-ran, not coverage it created — `evidence.json` is honest about the counting method but the number still reads bigger than the contribution.
- **[D4]** Everything is client-side. Persistence is `localStorage` via zustand; there is no server route, no database, no transaction, no ownership or authorization anywhere in the lesson. `05-PRACTICE.md` exercise 6 ("Sketch how the same contract would be enforced in a server route with a schema parser") is the only server content and it is a paper exercise with no solution code.
- **[D3]** Only four code blocks across nine chapters (`grep -c '```'` gives 2 in each of 02, 03, 06, 07 and **0** in 01, 04, 05, README). Chapter 04 ("Testing and debugging the boundary", 530 words) contains no test code at all.
- **[D1/D2, cosmetic churn]** `README.md` appears in the diff as a 165-line replacement, but `diff <(tr -d '\r' old) <(tr -d '\r' new)` reduces to **four appended lines**. Astra rewrote the file's line endings, hiding a four-line change inside a whole-file diff. The same happened in `aiheartbeat` in this batch.
- **[D7]** No glossary; "runtime guard", "boundary", "proof/event parity", "data URL", "narrowing" are used as known terms. A junior will also need the `as never` / `as unknown` cast trick in exercise 3 explained, which chapter 05 mentions only in passing ("values TypeScript would reject").

## One-paragraph summary for the index
A small, sharp lesson on the gap between TypeScript types and runtime values, taught on a real app rather than a toy. Astra added one 48-line guard module and wired it into two zustand mutations so that an unknown failure reason is rejected before any write, while malformed optional proof fields are trimmed, bounded and dropped — and the course is careful to explain why those two policies differ. The verification record is a model: a machine-readable `evidence.json` with per-gate commands, exit codes and durations, an explicit note that typecheck/lint/build are *not* counted among the 222 cases, and a frank account of a Turbopack build failure and the TypeScript narrowing bug the fix exposed. Two things to know before you pick it: the contribution is genuinely small next to the 222 mostly pre-existing tests, and the whole exercise is browser-local, so you practise input validation and state transitions but never touch a server, a database or authorization — chapter 5's last exercise asks you to design that yourself, with no solution provided.
