## What Astra did well
- The security fix is real and is the single most valuable CRUD lesson on the JS/TS stack. Before: `const organizationId = String(request.headers["x-organization-id"] ?? "")` — an attacker-controlled header used directly as a scope, and `prisma.lessonProgress.update({ where: { enrollmentId_lessonId: ... } })` with **no ownership check at all**. After: `organizationFor()` throws 403 unless `request.user.memberships` contains that org, and every route re-reads the enrollment with `findFirst({ where: { id, userId, organizationId } })`.
- The version-selection bug is subtle and correctly diagnosed. The old enroll route took `versions: { orderBy: { versionNumber: "desc" }, take: 1 }` — i.e. the *newest* version, draft or not. The new code requires `course.status === "PUBLISHED"` **and** `courseVersion.id === course.currentVersionId` **and** `courseVersion.status === "PUBLISHED"`. `02-CONCEPTS.md` names all three conditions and why: "This prevents a stale pointer, a draft pointer, or a version from another course from being enrolled."
- The transactional-outbox threading is done the right way: `recordDomainEvent(input, client: Prisma.TransactionClient = prisma)` and `auditLog(input, client = prisma)` keep every existing call site working while letting the routes pass `tx`, so the `DomainEvent` + `OutboxMessage` rows commit with the business write. The course explains why the argument matters instead of just showing it.
- `isCourseComplete` now distinguishes an explicit empty requirement list from an omitted one, and the course explains the JavaScript trap precisely: "If a future author changes parsing to coalesce every empty array to `undefined`, a no-assessment course silently becomes assessment-bound. Keep a test for both forms next to any parser change." The route-level derivation (`learner.routes.ts:377-379`) matches that description line for line.
- The honesty about what mocked tests prove is exemplary and appears in the README, not buried: "A passing mock test therefore demonstrates control flow and call grouping; it does not prove rollback, concurrent uniqueness, generated SQL, or production delivery of an outbox message."
- Exercises are prediction-first with concrete inputs and an explicit instruction to "Record the result before opening the answer key", and Exercise 8 asks the learner to "Name two claims the mock suite cannot prove" — teaching evidence literacy, not just the feature.

## Problems found (evidence required)
- **[D2]** The transaction claim is the weakest part of the evidence. In `learner.routes.test.ts` the transaction client is `const tx = new Proxy(prisma, { get: (target, property) => target[property] })` and `$transaction` is `vi.fn(async (callback) => { calls.transaction++; return callback(tx); })` — the "transaction" is literally the same mock object, so nothing about atomicity, rollback or isolation is exercised. The tests assert `calls.transaction === 1`, i.e. that `$transaction` was *called*. VERIFICATION discloses this, but it means the headline claim ("Groups learner mutations with transaction-client events/outbox writes") rests on call-shape assertions only.
- **[D3]** All nine exercises are predict-and-explain; none asks the learner to write code or a test. Compare `campusops/astraupskill/05-PRACTICE.md`, where each exercise ships an "Acceptance:" contract for a change the learner implements. `05-PRACTICE.md` here is 362 words while `06-SOLUTIONS-AND-REVIEW.md` is 1,982 — 36% of the course is the answer key.
- **[D7]** 417 words of `01-CODEBASE-MAP.md` for an npm-workspaces monorepo with four packages, a Prisma schema, Express middleware, Zod validation and a Next 15 front end. There is no time estimate per chapter and no glossary (transaction client, outbox, IDOR, tenancy, `P2002` are all used before being defined).
- **[D4, scope]** Despite the `next` entry in the stack list, the course never touches `apps/web` or `apps/worker`. Both are configured with `vitest run --passWithNoTests` (`apps/web/package.json:10`, `apps/worker/package.json:10`) and VERIFICATION correctly reports "Web and worker commands completed with passWithNoTests and found zero test files. They contribute zero cases and provide no UI/worker behavioral coverage." Honest, but a learner expecting Next.js content will not find any.
- **[D2, minor]** The `P2002` handler catches only the enroll route's duplicate; the error is matched by `(error as { code?: string }).code === "P2002"` rather than by `Prisma.PrismaClientKnownRequestError`, so any thrown object carrying a `code` field would be mapped to 409. Small, but the course teaches this snippet as the pattern.

## One-paragraph summary for the index
The best JS/TS course in this batch and the right one for learning multi-tenant authorization in a Prisma/Express API. The delivered change fixes a textbook set of IDOR holes — an `x-organization-id` header trusted without checking the actor's memberships, a lesson-progress update with no ownership filter at all, and an enroll route that picked the newest course version even when it was a draft — and then groups each learner mutation with its audit and outbox rows under one `prisma.$transaction` client. Everything the course says about the code is accurate down to individual lines, the 29 tests exist on disk and match the logs, and the README states up front that mocked-Prisma tests prove control flow and call grouping but not rollback, uniqueness races or outbox delivery. Two caveats: the nine exercises are all predict-and-explain with no code to write, and the transaction fixture is a proxy over the same mock object, so the atomicity claim is the least-evidenced part of an otherwise well-evidenced delivery. Expect to supply your own integration test against a real Postgres if you want to trust the transaction boundary.
