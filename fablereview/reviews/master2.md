## What Astra did well
- This is the biggest and best-targeted change in the batch. It fixes three separate real defects, not one: (a) `payments.routes.ts:17` listed payments with `OR: [{ organizationId: tenant.organizationId }, { organizationId: null }]` — an unscoped-row leak, now `organizationId: tenant.organizationId`; (b) the old webhook did `tx.payment.update({ where: { id: body.paymentId } })` with **no tenant predicate**, so any tenant could settle any payment by id; (c) `app.ts:58-62` decided HTTP status by `message.includes("Missing permission")`, which is exactly the fragile pattern a junior should learn to stop writing.
- The error model is the right shape: `DomainError(category, code, message)` in `packages/domain/src/errors.ts` with zero Express dependency, mapped to 400/403/409 by `apps/api/src/shared/errors.ts`, everything else sanitized to a 500 `"Internal server error."`. The readiness probe also stopped echoing raw exception text (`app.ts:48`).
- The monotonic-success rule is genuinely well thought through and well taught: `alreadySucceeded && !succeeded` still records an audit row (`payment.failed.ignored`) but skips the payment/invoice update *and* the outbox emission (`payments.service.ts:85-113`). `03-WORKED-CHANGE.md` explains why — "an informational late notification cannot undo a financial success".
- The route suite is not a mock-everything suite: `payments.routes.test.ts` composes a real `express()` + `express.json()` + the real `errorMiddleware` and sends a truncated JSON body over `fetch`, because as `04-TESTING-AND-DEBUGGING.md` says, "a service test cannot exercise `express.json()`". That distinction is worth teaching.
- Verification honesty is excellent and specific: "Prisma transaction callbacks are mocked in the service tests. They prove calls, arguments, decisions, and retry limits, but cannot prove PostgreSQL rollback, concurrent serialization, row locks, or durability." The delivery `limits[]` additionally admits "Subscription idempotency and count-based invoice numbering retain pre-existing race risks" — i.e. it names bugs it did *not* fix.

## Problems found (evidence required)
- **[D2]** No test touches a database. The delivery's own `testResults.scope` says "No live database or provider", and `VERIFICATION.md` reproduces with `$env:DATABASE_URL = "postgresql://test:test@127.0.0.1:65432/unused"`. The three headline properties — Serializable isolation, atomic rollback of payment+invoice+audit+outbox, and the retry actually resolving contention — are each asserted against a `vi.fn()` that resolves the callback. `it.each(["P2002","P2034"])("bounds %s contention retries...")` at `payments.service.test.ts:160` proves the `for` loop counts to two, nothing more.
- **[D2]** The webhook's authorization model is never questioned. `payments.routes.ts:28` calls `processMockPaymentWebhook(assertPermission(request, "payments:manage"), request.body)`, and `assertPermission` resolves the tenant from demo `x-organization-slug`/`x-user-email` headers (`shared/auth.ts:29`). So the tenant scoping the fix relies on is *self-asserted by the caller* — for a webhook, that is the untrusted party. The course calls the provider "synthetic" and says there is "no real signature verification", but never states that in production the tenant must be derived from the signed payload, not from a header. A junior could carry this pattern forward.
- **[D3]** Solutions are inlined into the teaching chapters even though a dedicated `06-SOLUTIONS-AND-REVIEW.md` exists. `01-CODEBASE-MAP.md`: "Exercise: mark each operation above as read, state write, or side effect. **Solution:** reads are identity/payment/invoice…". Same pattern in `02-CONCEPTS.md`, `03-WORKED-CHANGE.md` and `04-TESTING-AND-DEBUGGING.md`. The learner cannot attempt those four without reading the answer in the next sentence.
- **[D7]** `06-SOLUTIONS-AND-REVIEW.md` is 1,770 words — over a third of the course — and chapters assume comfort with `vi.hoisted`, Prisma `tx` clients, workspace build ordering and payload hashing. The course README concedes it "gradually asks mid-level questions". Real, but it is at the top of the difficulty range for the target learner.
- **[D5]** The reproduce block never boots the app or a database. There is no `docker compose`, `prisma migrate`, seed, or port; the learner can only run `verify`. The course argues this is deliberate, but it means every scenario in `05-PRACTICE.md` is executed only as a unit test.
- **[D1, minor]** Typography glitches in the generated prose: `02-CONCEPTS.md` "maps its validation, forbidden and conflict categories to HTTP400,403 and409"; `03-WORKED-CHANGE.md` "require an separate disposable PostgreSQL test database".

## One-paragraph summary for the index
The most substantial course in this batch, and the closest to what a junior actually needs for payment-shaped CRUD: idempotency keyed on a provider event id *plus* a payload hash, tenant predicates on every read, a legal-transition guard before writing, a rule that a late failure never un-pays an invoice, and a typed `DomainError`/`HttpError` hierarchy replacing an error handler that chose HTTP status codes by substring-matching exception messages. The bugs it repairs are real — the previous webhook updated `payment` by id with no organization filter at all — and the 30 tests assert query predicates and the *absence* of writes rather than just status codes. Its honest weakness, which it states itself, is that Prisma is mocked throughout, so Serializable isolation, rollback and the retry loop are described but never demonstrated. Budget a full day, read `02` and `03` twice, and treat the webhook's header-based tenant resolution as a teaching fixture rather than a pattern to copy.
