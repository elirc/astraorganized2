## What Astra did well
- The diagnosis is exactly right and stated in business terms: the old adapter called `_events.TryAdd(...)` and **discarded the boolean**, so under a race both callers returned their own freshly-generated event as a creation — "Storage contained one event, while responses could claim two different events existed" (`03-WORKED-CHANGE.md`). The non-concurrent half of the bug (same key, changed quantity, silently returning the old event as success) is called out as the more dangerous one: "A billing client could think quantity 11 had been accepted when storage still held quantity 10."
- Two genuine ASP.NET Core behaviors are taught correctly, not hand-waved. `Program.cs` now registers the header inside `context.Response.OnStarting(...)` with the comment "Error handling may clear headers before writing its response", and moves `app.UseExceptionHandler()` *after* that middleware; separately `AddProblemDetails(options => options.CustomizeProblemDetails = ...)` forces the body's `traceId` to equal the header. The API test asserts equality rather than mere presence: `Assert.Equal(problem?["traceId"].ToString(), conflict.Headers.GetValues("X-Trace-Id").Single())` (`tests/MeterForge.Api.Tests/Usage/UsageApiTests.cs:41`).
- Normalization-vs-identity is handled with unusual care. `UsageEvent`'s constructor trims `Meter` and `ExternalEventId` and converts `OccurredAt` to UTC but leaves `TenantId` raw; `02-CONCEPTS.md` states precisely that and warns "Do not normalize every string indiscriminately: two case-sensitive external identifiers can be different resources."
- `VERIFICATION.md` reports failures it found *during* verification ("The new integration test first exposed a missing trace header on handled errors ... it exposed a second mismatch"), records an environment restore failure and refuses to count it ("It is not counted as a passed test"), and volunteers a performance weakness Astra introduced ("GET by internal event ID scans the memory collection; no performance target is claimed").
- Best pedagogy in the batch. The README route table gives per-chapter time estimates (60–90 min, 4–6 h for practice), prescribes a four-column notebook — "prediction, observation, explanation, next check" — and states the standard directly: "An unexplained passing test is weaker evidence than a failed prediction that you can now explain accurately." `02-CONCEPTS.md` includes a five-row prediction table the learner must answer before reading the right-hand column.
- Exercises are real engineering with stated acceptance criteria and traps: exercise 2 makes the learner justify a length limit and warns "C# `string.Length` is not a count of user-perceived characters"; exercise 3 warns "Blindly generating a new UUID in a catch block loses the server's deduplication guarantee"; exercise 4 requires deterministic tie-breaking for equal timestamps and "pagination does not depend on dictionary iteration order".

## Problems found (evidence required)
- **[D2, minor]** `IUsageEventStore.FindByExternalIdAsync` survives on the interface (`src/MeterForge.Application/Usage/UsageIngestionService.cs:8`) but is no longer called by any production code — only by two assertions in `tests/MeterForge.Application.Tests/Usage/UsageIngestionTests.cs:26,70`. It is now a test-only seam on a production contract, and the course does not mention the leftover.
- **[D2, minor]** `InMemoryUsageEventStore.FindByIdAsync` does `_events.Values.FirstOrDefault(...)` — an O(n) scan on the new GET route. Disclosed in VERIFICATION's limits, but no exercise asks the learner to add the secondary index, which would be a natural and short follow-up.
- **[D4, minor]** Nothing here touches a database: the exercised store is a `ConcurrentDictionary`, and the PostgreSQL adapter is explicitly out of scope ("The PostgreSQL invoice adapter is a separate teaching boundary and does not make usage ingestion durable"). The `GetOrAdd` lesson maps onto `INSERT ... ON CONFLICT DO NOTHING RETURNING *`, but the course never draws that line.

## One-paragraph summary for the index
Start here for idempotency. MeterForge takes one endpoint — record a usage event — and uses it to separate four ideas a junior usually blurs together: entity identity vs. request identity, validation vs. normalization vs. equality, "this store is thread-safe" vs. "this operation is atomic", and "the query is tenant-scoped" vs. "the caller is authorized." The delivered fix is a textbook check-then-act race repair (`TryAdd` with a discarded boolean becomes `GetOrAdd` returning the stored winner), plus a payload-mismatch 409 that stops the server from silently accepting a changed retry, plus two real ASP.NET pipeline bugs around trace correlation that the integration tests caught during verification and that the course then teaches. Every claim checked out against the source, the 51-test count matches the TRX files suite by suite, and the limits section volunteers weaknesses including an O(n) scan Astra introduced. The only real gap is that no database is ever involved, so you learn the pattern in a `ConcurrentDictionary` and have to transfer it to `ON CONFLICT` yourself.
