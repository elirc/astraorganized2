# MissionControl / FleetCommand — Fable review

- **Path:** `missioncontrol`  ·  **Wave:** 2  ·  **Stack:** .NET 10 ASP.NET Core + Blazor + **EF Core** + SQLite (WAL), multi-workspace via global query filters  ·  **Batch:** B10
- **Astra's change (one line):** Made `TaskService.UpdateAsync`/`CreateAsync` validate-then-mutate inside an EF-owned `IsolationLevel.Serializable` transaction: a supplied title is rejected when it trims to empty, a supplied `ProjectId` is resolved through the workspace-filtered `db.Projects` query (so a foreign or non-existent project is a domain error instead of a silently persisted FK), `req.Tags`/`req.Metadata` are serialized into locals *before* any tracked entity is touched so a `JsonException` cannot leave a scoped `DbContext` dirty, project ticket numbers are allocated inside the transaction with `CommitAsync` before bus publication, plus a forward EF migration for thirteen entities that were in the model but missing from the snapshot, and test-host isolation (`DisableTestParallelization`, `FC_DISABLE_SCHEDULER=1`).
- **Course size:** 5,136 words across 9 files  ·  **Tests claimed:** 139 across 2 suites  ·  **Tests found on disk:** 139 (ApiTests 26 `[Fact]`; UnitTests 26 `[Fact]` + 12 `[Theory]` with 79 `[InlineData]` + 1 `[MemberData]` set = 113)

## What Astra did well
- This is the only project in the batch where the lesson runs on a **real ORM against a real database**, and the EF Core statements are technically correct where most courses get them wrong. `VERIFICATION.md`: "EF change tracking and a SQL transaction are separate mechanisms ... A rollback alone does not reset tracked properties, and an event bus is not a durable outbox." That single paragraph is worth more than most of the prose in this batch.
- The authorization/validation boundary is drawn precisely and is true of the code: `02-CONCEPTS.md` says `RequireAuthorization("Operator")` "does not guarantee a title is non-empty or a project belongs to the workspace. The service must enforce those invariants because other callers, such as orchestration, may invoke it without the HTTP route" — and `DispatchEngine.cs` does indeed call the service directly.
- The workspace-scoping fix is real and subtle. The old code did `if (req.ProjectId is not null) task.ProjectId = req.ProjectId;` — an unvalidated FK write. The new code resolves the project via `db.Projects.FirstOrDefaultAsync(...)`, which picks up `modelBuilder.Entity<Project>().HasQueryFilter(e => e.WorkspaceId == _workspace.WorkspaceId)` (`FleetDbContext.cs:141`), so a cross-workspace id is invisible. The course names exactly this mechanism: "This is stronger than checking only global id existence."
- The concurrency evidence is genuine, not a mock. `Concurrent_creates_and_moves_share_one_ticket_sequence` (`tests/FleetCommand.ApiTests/ApiTests.cs:237`) fires two `POST /api/tasks` and two `PUT /api/tasks/{id}` in parallel against one project and asserts `Assert.Equal(new long[] { 1, 2, 3, 4 }, tickets)` plus a persisted `ticketCounter` of 4 — over real HTTP, through the real pipeline, into real SQLite.
- The "dirty DbContext" scenario is the best-designed regression in the whole batch: an invalid update is attempted and then an unrelated valid save is performed **on the same scoped context**, with the original title kept as an independent copy "so an assertion cannot accidentally compare a mutated entity with itself" (VERIFICATION.md). That is a failure mode most senior engineers never think to test.
- Honest about what it did not do, in EF-specific terms: "ProjectId remains nullable without presence tracking: omitted and explicit null both preserve the assignment; clearing a project is not implemented", "no cross-request optimistic concurrency token was added", "migration of an existing production dataset was not performed".

## Problems found (evidence required)
- **[D7]** The course is thin relative to the codebase. `01-CODEBASE-MAP.md` is 435 words and `02-CONCEPTS.md` 458 words for an application with Blazor UI, an orchestration engine, an LLM dispatcher, webhooks, a scheduler and ~13 entity types. There is no reading-order table with time estimates (compare `meterforge/astraupskill/README.md`, which gives 60–90 min per chapter), and `07-TRACE-LAB.md` is 335 words.
- **[D3]** The single mechanism that makes the concurrency claim true is never explained. `SqlitePragmaInterceptor.cs:10` sets `PRAGMA journal_mode=WAL; ... PRAGMA busy_timeout=5000;`, and `BeginTransactionAsync(IsolationLevel.Serializable)` on Microsoft.Data.Sqlite issues `BEGIN IMMEDIATE`. Without the busy timeout the four parallel writers in the test would produce `SQLITE_BUSY`. The course says "explicit non-deferred SQLite transaction" (`02-CONCEPTS.md:3`) but never mentions WAL, `busy_timeout`, `BEGIN IMMEDIATE` or what a junior should expect when the lock wait expires.
- **[D7]** The README is a single unbroken block of six paragraphs with no headings and opens mid-thought ("Keep a concrete ledger while reading: request body, actor, workspace id, tracked entity, SQL outcome, response JSON, and emitted event"). A junior has to already know the domain to parse the first sentence.
- **[D2, minor]** `UpdateAsync` now duplicates parsing logic: `ValidateUpdateRequest` parses priority/status/due date and then the mutation block parses them again (`TaskService.cs:~115` and `:149`). It is correct but it is two sources of truth for the same rule — exactly the thing the course warns about elsewhere ("Do not create a second conflicting validation rule in the endpoint" is the analogous warning in meterforge).
- **[D2, minor]** An invalid update now leaves the scoped `DbContext` clean only for the cases tested (validation and serialization). If a *database* write fails mid-`SaveChangesAsync`, tracked entities stay mutated; VERIFICATION says so ("A failed database save requires appropriate context disposal/recovery") but no exercise makes the learner see it, so the safest habit (dispose the scope after a failed save) is stated rather than practiced.

## One-paragraph summary for the index
The one course in this batch that teaches CRUD on a real ORM against a real database, and it is precise about the things EF Core beginners get wrong: change tracking is not a transaction, rolling back SQL does not un-mutate your tracked entity, a global query filter is stronger authorization than an existence check, and a nullable DTO property cannot express "clear this field." The delivered change closes a real hole — an unvalidated `ProjectId` write that could point a task at another workspace's project — and wraps ticket-number allocation in a serializable transaction that is proven by four parallel HTTP requests asserting the sequence 1,2,3,4 in real SQLite. All 139 tests exist on disk and match the TRX counters suite by suite, and the limits section is written in EF vocabulary rather than marketing. Its weakness is size: 5,100 words is thin for an app this large, the map and concepts chapters are under 500 words each, and the SQLite WAL/`busy_timeout`/`BEGIN IMMEDIATE` machinery that actually makes the concurrency lesson work is never explained. Do it after MeterForge, and read `FleetDbContext.cs` and `SqlitePragmaInterceptor.cs` yourself alongside chapter 02.
