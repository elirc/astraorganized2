# .netpastebin (Paste workspace) — Fable review

- **Path:** `_Organized Desktop/01 Net Workspaces/.netpastebin`  ·  **Wave:** 2  ·  **Stack:** .NET 10 minimal API (ASP.NET Core) / JSON-file persistence / React 19 + Vite (JSX) / node:test + bespoke .NET console harness + Python HTTP & Chromium checks  ·  **Batch:** B09
- **Astra's change (one line):** Rebuilt the paste API and UI around explicit command contracts — capability edit keys with generated receipts, optimistic concurrency via a required quoted `If-Match` version (428 when absent, 412 on mismatch), durable `Idempotency`-style creation-request receipts so a lost acknowledgement can be retried exactly once, and a cooperating-process file lease with same-directory temp-file replacement so a failed write cannot truncate previously accepted data — plus a React layer that *retains* the user's draft on conflict and offers an explicit "Check current version" / "Use reviewed current version" review step.
- **Course size:** 5,845 words across 9 files  ·  **Tests claimed:** 76 (15 client + 30 backend + 17 HTTP + 14 browser)  ·  **Tests found on disk:** 30 `await Check("…")` calls in `verification/BackendChecks/Program.cs` (matches), `frontend/tests/client.test.js` (node:test), `verification/verify_http.py` 276 lines, `verification/verify_browser.py` 304 lines. **Zero xUnit tests.**

## What Astra did well
- **The lost-update lesson is taught end to end, server and client.** `03-WORKED-CHANGE.md` explains why the expected version must come from a strong `If-Match` header rather than a JSON body field ("a field that could be confused with a stored value"), shows the `CheckVersion` call placed *inside* `store.MutateAsync` so the check happens under the lease after a fresh load, and then makes the point most courses miss: "a correct server conflict response paired with a UI that discards the user's draft is still a poor product outcome." That is the actual mid-level lesson.
- **The backend code is idiomatic and readable**, unlike the other large rewrite in this batch. `backend/Api/AppHost.cs:127-161` uses real minimal-API routing with model binding — `app.MapPut("/api/pastes/{slug}", async (string slug, UpdateCommand command, HttpContext context, PasteCommands commands, CancellationToken cancellation) => …)` — and the project is properly layered into `Api/`, `Domain/`, `Data/`, `Models/` with one statement per line.
- **The checks genuinely exercise the change rather than counting calls.** `verification/BackendChecks/Program.cs` spawns **two separate `dotnet` worker processes** writing to the same store and asserts `data.Pastes.Count == 2 && data.Revision == 2` ("Cross-process write was lost."); another check asserts a restart does not rewrite an empty file byte-for-byte; a Windows sharing-conflict check asserts previously accepted bytes survive a failed replacement and accepts *either* `IOException` or `UnauthorizedAccessException` as the failure. The harness returns a meaningful exit code — `return report.passed ? 0 : 1` — so "exitCode 0" in the evidence is real, not a swallowed-failure artifact.
- **Practice tickets state the wrong answer as well as the right one.** `05-PRACTICE.md` Ticket 1: "A page-size selector that only hides rendered rows while requesting the old size is not a complete solution." Ticket 4 ("move the store to SQLite") explicitly asks for `WHERE slug = ? AND version = ?` with an affected-row-count check — a genuinely valuable bridge from this project's file store back to the SQL/EF stack.
- **Verification honesty is excellent.** It reports its own earlier failures (raw title control characters were accepted until a fix; an earlier build's display wrapper could not print a Unicode checkmark to CP1252) and explicitly states the limit of each layer: the client tests "use a controlled fetch implementation; they cannot prove that ASP.NET Core binds the real request correctly."

## Problems found (evidence required)
- **[D2][D7] There is not one xUnit test in the project, and the course teaches the substitute as a virtue.** `04-TESTING-AND-DEBUGGING.md` says "The backend checks are a small console harness referencing the application project. They do not need an external unit-test package", and the run command is `dotnet run --project verification/BackendChecks -- verification-output/backend-first-run`. `dotnet test` does not exist for this repo. A junior who finishes this course still cannot write a `[Fact]`, use `WebApplicationFactory<Program>`, or read a TRX — which is what every .NET job actually asks for. The harness is well built; it is simply the wrong artifact for an upskilling deliverable.
- **[D4] No relational database and no EF Core.** Persistence is a whole-workspace JSON document (`backend/Data/PasteStore.cs`, 246 lines) with a 20 MiB / 2,000-paste cap. The reliability lessons (leases, temp-file replacement, flush) are real and valuable, but they are *file-system* lessons; the target curriculum's EF Core/SQL content is deferred entirely to unimplemented Ticket 4.
- **[D7] `frontend/src/PasteWorkspace.jsx` is 787 lines containing only three components** (`Fields` at line 16, `Explorer` at line 96, `PasteWorkspace` at line 224). The original `main.jsx` was 644 lines, so the rewrite made the single-file problem worse rather than better. A React learner reading this gets no lesson in component decomposition, and the course never comments on the file's size.
- **[D2] minor** The project is a rewrite (94 delivered files) rather than the bounded change the course frames it as, so "no regressions" rests on the new checks alone — there is no pre-existing suite to compare against. The backups confirm the original had no tests at all.

## One-paragraph summary for the index
This is the best-taught reliability course in the batch and the cleanest .NET code Astra produced: idiomatic minimal-API routing, a proper `Api`/`Domain`/`Data` layering, and a headline lesson — optimistic concurrency with `If-Match`, correct 428-vs-412 semantics, idempotent creation receipts, and a UI that preserves the user's draft through a conflict instead of throwing it away — that transfers directly to any CRUD job. The verification record is trustworthy: check counts reconcile exactly (30 on disk, 76 total), the harness returns a real exit code, nine screenshots actually exist, and the write-up volunteers its own earlier defects. Two caveats matter before you commit time: there are **no xUnit tests** (the .NET checks are a bespoke console harness, so you will not learn `dotnet test` here), and persistence is a JSON file rather than EF Core, so the SQL half of the target stack appears only as an unimplemented practice ticket. Do it for the concurrency and idempotency chapters; pair it with an EF Core project for the persistence half. Budget 10-14 hours.
