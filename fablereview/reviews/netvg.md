## What Astra did well
- **It found a genuinely dangerous bug and removed it.** The backup `workforceApi.ts` wrapped `createQuote` in `try { … } catch (error) { … return { …locally computed quote… } }` — so a **400 business rejection** ("Contractor management is not available in Japan") produced a *fabricated successful quote* in the UI using duplicated rate constants from `mockDashboard`. The new version is a thin pass-through and the course states the rule plainly in `05-PRACTICE.md`: "quote creation must not manufacture a success during an outage or business rejection", while deliberately *keeping* the labelled mock fallback for `getDashboard`, where it is honest. Teaching a junior when a fallback is acceptable and when it is a lie is worth the whole course.
- **The error contract is the correct ASP.NET Core one.** `request<T>` now reads the body as text, attempts `JSON.parse`, and prefers `problem.detail ?? problem.title ?? body` — that is exactly the RFC 7807 `ProblemDetails` shape ASP.NET Core emits — with a comment explaining the plain-text fallback ("Some proxies return plain text; keep that useful diagnostic").
- **`RequestGate` is small, correct and actually testable**, and the three Node tests exercise real races with deferred promises, not mocks-of-mocks: *"a slower old response cannot replace the latest result or loading state"*, *"input-edit invalidation suppresses a delayed rejection and allows a fresh retry"*, *"cleanup invalidation suppresses completion without affecting another form instance"*. `07-TRACE-LAB.md` Exercise 7 then asks the learner to explain "why `finally` needs the same gate check as `try`" — the exact subtlety most people get wrong.
- **Evidence reconciles to the digit and the limits are candid.** 13 + 1 = 14 xUnit cases on disk = TRX `total="14"`; 14 + 3 = 17 = `expectedTests`. `04-TESTING-AND-DEBUGGING.md:107` volunteers two flaws in its own suite: "The rounding sample is not a midpoint, so it does not distinguish AwayFromZero from ToEven" and "The two-character `D!` sample reaches unsupported-country lookup rather than a letter-only syntax gate."

## Problems found (evidence required)
- **[D1] The course teaches a factually wrong C# rule about `checked`.** `03-WORKED-CHANGE.md:12`: *"total uses `checked` addition. The `try`/`catch` converts decimal overflow into a controlled failure."* In C#, the `checked`/`unchecked` context has **no effect on `decimal`** — it governs integral arithmetic and conversions only; `decimal` addition throws `OverflowException` in either context. So `checked(request.MonthlyCompensation + estimatedEmployerCosts + platformFee)` in `HiringQuoteCalculator.cs` is a no-op keyword, and a junior will leave with the belief that `checked` is what makes decimal overflow detectable. The behaviour of the code is fine; the explanation is not.
- **[D2] The one behavioural change to rounding is untested, and the test that names it does not test it.** The method now passes `MidpointRounding.AwayFromZero` (a real change from the default banker's rounding, `ToEven`), but the test is `CalculateAsync_NormalizesCodesAndRoundsAwayFromZero()` using `100.005m × 0.21 = 21.00105`, which rounds to `21.00` under *either* mode. The course admits this; it should have added `[InlineData]` for an actual midpoint instead.
- **[D2] Two pieces of newly-introduced dead code.** (a) The `catch (OverflowException)` branch is unreachable: compensation is capped at `1_000_000_000_000m` and the largest multiplier is `0.21m`, nowhere near `decimal.MaxValue` (~7.9 × 10²⁸). (b) The switch defaults were changed from real fallback values to `_ => throw new ArgumentOutOfRangeException()` — unreachable after the earlier `Enum.IsDefined` guard, thrown with no `paramName` or message, and inconsistent with the `Result<T>.Failure` style used for every other rejection in the same method.
- **[D4] There is no CRUD here.** No database, no EF Core, no persistence, no create/read/update/delete — the delivery limits confirm: "No authentication, quote persistence, database, audit log or external provider is added." The project is a stateless pricing calculator plus a form. The validation and error-handling lessons transfer, but a junior looking for the persistence half of the target stack will not find it.
- **[D3] `05-PRACTICE.md` is mostly the answer key, not practice.** Its body walks the learner through the exact implementation Astra already committed — "make the generic `request<T>` helper read the unsuccessful response body as text. Attempt JSON parsing and prefer `detail`, then `title`, then the raw body" — and even pastes the finished `createQuote` source. Only the final "**Exercise 5.**" is an actual task. More broadly, all nine exercises (0–8) are paper/reasoning tasks; not one asks the learner to write code and make a test go green.
- **[D2] minor** No mounted-React test exists (disclosed in the limits), so the `QuoteBuilder.tsx` state machine — where most of the user-visible change lives — is verified only by a TypeScript build.

## One-paragraph summary for the index
A tight, honest course built around one excellent finding: the React client used to *invent a successful quote from mock data whenever the API call failed*, so a legitimate 400 rejection showed the user a real-looking number. Astra deletes that, teaches the correct ASP.NET Core `ProblemDetails` error contract (`detail` → `title` → raw body), tightens the C# calculator's input boundary with `Enum.IsDefined` and ISO-code normalization, and adds a small `RequestGate` token so a slow response cannot overwrite newer UI state — all backed by 14 real xUnit cases and 3 deferred-promise Node tests whose counts reconcile exactly with the TRX. Two things to know before you start: the course states that `checked` is what detects `decimal` overflow, which is **wrong** (`checked`/`unchecked` does not apply to `decimal`), and there is no database, no EF Core and no persistence anywhere in this project — it is a stateless calculator, so treat it as an elective on validation, API error handling and async races rather than a CRUD course. Budget 3-5 hours.
