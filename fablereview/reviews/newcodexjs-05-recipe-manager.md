## What Astra did well
- The single most important distinction in CRUD web development is stated plainly and then demonstrated: "Being logged in is not permission to edit every record. The trusted caller identity comes from the verified token, while the ownership fact comes from the stored recipe; neither should come from a body field supplied by the caller." (`03-WORKED-CHANGE.md`).
- Test 1 proves it with a forged payload, which is the test most juniors never think to write: Bob sends a valid JWT *and* a body containing `user_id: alice.id`, and the API must still return 403 — then the test asserts the stored title is still `'Soup'`. It also covers 403 on DELETE, 403 on GET of a private recipe, 401 with no token, and 200 for the real owner. Five authorization outcomes in one test.
- The lock and the authorization read are in the same transaction as the write (`server/src/services/recipeService.ts:89-96`), with the reason in a comment: `// Lock and authorize inside the same transaction as the nested replacement.` The course is also honest about what a row lock does *not* buy you: "It does not provide an automatic user-facing merge strategy: two authorized sequential updates can still replace one another unless a version policy is added."
- Test 2 forces a *late* failure on purpose — a non-existent `categoryIds: [2147483647]` triggers a foreign-key violation after parent and child writes have begun — then asserts the full graph is unchanged (title, ingredients, steps, with original ids) and that the recipe row count is unchanged on the create path too. The course explains why this design was chosen: "An early validation-only test would not prove transaction atomicity."
- The validator rewrite is a real quality jump, not a cosmetic one. The backup shows the old `parseRecipeInput` did `ingredients.map(...).filter((item) => item.name)` — silently discarding invalid children so a request with three bad ingredients became a recipe with zero. The new version rejects with a `VALIDATION_ERROR`, and test 3 asserts that for eight distinct malformed shapes including `{ingredients:[null]}`, `{steps:[{}]}` and `{isPublic:'false'}`.
- `VERIFICATION.md` lists four checks — `tests`, `build`, `server-typecheck`, `client-typecheck` — all four of which appear at exit 0 in `implementation/checks.json`, and correctly omits any browser-check row.

## One-paragraph summary for the index
The capstone of this batch and the one to do last. It teaches the distinction juniors most often get wrong — authentication tells you who is calling, authorization compares that caller against the *stored* owner, and nothing about ownership may ever come from the request body — and proves it with a test where an authenticated user sends a forged `user_id` and still gets a 403. On top of that it moves the ownership read inside the update transaction behind a `SELECT … FOR UPDATE` lock, scopes the model update by `user_id` as a second barrier, and replaces a validator that silently discarded invalid ingredients (turning a malformed request into an empty recipe) with one that rejects them as domain errors. The rollback test deliberately fails *late* on a foreign key so it proves atomicity rather than validation, and all four claimed checks — tests, build, server typecheck, client typecheck — are backed by the evidence JSON. Expect the heaviest setup of the ten (PostgreSQL plus separate server and client installs) and note two unflagged rough edges: an omitted `isPublic` defaults to public, and the new validator is the densest code in the project yet is the one thing the worked chapter never walks through.
