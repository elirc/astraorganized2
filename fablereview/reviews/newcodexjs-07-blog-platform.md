## What Astra did well
- This is the batch's best *CRUD-semantics* lesson. Partial update is done correctly and explained correctly: `parsePayload(payload, true)` uses `recordSchema.partial()`, so a `PUT {title}` leaves `body` alone, while an explicitly-sent empty body clears it. `02-CONCEPTS.md` states the trap first — "Constructing a full object full of defaults during an edit would erase omitted data" — and `test/crud.test.ts` proves it: after `PUT { title: "Revised fixture" }` it asserts `changed.data.data.body === row.body` and `changed.data.data.id === row.id`.
- A real, silent bug was fixed. The backup's search was `builder.whereRaw("CAST(posts AS TEXT) ILIKE ?", ['%…%'])`, which casts the entire row to text — so searching `"2"` matched any post whose id or timestamp contained a 2. The replacement is a grouped `this.orWhereILike(field, …)` over four named columns, which also makes the filter compose correctly with `where("status", …)` instead of being ANDed against a row-literal match.
- The JSONB lesson is concrete and the fix is applied in both places that write tags: `databasePayload()` in `server/src/models/model.ts` and the seed (`server/db/seeds/001_seed.ts:28` `.map(record => ({...record, tags: JSON.stringify(record.tags)}))`). `02-CONCEPTS.md` names the actual failure mode — "A PostgreSQL JSONB column is not a PostgreSQL text array. The JavaScript driver can interpret an array parameter as a SQL array representation" — which is the kind of driver-level gotcha a junior will otherwise lose a day to.
- Idempotence/error semantics are tested properly: test 4 deletes a record, then asserts a second `DELETE` is 404 and a `PUT` to the same path is 404. The backup's `updateRecord`/`deleteRecord` returned `undefined` and the service only pre-checked via `get()`, so a concurrent delete between check and write produced a 200 with no row.
- Tag deduplication is specified precisely and tested: the zod transform keys on lowercased trimmed text and keeps the last spelling, and the test asserts `["one","ONE","two"] -> ["ONE","two"]`. That is a definition a learner can disagree with — which is what makes it teachable.
- Verification is honest and the evidence even preserves Astra's own failures: `initial-checks.json` records project 58 with `tests exit_code 1` and `server-typecheck exit_code 2`, `database-retry-checks.json` another `tests exit_code 1`, and only the final `checks.json` is all-zero. `logs/58-tests.log` = `# tests 4 # pass 4 # fail 0`, plus `setup-migrate`, `setup-seed`, `client-typecheck`, `server-build`, `server-typecheck` and a browser entry with `"seed_smoke": "passed"` — every one of the eight rows in VERIFICATION.md is backed. All 34 manifest hashes match disk.
- Dependencies here are pinned (`express ^4.21.2`, `knex ^3.1.0`, `zod ^3.24.1`, `typescript ^5.7.2`) rather than `"latest"` as in the JS1 projects, and the setup section correctly explains the workspace install, the `DATABASE_URL` lifetime, and that `npm run build` compiles the server *and* builds the client.

## One-paragraph summary for the index
The clearest lesson in the batch on the CRUD semantics that trip juniors: create vs. partial-update types, what "omitted" means versus "explicitly empty", why a JSONB column is not a text array, and why a delete of an already-deleted row should be a 404 rather than a quiet 200. Astra replaced a field-allowlist with zod create/partial schemas, fixed a genuinely broken search (the old query cast the whole row to text, so a search for "2" matched ids and timestamps), made tag serialization explicit in both the model and the seed, added a stable `created_at desc, id asc` ordering, and hardened the React form against stale search responses and double submits. Four tests run against a real PostgreSQL schema via real migrations, and the batch evidence backs all eight verification rows — including Astra's own earlier failing runs, which were left in the record. Weaknesses are the course furniture, not the code: chapter 7 repeats one paragraph six times, chapter 4 talks about three unrelated projects, and this course is a noun-swap of the kanban and job-tracker ones. Do this one; skip those two.
