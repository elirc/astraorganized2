## What Astra did well
- The server change is the same solid work as its siblings, including a real bug fix: the backup searched with `builder.whereRaw("CAST(applications AS TEXT) ILIKE ?", ['%…%'])`, casting the whole row to text so a search for `"2"` matched ids and timestamps. It is now a grouped `orWhereILike` over `company`, `role`, `stage`, `status`, which also composes correctly with the `status` filter.
- Partial update is right and tested: `recordSchema.partial()` in `parsePayload(payload, true)`, and `test/crud.test.ts:21-36` asserts that after `PUT { company: "Revised fixture" }` the `id` and the omitted `role` are unchanged and a fresh `GET` deep-equals the response. Astra correctly re-nouned the test to `company`/`role` rather than leaving the sibling's `title`/`body` (the `applications` table has neither).
- Missing-row semantics fixed: `update`/`remove` return the affected row and throw `NotFoundError` otherwise; test 4 deletes, then asserts the second `DELETE` and a following `PUT` are both 404.
- Dependencies are pinned (`express ^4.21.2`, `knex ^3.1.0`, `zod ^3.24.1`, `typescript ^5.7.2`) rather than `"latest"` as in the JS1 projects, and the README setup section correctly covers the workspace install, `DATABASE_URL` lifetime, `db:migrate`/`db:seed`, and a separate `astra_test_`-prefixed database for tests.
- Verification is honest: `batch04/logs/60-tests.log` = `# tests 4 # pass 4 # fail 0`, and all eight rows in VERIFICATION.md have matching zero-exit entries in `checks.json` (build, client-typecheck, server-build, server-typecheck, setup-migrate, setup-seed, tests) plus a `browser-checks.json` record with `"seed_smoke": "passed"` and `api_requests: 8`. All 34 manifest `after_sha256` values match the files on disk.

## Problems found (evidence required)
- **[D1]** A noun-swap broke a claim. `02-CONCEPTS.md:7` states: "An update is a partial object: omitting role means retain it, while explicitly sending an **empty role means clear it**." That is false here — `server/src/services/service.ts:6` declares `role: z.string().trim().min(1).max(255)`, so `PUT { role: "" }` returns a 400, not a cleared field. The sentence is true in `07-blog-platform`/`08-kanban-board` where the field it was written for (`body`) is `z.string().trim().min(0).max(20000).default("")`; substituting `role` for `body` made it wrong. A junior following the course's own "predict, then run" instruction will predict a 200 and get a 400.
- **[D8]** The course is a noun-swap of `07-blog-platform`. Measured with `diff` against 07: `02-CONCEPTS.md` differs by **1 line out of 45**, `README.md` by **2 of 67**, `03-WORKED-CHANGE.md` by 7 of 157, `07-TRACE-LAB.md` by 4 of 114. The underlying apps are clones too (same `routes.ts`, same controller/service/model shape, different table and columns). A learner doing 07, 08 and 09 reads the same 8,100 words three times.
- **[D4]** The domain is not modelled. `server/db/migrations/001_init.ts` gives `applications` a `stage` and a `status`, both unconstrained `string(255)` validated only as non-empty text — so `stage: "zzz"` and `status: "qqq"` are a valid application, and nothing distinguishes the two fields. A job tracker's actual CRUD lesson is the pipeline: legal stage transitions (`applied -> screen -> onsite -> offer`), a rejection that is terminal, and an audit row per transition. None of that exists, so the project teaches generic record editing wearing a job-tracker label.
- **[D3/D1]** `07-TRACE-LAB.md` has six "Boundary" headings whose body is the **same paragraph six times**, each pointing at `server/src/services/service.ts` and `parsePayload` — including Boundary 1 ("A React form, button or test sends a concrete operation", i.e. `client/src/App.tsx`), Boundary 5 (the PostgreSQL write in `models/model.ts`) and Boundary 6 (`utils/response.ts`).
- **[D3]** `06-SOLUTIONS-AND-REVIEW.md` repeats one identical **Review:** paragraph under all four exercises.
- **[D8]** `04-TESTING-AND-DEBUGGING.md` carries the shared cross-project paragraph naming Questboard, DevDeck and Live Chat, none of which exists in `newcodexJS`.
- **[D8, minor]** The new root `package.json:2` is `"name": "astra-crud-workspace-60"` — Astra's pipeline stage id shipped into a learner-facing file.
- **[D2, minor]** The advertised client guards (`client/src/App.tsx:28-29`, `const sequence = useRef(0), mutation = useRef(false)`) have no automated coverage; only the Chromium smoke check touches them.
- **[D5]** The documented `npm test` resolves to `npm run test --workspace server` -> `tsx --test ../test/*.test.ts`, a shell glob cmd.exe does not expand; `checks.json` shows the verified run used an explicit absolute path, so the documented command is unverified.
- **[D1, pre-existing noise]** `server/package.json` lists unused server dependencies inherited from the scaffold; the course's "read the server first" instruction sends a junior into them without warning.

## One-paragraph summary for the index
A Knex/PostgreSQL job-application tracker that got the same solid hardening as its two sibling projects: zod create/partial-update schemas, a fix for a search that cast the whole row to text (so "2" matched ids and timestamps), explicit JSONB tag serialization, stable list ordering, and real 404s when updating or deleting an already-deleted row, all covered by four tests against a real database schema. Two things keep it out of the path. First, it is a noun-swap of `newcodexJS/07-blog-platform` — one differing line out of forty-five in the concepts chapter — so doing all three teaches one lesson three times. Second, the swap introduced an error: the course promises that sending an empty `role` clears the field, but `role` is validated `.trim().min(1)`, so it returns a 400, and a learner following the course's own predict-then-run instruction will get the wrong answer. Do `07-blog-platform` instead.
