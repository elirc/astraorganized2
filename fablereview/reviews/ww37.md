## What Astra did well
- Both defects are textbook and both were really there. (1) `backups/109a97addd48/src/repositories/inMemoryInventoryRepository.ts:90-94` does `{...current, ...patch, updatedAt}`, and the old service passed `{sku: input.sku, name: input.name, unit: input.unit, reorderPoint: input.reorderPoint}` — so `PATCH {name}` wrote `sku: undefined` over a real SKU. (2) `createHold` read the item, awaited, then wrote, with no serialization, so two holds could each approve seven units out of ten.
- `runExclusive` is a genuinely instructive implementation: a promise tail (`previous = this.mutationTail`; install a new release promise; `await previous`), cloned Maps captured before the callback, restore-on-throw in `catch`, `release()` in `finally`. `02-CONCEPTS.md` walks through it call-by-call ("Call A saves the current tail, installs its own release promise, and waits for the previous operation").
- The concurrency test does not fake timing: `"serialized holds allow only one of two concurrent over-availability requests"` starts both promises together and asserts one fulfilled / one rejected plus a stored reserved quantity of exactly seven. A second test (`"shared repository preserves sufficient concurrent hold totals"`) proves the lock does not over-reject when capacity is adequate — the check most people forget.
- One test exists purely to **document a weakness**: `"unlocked reads can observe a suspended mutation callback"`. Writing a passing test that pins the limitation rather than hiding it is the single most honest thing in this batch.
- `02-CONCEPTS.md` anticipates the naive fix and explains why it is wrong: "a global 'remove every undefined key' rule would be unsafe: `clearedAt: undefined` can represent a deliberate state transition in an alert update. The owner of each command should decide which keys are meaningful."
- `VERIFICATION.md` is the most reproducible in the batch: Node 22.16.0 named as a requirement, `npm ci`, a PowerShell block with `if ($LASTEXITCODE -ne 0) { throw ... }` after every command, a warning that Node prints experimental-loader/strip-types noise, and a note on why the test script names the file explicitly ("so it cannot silently pass by discovering zero tests").
- Exercises and solutions are properly separated: `05-PRACTICE.md` is prose prompts with predictions ("Explain why an `if (input.reorderPoint)` implementation fails"), `06-SOLUTIONS-AND-REVIEW.md` carries the eight complete code blocks.

## Problems found (evidence required)
- **[D3/D1, omission]** The Next 15 async-`params` migration is applied but never taught. All three dynamic routes changed from `{ params }: { params: { itemId: string } }` to `{ params: Promise<{ itemId: string }> }` with `const { itemId } = await params` (`src/app/api/items/[itemId]/route.ts:16`, `adjust-stock/route.ts:15`, `reservations/[reservationId]/release/route.ts:15`). This is the most transferable Next.js-specific lesson in the whole delivery — it is a breaking change every App Router codebase hits on the 14→15 upgrade — and no chapter mentions it. The delivery summary reduces it to "Updates the staged Next dynamic route parameter shape".
- **[D3]** The relationship between the route's zod validation and the new service-level hand-rolled validators is never explained. Routes call `updateItemSchema.parse(await request.json())` (`src/app/api/items/[itemId]/route.ts:37`), and the service now *also* validates with `assertText`/`assertNonNegativeInteger`/allowlist checks (`src/services/inventoryService.ts:44-101`). `01` and `04` mention Zod only in passing; nothing says why the same rules exist twice or which is authoritative. A junior will copy one and delete the other.
- **[D2, duplication risk]** Those service validators duplicate `src/lib/validation/itemSchemas.ts` by hand — e.g. the minimum SKU length 3 and reorder-point non-negativity appear in both a zod schema and an imperative assert. There is no test that the two agree, so they will drift.
- **[D7]** 5179 words with `02-CONCEPTS.md` at 657 and `06` at 1428, all in dense unbroken paragraphs. The promise-tail explanation, which is the hardest idea in the course, gets one paragraph and no diagram or timeline; a junior who has not written a mutex before will need external reading.
- **[D2, minor]** `runExclusive` clones with `cloneItem`/`cloneReservation`/`cloneAlert`, which the course correctly notes are shallow ("A future nested domain object would need a deeper clone"), but nothing in the code prevents that future mistake — no comment at the clone sites, no test.
- **[D5, minor]** `package.json:10` pins the run to `--experimental-strip-types --experimental-loader ./tests/register-alias.mjs`, which ties the suite to a Node 22 feature flag. VERIFICATION says "Node 22.16.0 or a compatible Node 22 release supporting the checked-in TypeScript strip-types runner", but does not say what breaks on Node 24+ where the loader API changed.

## One-paragraph summary for the index
The best all-round package in the batch: two real bugs in a Next 15 inventory app — a PATCH that wrote `undefined` over metadata the caller never mentioned, and a hold flow where two service instances could each approve seven units out of ten — fixed with a key-by-key patch builder and a repository-owned promise-tail mutex that snapshots and restores state when a callback throws. Thirteen tests cover both the fixes and the retained behavior, including one test written specifically to prove a limitation (an unlocked read can see a suspended callback's intermediate value), and VERIFICATION.md gives a pinned Node version and a PowerShell block that fails loudly at each step. Two gaps to fill yourself: the Next 15 `params: Promise<...>` migration is applied but never explained, and the course never says why the routes' zod schemas and the new service-level asserts both exist. Budget a day; this one is worth doing carefully.
