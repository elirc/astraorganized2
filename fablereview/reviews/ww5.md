## What Astra did well
- The code change is the best-shaped CRUD lesson in this batch. `src/services/approvalService.ts:24-49` now does role check → decision enum check → notes bound → tenant-scoped approval read → assigned-approver check → `PENDING` check → linked-compensation read with `entityType`/tenant match → `SUBMITTED` check, *and only then* enters `withStoreTransaction`. The original (see `astraupskill/snapshots/src__services__approvalService.ts.txt`) updated the approval *first* and then looked up the compensation, so a broken link left a decided approval behind.
- The type-narrowing fix is a real security lesson: `compensationRepository.updateStatus` went from `fields: Partial<CompensationChange> = {}` to `fields: Pick<CompensationChange, "submittedAt"|"approvedAt"|"rejectedAt"|"appliedAt"> = {}` (`src/repositories/compensationRepository.ts:58`). The course explains *why* (`02-CONCEPTS.md`: "Callers must not be able to overwrite the tenant, employee, proposer, amount, or identity while updating a timestamp") and exercise 6 makes the learner demonstrate the identity-overwrite bug.
- The tests actually test behavior, not call counts. `src/tests/state-transition.test.ts` snapshots the whole store with `JSON.stringify(store)` and asserts byte-equality after a rejected call; the rollback test spies `auditService.log` with `mockRejectedValueOnce` and then asserts `status === "DRAFT"`, `notificationJobs` length 0, `auditLogs` length 1; the concurrency test runs two `Promise.allSettled` decisions and asserts exactly one fulfilled and exactly one `APPROVAL_DECIDED` audit row. That is real evidence.
- Verification honesty is genuinely good. Every chapter repeats that the store is process-local: `02-CONCEPTS.md` "A mock transaction can illustrate ordering but cannot prove crash durability or cross-process locking"; `VERIFICATION.md` lists "no durable database transaction, crash recovery, external notification send, durable outbox, or cross-process concurrency proof." The delivery JSON's `limits` array says the same thing. Claimed 11 tests, found 11.
- Correct on the Next.js detail it touches: `withApiHandler` was changed to `const params = routeContext ? await routeContext.params : ({} as TParams)` with `type RouteContext<TParams> = { params: Promise<TParams> }`, which is the right Next 15 App Router route-handler contract.

## Problems found (evidence required)
- **[D8]** Severe template smell *within a single project*: the identical 135-word paragraph beginning "A complete implementation review follows one high risk request through every boundary…" is appended verbatim as a `## Reviewer extension` section to **all nine** files (`grep -c "A complete implementation review follows one high risk request" astraupskill/*.md` returns 1 for every file). That is roughly 1,215 of the 4,198 words — about 29% of the course — one paragraph, nine times. It also mentions idempotency/"persisted receipt" behavior that this project does not implement.
- **[D1]** The trace lab's central worked example cannot be run. `07-TRACE-LAB.md`: "Trace this request: HR manager `u_hr_acme` approves approval `apr_acme_1` for compensation `cc_acme_1`." But `src/lib/db/mockData.ts:167` is `export const mockApprovals: ApprovalRequest[] = [];` — the seed contains **zero** approvals, and `apr_acme_1` appears nowhere in the repo (`grep -rn "apr_acme_1" src` → no hits). Worse, `cc_acme_1` is seeded with `status: "DRAFT"` (`mockData.ts:156`), so after Astra's own change it is precisely the record that *cannot* be decided. The learner must invent the fixture, and the chapter never says so.
- **[D8]** Off-project boilerplate in `04-TESTING-AND-DEBUGGING.md`: "When a **.NET or database test** reports zero tests, inspect the terminal summary rather than trusting a successful process exit." There is no .NET anywhere in this project; this sentence is clearly recycled from a C#/.NET course.
- **[D1]** The course frames Prisma as hypothetical — `07-TRACE-LAB.md`: "If you later replace the mock store with Prisma…" — but `prisma/schema.prisma` and `src/lib/db/prisma.ts` already exist in this project and `@prisma/client` is a dependency. `01-CODEBASE-MAP.md` never mentions either file, so a learner exploring the tree will find an unexplained second persistence layer.
- **[D5]** No fixture or run-the-app path. The commands (`npm install`, `npm test -- --run`, `npx tsc --noEmit`, `npm run build`) are correct and portable, but there is no Node version, no port, no `npm run dev` walkthrough, and — per the previous bullet — the one concrete data scenario the course gives does not exist in the seed. A junior cannot reproduce the trace without writing their own setup.
- **[D5][D7]** `VERIFICATION.md` still addresses Astra, not the learner: "Before handoff, verify listed source hashes and exact snapshots, and exclude private databases, environment files, dependencies, and build output." That is delivery-pipeline instruction, not a study step.
- **[D2, minor]** `withStoreTransaction` (`src/lib/db/mockStore.ts:67-90`) self-deadlocks if nested, because it `await previous` before running `work()`. Nothing nests today (`grep -rn withStoreTransaction src` shows three call sites, all top-level service commands), but the course teaches learners to add new transactional commands in exercise 8 and never warns them about this. Also note the preflight reads sit *outside* the serialized boundary — the course does acknowledge this indirectly in `07-TRACE-LAB.md` ("the initial preflight sees the old pending state only if it wins the serialized boundary"), which is why this is minor rather than a correctness hit.
- **[D3]** Only one fenced code block in the whole course (`03-WORKED-CHANGE.md`) plus a command block in `VERIFICATION.md`. Chapters 01, 02, 04, 05, 06, 07 contain no code at all.

## One-paragraph summary for the index
This is the strongest *code* lesson in B12 and one of the best all-round: a compensation-approval workflow where Astra moved every authorization, tenancy, linkage and lifecycle check ahead of the first write, added expected-status conditional updates so a second decider loses cleanly, narrowed an overly-wide `Partial<T>` update type to a whitelist of timestamp fields, and wrapped the approval/compensation/notification/audit writes in one serialized snapshot-rollback boundary — with 11 tests that assert whole-store equality after failures and race two decisions with `Promise.allSettled`. It is also honest: the course says over and over that its "transaction" is an in-memory teaching substitute and proves nothing about crash durability or cross-process locking. The problems are editorial rather than technical: one 135-word paragraph is pasted verbatim into all nine chapters (~29% of the word count), a stray sentence about ".NET tests" is recycled from another course, and the trace-lab's headline scenario names an approval ID (`apr_acme_1`) that does not exist in the seed data, where `mockApprovals` is an empty array. Fix those four things and this belongs in the core sequence as the canonical "multi-record write with side effects" chapter.
