## What Astra did well
- **Every number checks out.** Claimed 59 = 43 backend + 16 browser. `grep -cE "^\s*test\(" tests/workflow.test.ts` = 43; `browser-tests/board.spec.ts` = 16. The four screenshots referenced in `VERIFICATION.md` exist as real ~100-130 KB PNGs in `astraupskill/images/`. Nothing is inflated, and the delivery JSON's `limits` array matches what the chapters say.
- **It admits its own failed first run.** `VERIFICATION.md`: "The first browser run exposed a stale delete attempt while a comment edit was still completing, plus assertions that matched Next.js's separate route announcer or checked cookies before sign-out finished. The final implementation coordinates pending writes, and the corrected tests wait for accepted behavior." That is the opposite of overclaiming, and the Next.js route-announcer detail is a real, specific Playwright gotcha.
- **The Next.js server-action lesson is correct and non-obvious.** `src/modules/feedback/actions.ts` opens with `"use server"`, resolves the session, calls the service, and only *then* calls `revalidatePath("/", "layout")` inside a `try/catch` that, on failure, still returns `ok: true` with "Refresh failed; reload to see the accepted change." `01-CODEBASE-MAP.md` explains exactly why: "If that refresh fails, the code reports that the write was accepted rather than encouraging the user to submit another create." Most courses get the ordering right and miss the retry-hazard reasoning; this one teaches both.
- **The concurrency distinction is taught properly.** `02-CONCEPTS.md` separates atomicity (`BEGIN IMMEDIATE`, one document update, all-or-nothing status + audit + notifications) from optimistic concurrency (captured version), with the crisp line: "Serializing database writes alone would not detect that Bob edited stale content." The code backs it: `src/server/store.ts:41` `db.exec("BEGIN IMMEDIATE")`, and `service.ts:41` `function expected(record: {version:number}, value:number)` called at nine separate command branches.
- **The tests prove behavior, including cross-process behavior.** `tests/worker.ts` is a second Node process that repeatedly sends `{action:"vote", enabled:true}` for the same user/post; a test runs two of them and asserts a single vote survives. There is also a SQLite trigger that aborts the final aggregate write, after which the test re-reads the database independently to confirm no audit and no notification committed. `04-TESTING-AND-DEBUGGING.md` correctly frames why this beats "calling the same function twice sequentially in one test process."
- **Best reproducibility in the batch.** Root `README.md` pins Node ≥22.16, gives exact PowerShell commands (`npm.cmd ci`, `npm.cmd run setup:local`, `npm.cmd run dev`), the port (`http://127.0.0.1:3011`), exactly which three files setup creates, that setup *refuses to overwrite* any of them, that the original `data/feedback-db.json` is untouched and not auto-imported, that `verify` needs the dev server stopped, and how to redirect evidence with `FEEDBACK_VERIFY_RESULTS_DIR`. `package.json` has an `engines` field and pinned exact versions.
- **Exercises genuinely escalate and solutions are reasoning, not code.** 05-PRACTICE goes presentation (empty state) → feature with untrusted input (draft import preview) → hard distributed problem (idempotency receipts for comment creation) → architecture (relational migration preserving the same invariants). `06-SOLUTIONS-AND-REVIEW.md` opens by stating it "gives the reasoning a reviewer should expect, rather than a block of code to copy," and delivers on that — e.g. it warns that a cascading audit foreign key "could erase the very history the application promises to preserve."

## Problems found (evidence required)
- **[D7]** Only one fenced code block in the entire course: `grep -c '```' astraupskill/*.md` returns 2 for `03-WORKED-CHANGE.md` (one block, the `editPost` command shape) and 0 for the other eight files. For a course whose central artifacts are `transact()` in `src/server/store.ts` and `expected()` in `src/modules/feedback/service.ts`, never showing either is the one real pedagogy gap. The learner is repeatedly told to "open" a file rather than shown the eight lines that matter.
- **[D2, structural]** The delivery touched 59 files and effectively rewrote the application; `diff -r backup project` is not a readable artifact. The brief's "read the diff to see the change" workflow does not apply here, and the course never provides a before/after of the *old* code it replaced (contrast z1 and ww5, which ship `.before`/`.original.txt` snapshots — this project ships screenshots instead). A junior cannot see what the unsigned-cookie/JSON-queue version looked like, only that it existed. `src/server/json-store.ts` is still in the tree as the retired implementation but is never pointed at as the "before."
- **[D7]** Exercises 3 and 4 (durable idempotency receipts with fingerprint comparison inside the transaction; a full relational migration with dry-run counts and index selection) are mid-to-senior work, not junior work. They are correctly sequenced last and `05-PRACTICE.md` frames them as ownership-building, but a junior should be told explicitly that 3 and 4 are multi-day stretch tasks, not the same size as exercise 1.
- **[D1, very minor]** `01-CODEBASE-MAP.md` tells the reader to "compare the cross-process test with the retired process-local queue described in older notes," but the older notes are not linked and the retired `src/server/json-store.ts` is not named at that point. The root README's "The original documentation remains useful historical context" is the only pointer.
- **[D3, minor]** The `revalidatePath` failure path is taught as a live hazard ("If that refresh fails…"), but in Next.js App Router `revalidatePath` is synchronous cache-tag bookkeeping and will rarely throw. The *lesson* (never let a post-commit side effect make the user retry a create) is exactly right; the specific mechanism chosen to illustrate it is slightly artificial and the chapter does not say so.

## One-paragraph summary for the index
This is the best course in B12 and belongs early in the core sequence. It is a real Next.js 16 App Router app with server actions, and Astra replaced its unsigned identity cookie with signed expiring sessions and its truncating multi-write JSON store with a single validated aggregate committed inside a `BEGIN IMMEDIATE` SQLite transaction — then taught the two ideas a junior most often conflates: atomicity (status + audit + follower notifications commit together, proven by a SQLite trigger that aborts the write and a test that re-reads the database) versus optimistic concurrency (the form keeps the version it originally read, so a stale save is rejected even though the transaction serialized cleanly). Every claim I spot-checked matched the code, the 59 tests are real (43 `node:test` + 16 Playwright, both counted on disk), the four screenshots exist, and VERIFICATION.md volunteers that the first browser run failed and why. The setup story is exact: Node ≥22.16, pinned port 3011, a setup script that refuses to overwrite anything, and untouched original data. Its one weakness is that the course shows almost no code — one block in nine files — so read it with `src/server/store.ts`, `src/modules/feedback/service.ts` and `src/modules/feedback/actions.ts` open beside it, and treat practice exercises 3 and 4 as multi-day stretch work.
