## What Astra did well
- **The production change is the best Prisma lesson in B12.** `syncTags` went from `prisma.tag.findFirst(...)` → `prisma.tag.create(...)` (a classic read-then-create race) to `database.tag.upsert({ where: { spaceId_name: { spaceId, name } }, update: {}, create: {...} })`, on the transaction client, backed by a real `@@unique([spaceId, name])` at `prisma/schema.prisma:155`. The inline comment Astra added says exactly why: "The compound unique key makes this safe when two contributors introduce the same tag at once. Keeping the upserts on the transaction client also means a failed link replacement rolls back newly-created tags."
- **The TOCTOU fix in `savePage` is correct and well-reasoned.** The old code looked the page up globally *before* `$transaction` and then used that object inside it. The new code re-reads `tx.page.findUnique({ where: { id: input.pageId }, include: { revisions: ... } })` inside the callback and then checks `currentPage.spaceId !== space.id` → `ForbiddenError`. The added comment states the principle crisply: "The requested space is only a routing hint; the stored page relation is authoritative."
- **The filter-before-limit lesson is real and appears in three query shapes.** `listVisibleFeaturedPages`, `listRecentActivity` and the search path all now compose `visiblePageWhere(actorId, actor)` into the database `where` instead of post-filtering, and `getSpaceOverview` returns `safeSpace = { ...space, pages: visiblePages }` instead of the raw `space` object (`service.ts:167`) — closing a nested-include leak that no list-level filter would have caught.
- **Byte-exact pre-change snapshots with hashes.** `astraupskill/source-snapshots/{queries,schemas,service}.ts.original` plus a `SHA256SUMS.txt`. A reviewer can diff without trusting the prose.
- **Some of the honesty is genuinely good.** `04-TESTING-AND-DEBUGGING.md`: "A transaction mock only proves callback composition; it does not prove SQL rollback or cross-process locking. Keep those claims separate in a verification record." And: "The verification log records what ran and does not turn planned exercises into passing tests." `VERIFICATION.md` also discloses that the first test attempt failed on a stale generated Prisma client.

- **[D2, design]** The change now maintains **two independent implementations of "may this actor read this page"**: `visiblePageWhere` in `queries.ts` (SQL: `status = PUBLISHED` OR actor is `SPACE_ADMIN`/`CONTRIBUTOR` in the page's space) and `canReadPage` in `policies.ts:39-53` (in-memory, additionally takes `pageStatus` and `authorId` and gates on `canReadSpace`). They are close but not identical — `visiblePageWhere` does not consult space membership for read access the way `canReadSpace` does, and it ignores `authorId` entirely. No test asserts the two agree, and no chapter flags the duplication. Divergence between a SQL predicate and an in-memory policy is a classic way an authorization fix later regresses.

## One-paragraph summary for the index
The code change here is worth studying and the course around it is not yet worth doing. Astra fixed three things a junior on the Prisma/Next stack really does get wrong: filtering page visibility in application code *after* `take`, so hidden drafts eat result slots (now a `visiblePageWhere` predicate composed into the Prisma `where`); leaking drafts through a nested `include` even though the top-level list was filtered (now a sanitized `safeSpace`); and doing a `findFirst`-then-`create` tag lookup plus a slug check *outside* `$transaction`, so two simultaneous saves could duplicate a tag and a partially-written page could survive (now `tag.upsert` on the `@@unique([spaceId, name])` key, with slug selection and `syncTags` both on the `tx` client, and the page re-read inside the transaction so a forged `spaceSlug` cannot reparent a page). Every one of those claims checks out against the source. But the packaging undercuts it: the course has no code blocks at all in any of its nine files, its setup instructions never mention `DATABASE_URL` or `db:setup`, every evidence path it cites points outside the project and names an earlier run (`z6-test-03`) than the delivered one (`z6-test-05`), and the three shipped regression tests never import `savePage` — one of them builds a `vi.fn` and then asserts that same mock was called once, while claiming in its name to constrain "the write path." Read `src/modules/knowledge-base/service.ts` and `queries.ts` against the `.original` snapshots; treat the prose as a commentary, and write the two missing tests yourself as the exercise.
