## What Astra did well
- **The best test suite in B12 relative to its size.** Seven tests, none trivial. `projects compensation only for authorized roles` asserts `expect(JSON.stringify(restricted)).not.toContain("$165k-$180k")` *and* `!("compensationBand" in decision)` — i.e. it checks the serialized payload, not a rendered badge. `applies the complete compensation role matrix` loops all five declared roles and uses `Object.hasOwn(row, "compensationBand")`. `orders offsets, year boundaries, ties and invalid instants` builds a fixture with two different offsets representing the same instant (`2026-04-01T08:00:00-04:00` vs `-05:00`), a December/January year boundary, two ties and two invalid strings, and asserts the exact ID order out of *both* builders plus the `Unknown date` labels. `does not mutate the cached shared snapshot` `structuredClone`s the snapshot *and* the raw `getHiringDataset()` result and `toEqual`s both after running every builder.
- **The RSC payload lesson is the single most valuable Next.js-specific insight in this batch.** `03-WORKED-CHANGE.md`: "A browser assertion that a compensation badge is absent could pass even when the value travelled in the server payload. A pure DTO assertion sees the boundary where the sensitive value must disappear." That is exactly the mistake juniors make with Server Components, and the fix (`...(canSeeCompensation ? { compensationBand: ... } : {})`) is the right shape — an absent key rather than `undefined` or a hidden element.
- **The sort-the-label bug is a perfect teaching defect and it was really there.** The backup shows `.sort((left, right) => right.when.localeCompare(left.when))` operating on `formatDateTime` output. `02-CONCEPTS.md` explains the failure in one sentence: "`formatDateTime` converts a timestamp to a Los Angeles label such as `Apr 5, 6:00 AM`. Lexicographic comparison of those labels puts `Dec` before `Jan`." The comparator Astra wrote handles four documented cases (valid/valid by epoch, invalid-last, invalid/invalid by id, ties by id).
- **The `React.cache` immutability point is subtle, correct, and made actionable.** `src/features/shared/server/hiring-repository.ts:5` is `export const getHiringDataset = cache(async () => hiringDataset);`, so the same object is shared per request. `02-CONCEPTS.md`: "`React.cache` does not make mutation safe… `.sort()` mutates its receiver, so builders sort newly mapped arrays and never `snapshot.applicationRecords`." Practice exercise 6 then tells the learner to "Temporarily change a builder to sort `snapshot.applicationRecords` directly and watch this test fail" — a real break-it-and-see loop.
- **Verification honesty is exemplary and self-correcting.** The evidence folder contains both `test-02.log` (an earlier run showing `Tests 4 passed (4)`) and `root-test-01.log` (`Tests 7 passed (7)`), and `VERIFICATION.md` says outright: "Earlier four-test evidence remains historical." It also says "The empty component branch was inspected in source; no browser rendering pass was performed," and even warns "Do not run `next start` as evidence unless a bounded smoke test starts it with a timeout and kills it in a finally block." Nothing is dressed up.
- **Nine exercises with matched solutions, and each one is performable.** Exercise 7 is explicitly labelled "This is a design exercise; the current project is seeded and read-only, so do not claim it is implemented" — which matches the delivery JSON limit "The proposed optimistic-concurrency stage-change command is teaching material only."

## Problems found (evidence required)
- **[D4]** The project has no writes, no database, no transactions and no input validation — `README.md` (course) says so in the second sentence: "It has no write workflow or database. The useful CRUD lesson is therefore the read side." That framing is honest, but against the rubric's target (validation, ownership/authz, transactions, idempotency, pagination, persistence) this course only really covers projection-time authorization and error handling. A junior finishing z7 has learned nothing about persisting a record. It must be paired with a write-side course (ww5, z1 or z3/customer-feedback-board in this batch) rather than read alone.
- **[D2]** One of the four changes alters product behavior on the strength of Astra's own judgement, not a stated requirement. `get-jobs-page-data.ts` now filters `record.application.status === "active"` before counting applications and deriving `openStages`. `"active"` is a legitimate member of `ApplicationStatus` (`src/features/shared/types/hiring.ts:21-26`, alongside `paused`, `withdrawn`, `rejected`, `hired`), and the rationale in `02-CONCEPTS.md` is reasonable ("A historical hired, rejected, paused, or withdrawn record… should not inflate the active pipeline count"). But `paused` applications arguably *are* still in the pipeline, and no requirement, issue or product note is cited. The other three changes are unambiguous defect fixes; this one is a design decision presented as a fix.
- **[D3][D7]** `04-TESTING-AND-DEBUGGING.md` (550 words) contains **zero** code blocks, and `01-CODEBASE-MAP.md` and `05-PRACTICE.md` contain none either (`grep -c '```'` = 0 for all three). The testing chapter describes the `structuredClone` non-mutation pattern and the offset/tie fixture in prose while the actual assertions sit one directory away. Given that 03 and 06 do use code well, this is an inconsistency rather than a systemic gap.
- **[D2, minor]** The empty-state branch in `jobs-screen.tsx` is never exercised by any test — `VERIFICATION.md` admits it ("inspected in source; no browser rendering pass"). `buildJobsPageData` returning `highlightedJob: null` *is* tested, but the JSX branch that consumes it is not, and that branch is the thing that previously crashed on `.title`. A trivial `@testing-library/react` render of `JobsScreen` with `highlightedJob: null` would close this; the project has no React testing library installed.
- **[D7, minor]** The course `README.md` is a single unbroken 370-word block before the navigation list, and `02-CONCEPTS.md` runs 575 words with only one `##`. The exercise and solution chapters are well chunked; the front matter is not.

## One-paragraph summary for the index
Do this one early, and do exercises 1, 2, 3 and 6 properly. It is a small Next.js 16 App Router app with no database, so it teaches only the read half of CRUD — but it teaches it better than anything else in this batch. Astra found three defects that are all classic junior mistakes: a compensation band that was serialized into the React Server Component payload for every role and merely *hidden* by the component (so a restricted user's network response contained the salary); two lists sorted by their formatted display label instead of the stored instant, so "Dec" sorted before "Jan"; and a `highlightedJob` read that crashed on an empty dataset. The fixes are small and exactly right, and the seven Vitest tests are the strongest in B12 — they assert on `JSON.stringify` output rather than rendered markup, loop the full five-role matrix with `Object.hasOwn`, build a fixture with two timezone offsets, a year boundary, ties and invalid instants and assert the exact resulting order, and `structuredClone` both the snapshot and the cached dataset to prove no builder mutates shared state. The evidence folder even keeps a superseded four-test log and labels it as historical. Its only real limitation is scope: there are no writes, no transactions and no persistence here, so pair it with ww5, z1 or z3/customer-feedback-board.
